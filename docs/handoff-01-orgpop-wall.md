## ユーザーからのフィードバック（原文）

> 人気の上げ方難しい。シーズン30くらいまでやってもドームでの興行ができなかった。
> 人気は上がったり下がったりするのは現実でもあるので分かるが、何が原因で上がったり

要するに **(a) 人気が上がらずドーム興行に到達できない**、**(b) 上下動の原因が分からない** の2点。

## 実コード調査で判明した根本原因

### 原因1: orgPop 70+ 帯は数学的に純減する

**逓減カーブ** (`src/management.js` L10425 `Engine.orgPop.getDiminishingMultiplier`):

| orgPop帯 | 倍率 |
|---|---|
| 0–20 | ×1.00 |
| 20–40 | ×0.70 |
| 40–55 | ×0.35 |
| 55–70 | ×0.20 |
| **70–85** | **×0.12** |
| **85+** | **×0.08以下** |

**★→orgPop変動の生値** (`src/data.js` L1173 `SHOW_RATING_CONFIG.orgPopDeltaByStars`):
- ★5 → +2.0 / ★4 → +1.0 / ★3 → ±0 / ★2 → -0.5 / ★1 → -1.0

**年次自然減衰** (`src/management.js` L10444 `Engine.orgPop.calcAnnualDecay`):
- <50: -1 / <65: -2 / **<80: -4** / **<90: -7** / 90+: さらに大

**1シーズン12興行と仮定したシミュレーション**:

| orgPop帯 | ★5平均(年間+) | ★4平均(年間+) | 年次減衰 | ★5フル稼働の純増 |
|---|---|---|---|---|
| 70–80 | +2.88 | +1.44 | -4 | **-1.12** |
| 80–85 | +2.88 | +1.44 | -4 | **-1.12** |
| 85–90 | +1.92 | +0.96 | -7 | **-5.08** |

**→ orgPop 70を超えた瞬間から、★5を量産しても毎シーズン純減する。** これがシーズン30回してもドームに届かない直接原因。

### 原因2: ドーム集客の数学的天井

`src/data.js` L885: ドーム cap = **30,000**
`src/data.js` L889 `BASE_ATTENDANCE_CURVE`:
- orgPop 90 → 7,000 / 95 → 8,500 / **100 → 10,000**

`venue-attendance-spec-v2.0.md` §2.2 reach上限:
- orgPop 100 → reach 14,000、ソフトキャップ込みで上限 約 **18,000人**

**→ 仮にorgPop 100に到達してもドームは6割しか埋まらない設計。** 「ドームでの興行ができる/できない」以前に、ドームは現状「絶対に成立しない選択肢」になっている。

### 原因3: 人気変動の「見えない要素」が多すぎる

`src/management.js` L7104 のイベント表示:
```
📊 ★4 (MQ avg 65) → 団体人気+0.12 (現在: 72)
```
プレイヤーには「★4で+0.12」しか見えない。**本来+1.0が逓減で0.12に削られた**ことが完全に隠れている。さらに以下も全部サイレント:

| 要素 | コード位置 | 影響 |
|---|---|---|
| 逓減カーブ適用 | L10425, L10435 | ★効果が見えない倍率で削られる |
| 年次自然減衰 | L9407, L10444 | シーズン末に-1〜-7、通知なし |
| ガラガラペナルティ | L6327, MOMENTUM_CONFIG.EMPTY_ORGPOP_PENALTY | -0.5、別経路 |
| 王者リーダー気質 | L6759-6765 | +0.3/週、サイレント |
| 抗争解決ボーナス | L7033-7034 | +rivalOrgPopBonus、間接表示 |
| メディアアクション | L12644 | +0.4/回、ケア画面側 |
| 興行後追加抗争ボーナス | L7100 | bookedRivalryOrgPopBonus、サイレント |

## 検討した対策の方向性（前回会話で話したもの）

### 方向A: 数値バランスの根本調整

- 70–85帯の逓減を ×0.12 → **×0.20** 程度に緩和
- 85+帯の逓減も比例して引き上げ
- 年次減衰 -4/-7 → **-2/-4** 程度に緩和
- もしくは ★5 orgPopDeltaByStars を 2.0 → **3.0**
- 同時に `BASE_ATTENDANCE_CURVE` の orgPop 95–100帯を持ち上げる（10,000 → **15,000程度**）
- 数値だけを動かすとバランス全体が動くため、auto-sim での影響確認が必須

### 方向B: 透明性UI改善（プレイヤーが因果を理解できるように）

興行後イベントの表示を内訳付きに:
```
📊 興行収支
  ★4興行 …………… +1.00
  人気帯逓減 ……… ×0.12
  ────────────
  小計 ……………… +0.12

  リーダー気質(王者) +0.04
  満員ボーナス …… +0.04
  ─────────────
  合計 …………… +0.20 (現在: 72)
```

シーズン末に専用通知:
```
📰 シーズン末年次評価
  人気帯による自然減衰 -4
  (大きな団体ほど維持が大変)
```

### 推奨

**A + B を両方実施しないと意味がない。**
- A だけ → 「数字いじっただけ」で何が変わったかプレイヤーに伝わらない
- B だけ → 「見えるけど超えられない壁が見える」だけになりフラストレーションが増す

## 新しい部屋で最初にやるべきこと（推奨手順）

1. **リポジトリを clone する**（手元の情報だけで進めない）
2. `specs/venue-attendance-spec-v2.0.md` と `src/management.js` の `Engine.orgPop` モジュール (L10421-10510) を実際に読み直す
3. `test/auto-sim.js` を確認して、現状の orgPop推移をシミュレートする手段を把握する
4. 仕様書ドラフトを書く前に、auto-sim でシーズン30相当を回して **現状の orgPop 上限実測値**を取る（理論値と一致するか検証）
5. 仕様書 `specs/orgpop-rebalance-spec-v1.0.md` のドラフトを作成
6. ドラフトをユーザーレビュー → 確定 → 実装
