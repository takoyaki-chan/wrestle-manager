## TL;DR

1. **実効データは再代入側**(旧軸・2026-03-14の原文系統+4月の増補)。const側(新軸)はGL-01〜GL-10が後勝ち上書きで死んでおり、**歴代のブック経由改訂(03-16の全行改訂・08-11の口調全直し)はすべて死んだconst側に積まれてきた**。つまりGLIMPSE_Bの承認済み改訂は一度も画面に出ていない。
2. さらに悪いことに、2026-08-01のgetDialoguePool軸入れ替え以降、**実効(旧軸)側は全アーキタイプ×全性格が `normal._default` に落ちる**(実測10/10コンボが同一セリフ)。B層は現在、性格も口調も分岐しない「テンプレ一本」状態。
3. 原因は構造的: セリフ抽出パーサ(`tools/extract-dialogue-parser.js`)は `const宣言` と `ドットパス代入`(GLIMPSE_A型)しか拾わず、**ブラケット代入(`GLIMPSE_B_LINES['GL-01'] =`)とpush実行文は不可視**。exportはconst側だけをブックに載せ、applyはconst側だけに書き戻す。ズレは仕組みで再生産される。
4. **推奨: const側(新軸)を正として統一**。実効側にしかない生存セル(composed 42+GL-02-hostile 13)を新軸へ移植し、4月の文脈ズレセル群は原則削除、再代入・pushブロックを撤去する。

## 4. 【重大】実効側は平坦化している(getDialoguePoolの罠)

08-01の `getDialoguePool` は archetype第一で探索し、`archKeys = [a,'standard','_default','normal']` / `persKeys = [p,'normal','_default']`。旧軸の実効データではトップの `normal`(性格バケツ)が archKeys の 'normal' にヒットし、その中の `_default`(改名を免れた旧キー)が persKeys の '_default' にヒットするため、**第1ループが常に `normal._default` を返す**。

実測(GL-01勝利、実データ+実関数):

| コンボ | 現状の実効 | const側を実効にした場合 |
|---|---|---|
| 標準×強気 | よし、勝てた。この調子で頑張ろう | 楽勝！ 私に勝てるわけないでしょ |
| ヤンキー×強気 | よし、勝てた。この調子で頑張ろう | へっ、雑魚が。話にならねぇ |
| お嬢様×ノーマル | よし、勝てた。この調子で頑張ろう | 勝てたわ。……積み上げたものが、出ただけね |
| クール×寡黙 | よし、勝てた。この調子で頑張ろう | ……勝った。それでいい |
| (計10コンボ) | **全部同一** | 全部セル別に正しく分岐 |

- GLIMPSE_Aが無事なのは、内側キーが `standard` に改名済みで第1ループが正しく外れ、第2ループ(性格第一)に到達するため。GLIMPSE_B実効側は `_default` が残ったせいで誤ヒットする
- 副作用: 棚卸し09の分類3b(`_default`のあたし行)は「在籍セルに発火する」と書いたが、**08-01以降は実際には発火していなかった**(全員がnormal._defaultに落ちるため)。修正自体は正しいので影響なし
- 4月の文脈ズレセル群が今まで無害だったのも、この平坦化が発火を握り潰していたため。**平坦化だけ直すとズレセリフが画面に出始める**ので、統一とセル整理は同時に行うこと

## 5. ワークブックパイプラインの構造欠陥(タスク③の答え)

`tools/extract-dialogue-parser.js` の宣言検出正規表現は `const NAME =` と `path.to.existing =`(**ドットパスのみ**)。`GLIMPSE_B_LINES['GL-01'] =` のようなブラケット代入は構文上ドットパスでないためマッチせず、push実行文も宣言でないため対象外。

- **export**: sandboxにはconst側しか入らない → ブックはconst側(死にデータ)を写す。08-12の実測(HEADのブックに私版あり・あたし版なし)と一致
- **apply**: 同じ宣言スキャンでID解決するため、改訂はconst側に書き戻される(6295662のdiffで確認)
- **GL-02-hostile(13セル)とpush群はブックに一度も載っていない** = 全直しレビューのスコープ漏れ
- src全体でトップレベルのブラケット代入はGLIMPSE_Bの11箇所だけ(全数grep確認)。**このテーブルだけが盲点だった**。キーにハイフンが入る('GL-01')ためドット記法が使えなかったのが遠因

## 6. 方針の選択肢と推奨

**案A(推奨): const側(新軸)を正として1定義に統一する**

- 根拠: (a)const側が承認済み改訂の正統(03-16改訂+08-11全直し+Keisukeレビュー済みのブックと一致)、(b)新軸はプロジェクト方針「第一分岐はarchetype」に一致、(c)統一だけで§4の平坦化も§5の盲点も同時に消える(ブラケット代入が存在しなくなる)
- 失うもの: 実効側にしかない127セル → **生存させたい55セル(composed42+hostile13)は新軸へ転置してconstに移植**するので実質失わない。移植分は未検品なので次の検品サイクル対象として記録

**案B: 再代入側を正とする** — ✗ 非推奨。承認済みの08-11全直しを丸ごと捨てることになり、ブックと実効の乖離が固定化し、平坦化バグも別途直す必要が残る。
