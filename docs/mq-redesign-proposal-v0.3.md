## 1. 経路一本化 — 方向①+profile方式(survey選択肢5)⭐

### 1.1 構造

`Engine.mq.finalize(state, matchResult, context, profile)` を純粋関数として新設する。

- **入力**: シミュレーション済みのエンジン素点(再シミュレーションしない)+興行文脈(因縁/タイトル/観客・会場/バフ/ラストラン/trust/鮮度)+profile名
- **出力**: 最終MQ+寄与内訳メタデータ(mqInventory相当を標準装備)
- **呼び出し元**: `App._finalizeShowImpl`(UI)と `Engine.executeShow`(headless)が**同じ関数**を呼ぶ。app.js 側の独立加算(6143-6146, 6413-6432)は全廃

### 1.2 profile定義

| profile | 適用要素 | 使用経路 |
|---|---|---|
| `normal-single` | 因縁/タイトル/観客・会場/マイルストーン2種/ラストラン/trust/鮮度 | プレイヤー通常興行・headless通常興行(シングル) |
| `normal-tag` | 観客・会場/ラストラン(+将来タッグ因縁を入れる余地) | 同(タッグ) |
| `ppv` | 因縁のみ(現状維持) | PPV/天頂戦 |
| `raw` | 補正なし(素点=最終) | ジュニア/春タッグ/秋勝ち残り/B3等イベント戦 |
| `ai-show` | 因縁のみ(現状維持) | AI通常興行 |

特殊興行に通常会場補正を持ち込まない(大会仕様変更はしない)。**経路は一本、仕様差はprofileで明示**が原則。

### 1.3 一本化に伴う個別決定

| 論点 | 決定案 |
|---|---|
| 鮮度(初顔+2/マンネリ-1〜-5) | ✅ **決定: 集客専用へ移す**(2026-07-24 Keisuke決裁。フェーブル推奨の「MQに残す」を退けた)。MQ加算は全経路から除去(UI経路の加算も廃止)。既存の鮮度ラベル計算(Engine側matchupLog)は維持し、動員計算への係数適用へ転用する。数値設計はP3。**不変条件: 同カード連発への抑止力(マンネリカードの実質ペナルティ)が動員側で維持されること** |
| +12外部キャップ | ⭐ **廃止**。実測到達0%の死んだ機構。外部補正の暴れは§3の再設計側で抑える(キャップで縛るのではなく、そもそも盛らない) |
| trustペナルティ | ⭐ 維持(normal-single)。発動1.81%と稀だが「士気が崩れた選手の試合は精彩を欠く」は嘘のない因果。UIにも初適用になる点だけ留意 |
| マイルストーン2種/ラストラン/次戦バフのMQ加算 | ⭐ 維持(normal-single/tag)。UI経路にも初適用=バフが謳い文句どおりに効くようになる(現状はUIで半分死んでいたバグ的状態の解消) |
| 次戦MQバフの消費責務 | 共通関数側で消費(1回限りの管理を一元化) |
| attendanceの経路差(タッグappeal 0扱い/Engine側、attendanceMultiplier 2種/App側) | 共通関数のスコープ外だが同時に揃える。App側実装(4人draw power平均+Multiplier適用)を正としてEngine側へ移植 |
| タイトルfallback(+15/App) | 削除。定数+5に一本化 |
| ケミストリー分岐(常に0) | 全経路から削除(dead code掃除) |
| タイトル格差ペナルティのメタデータ | 削除 |

### 1.4 既存セーブ

過去の保存MQは書き換えない(survey D-2どおり)。セーブに移行バージョンを記録し、新経路は未来の試合から。

## 2. 上限撤廃+「歴代最高MQ」記録制 ⭐

Keisuke起案を採用し、以下のとおり具体化する。

### 2.1 クランプ整理

| 箇所 | 現状 | 変更後 |
|---|---|---|
| シングル素点 | 下限5・上限なし | 変更なし |
| タッグ素点 | 5〜100クランプ | ⭐ **内部100クランプ撤廃**(下限5のみ)。シングルと同思想に統一(survey E-2の選択肢1) |
| UI経路の段階的100クランプ | あり(4箇所) | **全廃**(共通関数に置換された時点で消滅) |
| 最終確定 | 経路によりまちまち | 全profile共通で `max(5, ...)`・上限なし |

### 2.2 歴代最高MQ記録(`state.mqRecord`)

```
state.mqRecord = {
  value: 100,          // 初期値100(Keisuke案採用。序盤の安売りを防ぐ)
  holderIds: null,     // 記録保持者(2〜4名)
  orgId: null, season: null, week: null, stage: null  // どの舞台か
}
```

- **スコープ**: ✅ **決定: 業界記録(全団体・全経路)を1本**(2026-07-24決裁)。新聞は業界紙なので、AI団体やPPV・天頂戦で生まれた名勝負も一面になる。自団体記録・シーズン記録は既存の careerBestMQ / seasonBestMQ が既にあるため新設しない
- **更新判定**: `Engine.mq.finalize` の返却値で判定(全経路が自然に対象になる。一本化の恩恵そのもの)
- **既存セーブ移行**: `max(100, 保存済みcareerBestMQの最大値)` で初期化。旧セーブで即・記録更新ラッシュが起きるのを防ぐ

### 2.3 名勝負の相対判定

- **機械系の閾値(trust/人気/成長/関係値の30〜80帯)は絶対値のまま維持**。これらは「良い試合だったか」の判定であり、歴史的名勝負とは別の概念。全面相対化は下流破壊が大きすぎる(棚卸し§6)
- **物語系(新聞評価・年代記・実績・「名勝負」ラベル)だけ記録連動へ**: `mqRecord.value - 5` 以上を「歴代級」、記録更新を「事件」として扱う
- 数値表示は現状のまま(100超もそのまま表示)。「歴代最高◯◯」を併記する見せ方はD側の演出設計で扱う

### 2.4 線形報酬の保護

100超で伸び続ける2箇所は入力側で飽和させる:
- 対抗戦/挑戦状メディア収入 `MQ×eventPerMQ` → `min(MQ,100)×eventPerMQ`
- MVP/ランキングの `bestMQ×0.3` 系 → 同様に `min(MQ,100)` を入力
(星・閾値系は棚卸し§6で100超安全を確認済み)

## 3. 外部補正の再設計 — 「下駄」から「状況の増幅」へ

### 3.1 問題の実体(実測)

観客/会場補正: 平均+4.013、発動99.54%、σ0.438。**ほぼ全試合に同じ+4が乗る定数**であり、補正ではなく下駄。外部寄与の約8割を占めながら試合間の差を作っていない。

### 3.2 再設計案 ✅ 決定(2026-07-24決裁)

**「普通の入りの興行=0」を中心に、正負対称の帯へ組み直す。**

| 状況 | 現行 | 案 |
|---|---|---|
| 超満員(95%+) | +2〜+3 | +3 |
| 満員(85%+) | +1〜+2 | +1 |
| 普通(60〜85%) | 0〜+1 | **0** |
| まばら(40〜60%) | -1 | -2 |
| 閑古鳥(40%未満) | -3 | -4 |
| 会場格ボーナス | 0〜+3(ほぼ常時) | **廃止**(会場の格は期待値=採点基準側が背負う。§3.3) |

- 意図: 「客が入って会場が沸いたから試合が跳ねた」は満員のときだけ起きる特別な事実になる。ガラガラの会場では名勝負も冷える——残酷さも正しく出る
- 平均MQが約4点下がるため、下流の期待値定数を同時に再較正する: `EXPECTED_MQ_BY_VENUE`(ui-render.js)/ `SHOW_RATING_CONFIG.expectedMQTotal`(data.js)/ 新聞寸評5段階。**この再較正が本丸の作業**であり、数値草案はフェーブルが出し、計測はauto-simで検証する
- **不変条件(feedback_numeric_targets_need_invariants 準拠)**:
  1. 通常興行の最終MQ平均は現行55.8±2.0に収まる(較正後)
  2. 観客/会場補正の発動率(≠0の割合)は40%以下に下がる(下駄の解消)
  3. 満員興行と閑古鳥興行の同カードMQ差が平均5点以上つく(差を作る補正になる)
  4. 星評価分布(1〜5★)の各帯比率が現行±5ptに収まる

### 3.3 会場の格の行き先

会場ボーナス(0〜+3)は廃止するが消すのではなく、**採点基準(期待値)側へ移す**。ドーム興行はMQが上がるのではなく「求められる水準が上がる」——同じMQ60でも公民館なら快挙、ドームなら物足りない。これは新聞寸評の `expectedMQ` が既に持っている思想であり、そちらへ一本化する。

### 3.4 触らないもの

- 因縁(+1〜+5、発動36.7%、σ1.463): 発動が選択的で差を作れており、物語的裏付けもある。**現状維持**
- ドラマ減点/ペーシング/決着減点: エンジン素点側は今回のスコープ外(§5参照)

## 5. 大ニュース新聞システム(週頭通知+一面)

基盤調査(2026-07-24)の結論: **一面選出の仕組みは既にある**。`Engine.newspaper.PRIORITY`(management.js:25981〜)の priority ソートで `topStory` が決まるため、大ニュースは既存機構への追加で実現できる。新設が必要なのは「週頭通知の器」と「記事タイプ3種」のみ。

### 5.1 大ニュースの定義と対象 ✅ 決定(2026-07-24 Keisuke選定)

**Tier S(大ニュース=一面ジャック+週頭通知)は新設4種のみ。既存記事からの昇格はなし**(王座交代・派閥・破産系は見送り。運用後に頻度の体感を見て再検討可)。

| トリガー | 種別 | 頻度想定 |
|---|---|---|
| 歴代最高MQ更新(§2.2) | 新設 | 数シーズンに1回 |
| 大物ルーキーデビュー(trainCap-OVR 125+) | 新設(ロードマップ起案済み) | 上位2%≒数シーズンに1回 |
| 期待のライバル関係(同年代117+が2人、初めて揃った年) | 新設(同上) | 稀 |
| **トップ団体王者の重傷**(業界ランキング1位・2位の団体の王者が重傷以上の怪我) | **新設(2026-07-24 Keisuke追加起案)。記事タイプ自体も新規** | 稀 |

**頻度の設計原則: 大ニュースは年に数回まで**。毎週鳴るピロリんは事件ではなく騒音になる。

### 5.2 大ニュース判定の仕組み ⭐

「大ニュース」を priority の付け替えで作らない。**`BIG_NEWS_TYPES` 集合を新設**し、週次新聞生成後に `topStory.type ∈ BIG_NEWS_TYPES` なら `weeklyNewspaper.isBigNews = true` を立てる。

- 新設3種(記録更新/大物ルーキー/ライバル揃い踏み)は priority 300超(leagueElevation より上)で一面を保証しつつ、集合にも登録
- 既存記事の昇格(王座交代180等)は **priorityを動かさず集合に足すだけ**。「一面に載る条件」と「週頭に鳴らす条件」を分離することで、既存の紙面バランス(王座交代130帯・興行120帯の設計)を壊さない
- 記事化ルートは既存の `Engine.industryNews.push` → `NEWS_HEADLINE_TEMPLATES` パターンに乗せる

### 5.3 週頭通知の器(要デザイン・コンセプト案)

発火点: 週送り後の `popupActions` チェーン(app.js:9362〜)に追加。`isBigNews` かつ未通知の週のみ。

- **SE**: 既存 `notify`(E6→F6の2音、まさにピロリん)をベースに、大ニュース専用 `bignews` SE を新規合成(notify+ベル系スパークル)。本作のSEは全てWeb Audio合成が流儀なので素材ファイル不要
- **ポップアップ**: 軽量モーダル1枚 — 新聞アイコンがドロップイン+見出し1行チラ見せ+「紙面を読む」(→新聞1面へ遷移)/「あとで」(→ナビの📰ボタンに未読バッジ点灯、閲覧で消灯)
- 新聞1面を開いたときの `paper`+`reveal` SEは既存流儀をそのまま使う
- 既存スナップショット通知(ログ行止まり・8%抽選)とは別経路。大ニュースは確実に届ける(snapshot-notification設計原則3「緊急は見逃さない」と同じ思想)

### 5.4 新設3記事の発火設計

| type | 発火タイミング | 判定材料(既存流用) |
|---|---|---|
| `mqAllTimeRecord` | 記録更新が起きた週の新聞 | `state.mqRecord`(§2.2)。careerBestMQ更新と同じフック地点で検知 |
| `hotProspectDebut` | trainCap-OVR 125+ の新人の**デビュー戦が行われた週** | `Engine.rival.trainCapOVR`(management.js:6949)+careerHistoryのdebutイベント。デビュー記事自体が現状ゼロなので新設 |
| `fatedRivals` | 同年代・trainCap-OVR 117+ が2人**初めて揃った年**の、2人目のデビュー戦週 | 同上+年齢差判定。1団体内に限定しない(業界紙視点) |
| `topChampionInjury` | 業界ランキング1位または2位の団体の**現王者**が**重傷以上**の怪我を負った週 | 団体ランキング(org-ranking-spec-v2.0)+王座保持情報+怪我重篤度。**AI団体の王者・怪我データがどこまで追跡されているかの調査が実装前に必要** |

※ ロードマップは「年齢差1歳以内」。コードベースの同世代慣例は3歳以内(relationships.js)だが、**こちらは"逸材が同時代に現れた"という希少事件**なので、起案どおり1歳以内の狭い定義を維持する。

### 5.5 記事文面

黒田トーンで各type 2〜3バリエーション → **Opusに執筆委託、全文Keisukeレビュー**(feedback_text_review_required)。ナレーション方針は「格言禁止・事実記述」(feedback_narration_factual_wording)に従う。
