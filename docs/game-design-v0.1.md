# ■ 第1部：現行シミュレーター分析

## 1.1 アーキテクチャ概要

現行システムは**単一HTMLファイル**（約1,760行）にCSS・JS・データすべてを内包。バニラJSのみでフレームワーク不使用。

**構成要素**
- CSS（約480行）：アニメーション・レスポンシブ含む
- HTML構造（約12行）：最小限のコンテナのみ。全UIはJSで動的生成
- データ定義（約150行）：キャラクター・技テーブル・実況テンプレート
- オーディオエンジン（約110行）：Web Audio APIによる効果音合成
- ゲームロジック（約450行）：ターン処理・ダメージ計算・決着判定
- UI描画（約350行）：選択画面・試合画面・リザルト・モーダル

## 1.2 現行パラメータ体系

| パラメータ | 略称 | 値域 | 用途 |
|-----------|------|------|------|
| Power | pw | 58-90 | ダメージ計算の攻撃基礎値 |
| Speed | sp | 68-91 | 攻撃側決定の確率補正 |
| Technique | te | 47-91 | ダメージ計算の攻撃補助値 |
| Stamina | st | 68-85 | HP算出基礎値 + 防御基礎値 |
| Mental | mn | 63-91 | ギブアップ耐性 + キックアウト確率 |

**HP計算**: `HP = stamina × 1.9`（例: st79 → HP150）
**Overall**: `(pw + sp + te + st) / 4`（mnは含まない）

### 分析ポイント
- ✅ 5パラメータでバランスよく役割分担されている
- ⚠️ Mentalが唯一Overallに含まれず、「隠しステータス」的な立ち位置
- ⚠️ Speedの影響が限定的（攻撃側決定確率のみ）
- ⚠️ スタミナが「HP算出」と「防御力」を兼任しており、二重の役割

## 1.3 ダメージ計算式

```javascript
base = move.d + (atk.pw × 0.15) + (atk.te × 0.1)
defense = (def.st × 0.1) + (def.mn × 0.035)
mMod = 1 + (momentum_advantage × 0.003)
rF = 0.85 + (random × 0.3)  // 0.85〜1.15
raw = (base - defense) × mMod × rF × phase.mult
dmg = max(4, round(raw))
```

**フェーズ乗数**

| フェーズ | ターン | 乗数 | スタイル技確率 |
|---------|-------|------|--------------|
| Opening | 1-4 | ×0.9 | 20% |
| Mid | 5-8 | ×1.05 | 40% |
| End | 9-12 | ×1.2 | 55% |
| Climax | 13-20 | ×1.4 | 70% |

### 分析ポイント
- ✅ フェーズによるダメージ段階制は試合にドラマ性を生む
- ✅ モメンタム補正で「流れ」を表現
- ⚠️ プレイヤーの介入がない（全自動シミュレーション）
- ⚠️ 技の差別化が「ダメージ値d」のみ。命中率・追加効果なし
- ⚠️ 同じ技を連続で使う可能性がある（前ターンの記憶がない）

## 1.4 技システム

**共通技プール**: 約70技（6カテゴリ）
- strike（20技）: d2〜d10
- throw（20技）: d2〜d10
- submission（14技）: d2〜d9
- aerial（8技）: d7〜d9
- ground（8技）: d3〜d5
- rollup（7技）: d4〜d5

**スタイル専用技プール**: 7スタイル × 12技（d10〜d16）

**技選択ロジック**:
1. フェーズのsCh%でスタイル技プールか共通技プールかを決定
2. catW（スタイル別カテゴリ重み）で技カテゴリを選択
3. 該当カテゴリからランダムに1技を選出

### 分析ポイント
- ✅ 7スタイルの差別化がカテゴリ重みで明確
- ✅ 共通技→スタイル技の段階的エスカレーションが自然
- ⚠️ キャラ固有の必殺技（フィニッシャー）が不在
- ⚠️ 技にコスト概念がない（スタミナ消費なし）
- ⚠️ 技の「命中判定」がない（全技100%命中）

## 1.5 決着システム

| 条件 | トリガー | 判定 |
|------|---------|------|
| フォール | HP≤0時、ギブアップ以外 | キックアウト確率 = (mn/100)×0.40。最大2回まで |
| ギブアップ | HP≤0時、確率判定 | 脱出確率 = (mn/100)×0.35。最大2回まで |
| 丸め込み | rollup技 + HP≤25% | 成功率15%固定 |
| タイムアップ | ターン20超過 | HP残量比較で判定勝ち or ドロー |

**Finish Clickシステム**（v3.5新機能）:
- フォール/ギブアップ/丸め込みの結果は**事前に内部決定**
- プレイヤーにクリックを要求し、演出的な「間」を作る
- 結果自体はクリックに影響されない（演出専用）

### 分析ポイント
- ✅ Finish Clickは「観戦の臨場感」を生む優れた演出
- ✅ キックアウト上限2回で「引き延ばし」を防止
- ✅ 丸め込み15%は番狂わせ要素として機能
- ⚠️ プレイヤーの判断は結果に影響しない
- ⚠️ ギブアップ判定がHP0時のみ（途中で極めて勝つ概念がない）

## 2.4 全体設計の方針確定（オーナーフィードバック第2弾 2/19）

### ★ 能力値スケールの変更
**200段階制へ拡大**:
- 一般レベル: 50〜90程度
- トップ層: 80前後で戦っている
- 100超えたら「こいつ強くなったな」と感じるライン
- 潜在能力（才能値）はトップ級で160程度。ほぼ到達不可能
- 最盛期でも100前後が現実的な天井

### ★ 育成システムの大幅変更
**練習メニュー個別割り当ては廃止**:
- 成長は「才能のあり方に自然に引っ張られる」形
- 毎週の成長はランダムだが、才能傾向に沿って偏る

**コーチシステム（新規）**:
- コーチを雇用することで成長率にボーナス
- コーチによって得意分野が異なる
- プレイヤーの育成介入は「どのコーチを雇うか」が主な判断ポイント

### ★ スカウトプール再登場年齢
- 固定15歳ではなく、**13〜17歳の幅**で再登場

### ★ 才能値の設計変更
- 才能値は「ランダム生成」ではなく**固定値**
- 転生時は基本データに対して**多少のランダム変動**（±5程度）

### ★ 重要な方針転換
戦闘エンジンの詳細設計を進める前に、**ゲーム全体の大枠設計**を先に固める。

## 3.5 命中判定

### 3.5.1 計算式
```javascript
hitRate = move.accuracy + (atk.tec × 0.15) - (def.spd × 0.08)
hitRate = clamp(hitRate, 30, 98)

if (random(100) > hitRate):
    // 回避！ ダメージなし、モメンタム反転、専用演出
```

### 3.5.2 設計意図
- **大技の唯一のリスク**。SPシステムがないため、命中率だけが大技の抑制機構
- TEC型は命中補正が高く、大技でも安定して当てられる
- SPD型は回避率が高く、相手の大技を避けやすい
- 回避成功時はモメンタムが大きく反転

### 3.5.3 tier別命中率の目安

| tier | accuracy目安 | TEC100 vs SPD100での実効命中率 |
|------|------------|---------------------------|
| tier1（小技） | 95-98 | 約97-105→98cap |
| tier2（中技） | 85-92 | 約92-99→98cap |
| tier3（大技） | 75-85 | 約82-92 |
| tier4（フィニッシャー） | 70-80 | 約77-87 |

### 3.5.4 回避時の処理
- ダメージ: 0
- モメンタム: 攻撃側に-15、防御側に+15
- 演出: 専用実況テンプレート
- 大技回避はMQスコアにわずかに加点

## 3.6 ダメージ計算式

### 3.6.1 基本計算
```javascript
// 攻撃値——技ごとに「どのパラメータでスケールするか」が異なる
atkVal = move.power
       + (atk.pwr × move.pwrScale)
       + (atk.spd × move.spdScale)
       + (atk.tec × move.tecScale)

// 防御値——STAが防御の主軸、MNTが補助
defVal = (def.sta × 0.08) + (def.mnt × 0.01)

// モメンタム補正
mMod = 1.0 + (momentum_advantage × 0.004)

// ランダム幅
rF = 0.85 + (Math.random() × 0.30)  // 0.85〜1.15

// フェーズ乗数
pMult = phase.dmgMult

// 最終ダメージ
dmg = Math.max(3, Math.round((atkVal - defVal) × mMod × rF × pMult))
```

### 3.6.2 計算例

**中堅同士（能力値75前後）、tier2 strike（power12, pwrScale0.08, spdScale0.02）、Midフェーズ**:
- atkVal = 12 + (75×0.08) + (75×0.02) = 19.5
- defVal = (75×0.08) + (75×0.01) = 6.75
- dmg = 13（HP150に対して約11-12発 → 20ターン前後）

**トップ級PWR100がSTA60の相手にtier3 strike（power18）をClimaxフェーズで決めた場合**:
- atkVal = 28, defVal = 5.4
- raw = 22.6 × 1.35 = 30.5（HP120に対して4発で沈む）

### 3.6.3 カテゴリ別スケール傾向

| カテゴリ | 主スケール | 副スケール | 特徴 |
|---------|----------|----------|------|
| strike | PWR ×0.08 | SPD ×0.02 | 安定ダメージ。最も平均的 |
| throw | PWR ×0.08 | TEC ×0.02 | pinBonus付き。フォール狙い |
| submission | TEC ×0.08 | MNT ×0.02 | subBonus付き。ギブアップ狙い |
| aerial | SPD ×0.08 | PWR ×0.02 | 高威力だがaccuracy低め |
| ground | PWR ×0.05 | TEC ×0.03 | 低威力だが安定 |
| rollup | TEC ×0.08 | SPD ×0.05 | 低ダメージだが即フォール判定 |

## 3.7 カウンター判定

```javascript
counterRate = 5 + (def.tec × 0.05) - (atk.spd × 0.02) + phase.counterBonus
counterRate = clamp(counterRate, 3, 25)

if (Math.random() × 100 < counterRate):
    dmg = Math.round(dmg × 0.5)   // ダメージ半減
    momentum += 20（防御側に）      // モメンタム大きく反転
```

| フェーズ | counterBonus | 実効カウンター率（TEC100 vs SPD100） |
|---------|-------------|-----------------------------------|
| Opening | +0 | 約8% |
| Mid | +3 | 約11% |
| End | +5 | 約13% |
| Climax | +8 | 約16% |

### 3.8.2 フォール / キックアウト判定
```javascript
kickoutRate = (def.mnt / 200) × 0.45
if (isFinisher) kickoutRate *= 0.6
if (kickoutCount >= 2) kickoutRate = 0 // 3回目は確定フォール
```

### 3.8.3 フォールⅡ（HP残りでの押し切り）
```javascript
pinRate = move.pinBonus + (100 - (def.hp / def.maxHp × 100)) × 0.3
pinRate = clamp(pinRate, 5, 60)
kickoutRate_II = (def.mnt / 200) × 0.55 + (def.hp / def.maxHp) × 0.2
```

### 3.8.4 ギブアップ / ロープブレイク判定
```javascript
ropeBreakRate = (def.mnt / 200) × 0.35
if (ropeBreakCount >= 2) ropeBreakRate *= 0.3

// ギブアップⅡ
subRate = move.subBonus + (100 - (def.hp / def.maxHp × 100)) × 0.25 - (def.mnt × 0.08)
subRate = clamp(subRate, 5, 50)
```

### 3.8.5 丸め込み判定
```javascript
rollupRate = 10 + (atk.tec - def.tec) × 0.05 + (100 - (def.hp / def.maxHp × 100)) × 0.15
rollupRate = clamp(rollupRate, 5, 30)
```

### 3.8.6 TKO（レフェリーストップ）
```javascript
if (def.hp / def.maxHp <= 0.15 && consecutiveHitsTaken >= 2):
    tkoRate = 25 + (100 - (def.hp / def.maxHp × 100)) × 0.3 - (def.mnt × 0.10)
    tkoRate = clamp(tkoRate, 5, 50)
```

- 決着方法ボーナス
- HP差（接戦ほど加点）
- 両選手の人気ボーナス

**MQランクと人気変動**:

| MQランク | スコア目安 | 勝者 | 敗者 |
|---------|----------|------|------|
| ★★★★★ 歴史的名勝負 | 90以上 | 人気 大UP | 人気 UP |
| ★★★★ 名勝負 | 70-89 | 人気 UP | 人気 微UP |
| ★★★ 好勝負 | 50-69 | 人気 微UP | 変動なし |
| ★★ 凡戦 | 30-49 | 変動なし | 人気 微DOWN |
| ★ 塗試合 | 29以下 | 人気 微DOWN | 人気 DOWN |

# ■ 第8部：Heat / ライバルシステム

## 8.1 基本構造——二層の熱量システム

| 概念 | 属性 | 一言説明 |
|------|------|---------|
| **ライバル度** | 個人間（A vs B） | 選手同士の因縁の深さ。蓄積型・消費リソース |
| **Heat** | 団体全体 | 団体の「今の勢い」。常時表示の温度計 |

## 8.2 ライバル度（個人間の因縁）

### ライバルランク（4段階）

| ランク | 意味 | 条件（目安） |
|-------|------|------------|
| NONE | 特に関係なし | 初対面 |
| KNOWN | 顔見知り | 対戦したことがある |
| RIVAL | ライバル関係 | 繰り返し好勝負 |
| FEUD | 抗争中 | 因縁が深まり、決着を待つ段階 |

### ライバル度の上昇条件
- 同じ相手との接戦（MQ★★★以上）
- タイトルの奪い合い
- 僅差の勝敗
- 一方的な連勝（「リベンジ期待」）
- ライバル体質特性持ち → 上昇速度UP

### 決着戦（ライバル度の消費）
- 発動条件: RIVALランク以上
- 効果: 決着戦後、ライバル度消費→両者のPop大UP
- 消費後: ランクがKNOWNまでリセット

## 8.3 Heat（団体の勢い）

### Heatランク（5段階）

| ランク | 意味 |
|-------|------|
| COLD | 団体に勢いがない |
| NEUTRAL | 平常運転 |
| WARM | 注目度上昇中 |
| HOT | 盛り上がっている。集客ボーナス |
| HEAT | 最高潮。全ボーナス最大 |

### Heatの効果
- 興行の集客力ボーナス
- MQボーナス
- スポンサー収入に影響
- スカウト候補の質に影響

### Heatの自然減衰
毎週自然に減衰。「勢いを維持するためには常に熱いカードを組み続ける必要がある」

### 9.2.1 潜在値公式の変更経緯（v1.0→v1.1）

v1.0では `初期値×2（上限200）` の一律倍率だったが、以下の問題があった:
- 強キャラ（初期90）の潜在値180と弱キャラ（初期20）の潜在値40では格差が固定化
- 弱キャラを育てても実用圏に届かず、育成の意味が薄い

v1.1の案A公式は**弱者ほど高倍率・強者ほど天井に近づく**段階的カーブ:

| 初期値帯 | 潜在値 | 実質倍率 | 設計意図 |
|---------|--------|---------|---------|
| 90+ | 177-185 | ×1.9-2.0 | 天井185で絶対的支配を防止 |
| 60-70 | 138-151 | ×2.1-2.2 | 中堅に十分な成長余地 |
| 20-40 | 86-112 | ×2.8-4.3 | 弱キャラでも育成で実用圏到達可 |
