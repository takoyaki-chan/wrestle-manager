## 1. 経路一本化 — 方向①+profile方式(survey選択肢5)⭐

### 1.1 構造

`Engine.mq.finalize(state, matchResult, context, profile)` を純粋関数として新設する。

- **入力**: シミュレーション済みのエンジン素点(再シミュレーションしない)+興行文脈(因縁/タイトル/観客・会場/バフ/ラストラン/trust/鮮度)+profile名
- **出力**: 最終MQ+寄与内訳メタデータ(mqInventory相当を標準装備)
- **呼び出し元**: `App._finalizeShowImpl`(UI)と `Engine.executeShow`(headless)が**同じ関数**を呼ぶ。app.js 側の独立加算(6143-6146, 6413-6432)は全廃

### 1.2 profile定義

| profile | 適用要素 | 使用経路 |
|---|---|---|
| `normal-single` | 因縁/タイトル/観客・会場/マイルストーン2種/ラストラン/trust/鮮度 | プレイヤー通常興行・headless通常興行(シングル) |
| `normal-tag` | 観客・会場/ラストラン(+将来タッグ因縁を入れる余地) | 同(タッグ) |
| `ppv` | 因縁のみ(現状維持) | PPV/天頂戦 |
| `raw` | 補正なし(素点=最終) | ジュニア/春タッグ/秋勝ち残り/B3等イベント戦 |
| `ai-show` | 因縁のみ(現状維持) | AI通常興行 |

特殊興行に通常会場補正を持ち込まない(大会仕様変更はしない)。**経路は一本、仕様差はprofileで明示**が原則。

### 1.3 一本化に伴う個別決定

| 論点 | 決定案 |

| 鮮度(初顔+2/マンネリ-1〜-5) | ✅ **決定: 集客専用へ移す**(2026-07-24 Keisuke決裁。フェーブル推奨の「MQに残す」を退けた)。MQ加算は全経路から除去(UI経路の加算も廃止)。既存の鮮度ラベル計算(Engine側matchupLog)は維持し、動員計算への係数適用へ転用する。数値設計はP3。**不変条件: 同カード連発への抑止力(マンネリカードの実質ペナルティ)が動員側で維持されること** |

### 2.3 名勝負の相対判定

- **機械系の閾値(trust/人気/成長/関係値の30〜80帯)は絶対値のまま維持**。これらは「良い試合だったか」の判定であり、歴史的名勝負とは別の概念。全面相対化は下流破壊が大きすぎる(棚卸し§6)

## 3. 外部ボーナス総再設計 — MQの三層構造 ✅ 方向決定(2026-07-24 Keisuke)

v0.3の§3(観客帯の張り替えのみ)を全面改稿。**MQに加算される全要素を洗い出し、「その点数はリングの中で実際に起きたことか?」の一点で再検討した**。結論として、MQを次の三層に組み直す。

| 層 | 中身 | 何が決めるか |
|---|---|---|
| 土台 | OVシーリング | 選手の実力(重力) |
| 中身 | ドラマ回復+**超過レイヤー(§3.7新設)** | その夜リングで起きたこと(天井の蓋を開ける唯一の鍵) |
| 空気 | **観客帯×試合注目度(§3.2)** | 会場の熱と、観客がその試合をどれだけ観たかったか |

固定加算(御守り型)は全廃し、各要素は「リング内化(シミュレーションへの入力になり、結果として素点が動く)」か「会場の空気(稀にしか動かない外部)」のどちらかへ振り分ける。

### 3.1 全要素の判定表

| 要素 | 現行 | 判定 | 行き先 |
|---|---|---|---|
| 因縁 +1〜+5 | 固定加算 | ❌ | リング内化(§3.3)+注目度(§3.2) |
| タイトル +5 | 固定加算 | ❌ | リング内化(§3.4)+注目度(§3.2) |
| 観客/会場 -3〜+6 | ほぼ定数+4の下駄 | ❌ | 会場の熱×注目度へ再設計(§3.2) |
| trust -1.53×人 | 事後減算 | △機構が嘘 | コンディション化(§3.5) |
| マイルストーン/次戦バフ +3 | 固定加算 | ❌ | コンディション化(§3.6) |
| ラストラン +2/+5 | 固定加算 | ○例外許容 | 外部のまま維持(稀・物語的裏付け最強) |
| 鮮度 | (MQ除去済み) | 決裁済み | 集客専用へ(P3) |
| タッグ固有ボーナス群 | 内容測定値 | ○合格 | 維持(係数はスケール較正時に見直し) |
| 特性2種 | 確率的 | ○合格 | 触らない |

### 3.2 観客補正 = 会場の熱 × 試合注目度 ✅ 決定(2026-07-24)

**興行一律の加算をやめ、試合ごとに配分する。** カード編成の妙(誰をメインに置くか)がMQに正しく響く。

```
matchCrowdBonus = venueHeat(満員率) × engagement(その試合の注目度)
```

- **venueHeat**(🔧仮値。最終閾値は満員率の実分布を計測し「超満員が興行の10%以下」になるよう置く):
  超満員(98%+) +4 / 満員(90〜98) +2 / 普通(65〜90) **0** / まばら(45〜65) -2 / 閑古鳥(45%未満) -4
- **engagement**(0.4〜1.25 🔧): 参加選手の人気(主成分)+因縁あり+タイトル戦+メイン枠 から算出。人気はここで初めてMQに(正直な形で)触れる——「スターの試合は満員の熱を最も受け取る」
- 負側も掛け算が効く: 閑古鳥の中のメインイベントが最も冷える(-4×1.25)。前座の新人戦は淡々と(-4×0.4)。**大観衆の前で戦わせてもらえる格、の残酷さが出る**
- 会場格ボーナス(0〜+3)は廃止し、期待値(採点基準)側へ移管——ドームは点が上がる場所ではなく、求められる水準が上がる場所(※v0.5で「熱の器」§3.2bが加わったため、正確には「無条件では上がらないが、埋め切れば他より高く跳ねる場所」)
- **実測知見(2026-07-24 P3c計測で確定)**: 満員率は使えない。興行の92.9%が満員率95%以上・中央値100%(完売)で、占有率ベースの帯はどう切っても定数化する。**venueHeatの入力は「需要/キャパ比(fill pressure)」に変更**——完売でも「定員ぴったり」と「キャパ1.5倍の需要で瞬殺」は熱が違う。需要分布の実測をP3c実装に含め、閾値は「最上位帯が興行の10〜15%以下」になるよう置く

### 3.2b 会場規模=熱の器+ドームメイン大一番+メイン気迫 ✅ 決定(2026-07-24 Keisuke起案)

- **会場規模は観客熱の振れ幅(器)を決める** 🔧: 超満員時の熱上限を 公民館〜小ホール+2 / 市民会館〜中ホール+3 / 大ホール+4 / アリーナ・大会場+5 / **ドーム+6〜7(別格)**。負側も器に比例(空のドームは最も深く冷える)。会場ボーナスの単純復活ではない——**埋め切ったときだけ**他では届かない熱が出る。会場選択(身の丈か挑戦か)が観客熱に直結する
- **ドーム興行のメインイベントは大一番(ビッグマッチ)ルールでシミュレーション**: 試合が長くドラマの発生余地が大きい=超過レイヤー圏内に届きやすい。「ドームのメインから歴史的名勝負が生まれる」を式で保証ではなく可能にする
- **メイン枠**: engagement係数+0.1〜0.15(v0.4から継続)に加え、**気迫=実効OV+1** 🔧(固定MQ加算ではなく選手の出来として)。「名勝負はメインから生まれる」統計が薄く自然に積み上がる

### 3.3 因縁のリング内化

固定+1〜+5を廃止し、2チャネルへ:

1. **リング内**: 因縁段階(45/55/65/80)がドラマ発生率を押し上げる——カウンター率+2/+3/+4/+5pt、フォール/ギブアップ脱出率+0.05/+0.08/+0.11/+0.15 🔧(名勝負製造機と同じ機構・同じ効かせ方。重複時は加算だが上限は特性と共通のキャップに従う)。**因縁戦は「+3が隠れて乗る」のではなく実際に激しい試合になり、観戦モードに映る**
2. **注目度**: §3.2のengagementに因縁が寄与(観客は因縁に沸く。ただし客がいない会場では沸きようがない——掛け算なので自然にそうなる)

解決済み(好敵手/宿怨)+2も同様に、小さめのリング内効果+注目度へ。分散が生まれ、宿怨戦が期待外れに終わる夜も出る——それがドラマの真実であり、爆発した夜が本物になる。

### 3.4 タイトルのリング内化

固定+5を廃止し: **王座戦は簡単に終わらない**——フォール/ギブアップ脱出率+0.10 🔧(挑戦者・王者とも)。式典としての格は engagement +0.15〜0.2 🔧 へ。

### 3.5 trustのコンディション化

事後減算-1.53×人を廃止し、**trust<35の選手はその試合のコンディションが落ちる**(実効OV -3 🔧)→シーリングが自然に下がる。心が離れたエースの塩試合が、数字の操作ではなく本人の出来として現れる。

### 3.6 バフのコンディション化

- 全試合MQバフ(+3): その週の全選手のコンディション上昇(実効OV +2 🔧)へ変換
- 次戦MQバフ(+3): 指定ペアの当該試合のみ同様
- attendanceMultiplier側は現行維持。消費セマンティクス(1回限り)も変えない

### 3.7 超過レイヤー — 天井の蓋を外す ✅ 方向決定(2026-07-24)

**現行式ではどれだけ完璧な試合をしてもOVシーリングを超えられず、奇跡が数学的に起これない。** これはCLAUDE.md「本当に奇跡が起きたとき感動は本物になる」と矛盾し、歴代記録が育成の答え合わせになってしまう。素点式の再設計は次段としたが、**既存の式を一切触らず項を1つ足すだけ**の限定再開を行う。

- **発火条件**: ドラマ減点を完全に取り返した試合(実測0.19%)+まともな決着(決着減点≤1)
- **燃料**: ドラマ回復の上限(キックアウト2回/カウンター3回/攻守逆転3回/ビッグムーブ6回)を超えて発生したイベント。**現在は1点にもならず捨てられている超過分**が、逓減カーブで天井の上へ突き抜ける
- **式(🔧仮)**: `excess = 4×(k-2)⁺ + 1.5×(c-3)⁺ + 1×(l-3)⁺ + 0.3×(b-6)⁺` → `overflow = min(12, round(4×√(excess/4)))`(excess4→+4、9→+6、16→+8)
- タッグも同ルール(タッグ側の回復上限3/4/4/8を基準に)。全profile共通(素点内なので天頂戦・大会でも起こる——決勝の死闘が歴史を作れる)
- **OVRは重力であって運命ではなくなる**。格上は高い所から始められるが、蓋を開けるのは「その夜リングで起きたこと」だけ
- 副作用として: 名勝負製造機(イベント発生率を上げる特性)が名前どおりの存在になる/因縁のリング内化(§3.3)が超過の燃料を作る——「歴史に残る一戦は因縁から生まれる」が式から自然に出る
- **実装済み(2026-07-24 P3a、コミットb186c5c)**: 実測=シングル発生率0.125%(目標帯内)/overflow平均3.75・最大7/平均MQシフト+0.005/通常興行で最大106を観測。タッグは発火0件(ペーシング条件が厳しい。運用を見て将来調整余地)

### 3.7b OV100超の減衰シーリング ✅ 決定(2026-07-24 Keisuke起案)

現行シーリングはavgOV100で100に頭打ちし、能力値100超が完全に無駄になる。第4セグメントを追加:

```
avgOV > 100: ceiling = 100 + 0.25 × (avgOV − 100)   🔧
```

- 傾き0.25=通常帯(0.85)の3割以下。「かなり減衰するがちゃんと反映」。OV110ペアで+2.5、OV120で+5、実測最大級(128)でも+7
- **OV100以下の試合は1点も変わらない**(既存セグメント不変・追加のみ。超過レイヤーと同じ流儀)
- 潜在値改定(パワー特化170-188等)と整合——規格外の素質がキャリア終盤に規格外の土台として実る。大物ルーキー一面記事(§5)にも実体が伴う
- 記録バランス: ステータス極限で買えるのは最大+5〜7、「夜」の要素(超過+12/観客+8)は最大+20。**土台は買えるが歴史を作るのは夜**、の線は維持。理論上限は約130
- タッグエンジンのシーリングも同式(共通セグメント関数なら自動)

### 3.8 平均低下の受け入れと物差し再較正 ✅ 決定(2026-07-24 A案)

観客下駄の撤去で通常興行平均は約-4(58.3→約54)。**埋め戻さない**(B案=素点カーブへの+4埋め戻しは、下駄の埋め直しでありPPV・大会まで一律持ち上げるため却下)。副産物として「週次興行<特別興行」の序列が正しく開く(現状は下駄でPPV平均68に不当接近している)。

物差しの連動:
1. **表示・演出系(必ず動かす)**: `SHOW_RATING_CONFIG.expectedMQTotal`(220)/`EXPECTED_MQ_BY_VENUE`/新聞寸評5段階/★帯 → 新分布実測に合わせ-4相当シフト
2. **経済・成長系(計測してから決める)**: trust好試合70/人気30/50/70/成長65/80/メディア45/60 → 閾値越え率の変化を実測し、**プレイヤー経済(trust週次収支・人気成長率・ブレイクスルー率)が現行±10%に収まるものは据え置き、外れるものだけ調整**
3. **記録系**: 歴代記録スタート値はP3着地後の分布で最終決定(軌跡計測スクリプトを回し直す)

## 5. 大ニュース新聞システム(週頭通知+一面)

基盤調査(2026-07-24)の結論: **一面選出の仕組みは既にある**。`Engine.newspaper.PRIORITY`(management.js:25981〜)の priority ソートで `topStory` が決まるため、大ニュースは既存機構への追加で実現できる。新設が必要なのは「週頭通知の器」と「記事タイプ3種」のみ。

### 5.1 大ニュースの定義と対象 ✅ 決定(2026-07-24 Keisuke選定)

**Tier S(大ニュース=一面ジャック+週頭通知)は新設4種のみ。既存記事からの昇格はなし**(王座交代・派閥・破産系は見送り。運用後に頻度の体感を見て再検討可)。

| トリガー | 種別 | 頻度想定 |
|---|---|---|
| 歴代最高MQ更新(§2.2) | 新設 | 数シーズンに1回 |
| 大物ルーキーデビュー(trainCap-OVR 125+) | 新設(ロードマップ起案済み) | 上位2%≒数シーズンに1回 |
| 期待のライバル関係(同年代117+が2人、初めて揃った年) | 新設(同上) | 稀 |
| **トップ団体王者の重傷**(業界ランキング1位・2位の団体の王者が重傷以上の怪我) | **新設(2026-07-24 Keisuke追加起案)。記事タイプ自体も新規** | 稀 |

**頻度の設計原則: 大ニュースは年に数回まで**。毎週鳴るピロリんは事件ではなく騒音になる。

### 5.2 大ニュース判定の仕組み ⭐

「大ニュース」を priority の付け替えで作らない。**`BIG_NEWS_TYPES` 集合を新設**し、週次新聞生成後に `topStory.type ∈ BIG_NEWS_TYPES` なら `weeklyNewspaper.isBigNews = true` を立てる。

- 新設3種(記録更新/大物ルーキー/ライバル揃い踏み)は priority 300超(leagueElevation より上)で一面を保証しつつ、集合にも登録
- 既存記事の昇格(王座交代180等)は **priorityを動かさず集合に足すだけ**。「一面に載る条件」と「週頭に鳴らす条件」を分離することで、既存の紙面バランス(王座交代130帯・興行120帯の設計)を壊さない
- 記事化ルートは既存の `Engine.industryNews.push` → `NEWS_HEADLINE_TEMPLATES` パターンに乗せる

### 5.3 週頭通知の器(要デザイン・コンセプト案)

発火点: 週送り後の `popupActions` チェーン(app.js:9362〜)に追加。`isBigNews` かつ未通知の週のみ。

- **SE**: 既存 `notify`(E6→F6の2音、まさにピロリん)をベースに、大ニュース専用 `bignews` SE を新規合成(notify+ベル系スパークル)。本作のSEは全てWeb Audio合成が流儀なので素材ファイル不要
- **ポップアップ**: 軽量モーダル1枚 — 新聞アイコンがドロップイン+見出し1行チラ見せ+「紙面を読む」(→新聞1面へ遷移)/「あとで」(→ナビの📰ボタンに未読バッジ点灯、閲覧で消灯)
- 新聞1面を開いたときの `paper`+`reveal` SEは既存流儀をそのまま使う
- 既存スナップショット通知(ログ行止まり・8%抽選)とは別経路。大ニュースは確実に届ける(snapshot-notification設計原則3「緊急は見逃さない」と同じ思想)

### 5.4 新設3記事の発火設計

| type | 発火タイミング | 判定材料(既存流用) |
