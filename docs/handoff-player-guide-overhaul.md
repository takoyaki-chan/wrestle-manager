# プレイヤーガイド本格化 引き継ぎ書

**作成日**: 2026年4月13日
**対象ブランチ**: 未定（`feature/player-guide-overhaul` を推奨）
**想定実装環境**: Claude Code デスクトップ
**優先度**: 中〜高（DLサイトのレビューで明確に指摘された課題）

---

## 1. 背景と問題提起

### 1.1 きっかけ

DLサイトに投稿された購入者レビュー（2026年4月3日）で、以下の指摘を受けた:

> マイナス点としては、マスクデータなのか明示されているか不明なデータが重要なデータとして扱われている点がある。しっかり遊ぼうとするとこれはどこに書いてあるの?となる場面も多そう。

このレビュアーは長文かつ詳細なフィードバックを残しており、ゲームの構造をかなり理解した上での指摘である。**「数字が見えないこと」自体が問題なのではなく、「重要な隠しメカニクスがどこにも説明されていない」ことが問題**と読み取れる。

### 1.2 現状の情報の散在

プレイヤー向けドキュメントは現在3箇所に分散している:

| ドキュメント | 種類 | trust説明 | 関係性 | 経営 | コーチ |
|---|---|---|---|---|---|
| `ガイド-はじめの一歩.html` | チュートリアル | △ 簡素 | ❌ | △ | △ |
| `ガイド-パラメータ解説.html` | パラメータ表 | ❌ | ❌ | ❌ | △ |
| `specs/*.md` (27本) | 開発者向け仕様 | ✅ 詳細 | ✅ | ✅ | ✅ |

つまり、**プレイヤーが必要な情報は仕様書に全部書いてあるが、プレイヤー側からはアクセスできない**状態。

### 1.3 設計思想との両立

`CLAUDE.md` の数値哲学:

> 数字はドラマの裏で動くもの。表に出すぎてスプレッドシート最適化ゲームにしない

この方針は維持する。**ガイドでは具体的な数値や数式は出さず**、「こういう傾向がある」「こういう要因で動く」というレベルで言語化する。プレイヤーがメタ計算でゲームを攻略するのではなく、**直感的な判断材料を持てる**状態を目指す。

## 2. ゴール

### 2.1 達成したいこと

1. **「これはどこに書いてあるの?」をなくす** — プレイヤーが疑問を持ったとき、必ず1箇所のガイドで答えが見つかる状態にする
2. **隠しメカニクスを「存在を明示しつつ、数値は伏せる」** — trust、関係性、wear などが「裏で動いている」ことだけは伝える
3. **既存3ドキュメントの統廃合** — 「はじめの一歩」（チュートリアル）と「公式ガイド」（リファレンス）の役割を明確に分ける
4. **設計思想の保護** — スプレッドシートゲーム化させない粒度を守る

### 2.2 達成しないこと（明示的なスコープ外）

- 数式や閾値の公開
- キャラクターの個別データ（パラメータ値、ポテンシャル値など）の表示
- ガイドからゲーム本体への動的リンク（静的ドキュメントとして完結させる）
- 多言語対応

## 4. ガイドの新構成案

### 4.1 ドキュメント体系（再編後）

```
┌─────────────────────────────────────────────┐
│  ガイド-はじめの一歩.html                     │
│  → 初プレイ向けチュートリアル（既存を維持）    │
└─────────────────────────────────────────────┘
                    ↓ 卒業
┌─────────────────────────────────────────────┐
│  ガイド-公式リファレンス.html （新規）         │
│  → 全システムの公式リファレンス               │
│  → パラメータ解説の発展形                    │
│  → trust・関係性・経営など隠しメカも網羅       │
└─────────────────────────────────────────────┘
```

旧 `ガイド-パラメータ解説.html` は新ガイドに統合されて廃止。

### 4.2 公式リファレンスの章構成案

#### 第1章 — 選手のステータス
- 5つの基本ステータス（PW / SP / TE / ST / MN）の意味と使われ方
- AC（精度）の位置づけ ※ 既存のパラメータ解説の内容
- OVR と伸びしろ
- スタイル（Striker / Grappler / Submission / Allround / Powerhouse / Highflyer）
- 年齢と成長カーブ

#### 第2章 — コンディション
- 体調（fatigue）— なぜ60を切ると休養に入るのか
- wear（摩耗）と durability（耐久性）
- 怪我のメカニズム
- モチベーション
- ※ いずれも具体的な数値ではなく「上下する要因」を列挙する形

#### 第3章 — 試合と試合の質（MQ）
- MQ が何で決まるか
- 「ドラマのある試合」とは何か
- 因縁・タイトル戦・対抗戦による補正
- ベテランボーナス
- 観客動員と MQ の関係

#### 第4章 — 信頼度（trust）と選手の心 ★最重要章
- **trust とは何か**: 隠し数値であること、見えない理由（設計思想として）
- **trust が上がる要因**: 出場、メイン抜擢、因縁カード、好試合
- **trust が下がる要因**: 出場機会の減少、長期間の冷遇、給与カット、希望と異なる役割
- **trust の段階的な傾向**:
  - 高い（70+）: 維持にコストがかかる「絶大な信頼」
  - 中（40-70）: 通常範囲、安定運営の目標
  - 低い（40未満）: 危険信号、回復に時間がかかる
- **mental パラメータの影響**: 精神力が高い選手は trust 変動が穏やか
- **ケアアクションの使い分け**: ストック、声かけ、各種ケアの効果範囲
- **trust 崩壊の前兆**: セリフ・表情・行動でどう現れるか
- **やってはいけないこと**: 連続不出場、長期メイン外し、給与一方的カット

⚠️ この章は **数式を一切出さない** こと。「○○すると上がりやすい」「××は危険」という定性的な言語で書く。

#### 第5章 — キャラクター相関
- 関係性の種類: trust, rival_friend, destined_rival, intrigued, dislike, etc.
- 関係性が生まれる条件
- 試合への影響: 因縁試合の補正、ストーリー上の重要性
- 相関図の見方

#### 第6章 — 団体経営の数字
- 資金の流れ: 興行収入、選手給与、コーチ費用、施設費
- 人気（orgPop）の上下要因
- 倒産条件と4週連続黒字目標
- 補助金モード

#### 第7章 — コーチ
- コーチの役割: スタイル一致、指導力、人柄
- いつ雇うべきか
- 担当選手の選び方
- 既存コーチの個別解説（簡易プロフィール）

#### 第8章 — システム別早見表
- ドラフト（既存仕様の要点）
- 引き抜き
- タイトル設立条件
- 対抗戦
- PPV
- 施設投資

#### 付録 — よくある質問
- 「選手を出場させているのに trust が下がるのはなぜ?」
- 「同じ試合を組んでいるのに MQ が安定しないのはなぜ?」
- 「お金が足りない、何を削るべき?」
- 「誰をエースにすべき?」
- 「コーチは何人雇うのが正解?」

## 5. 実装方針

### 5.1 ファイル形式

- **HTML 単体ファイル** で実装（既存ガイドと統一）
- CSS は既存ガイドのデザインを踏襲（newspaper 風 or 既存 `wrestle-manager-design-system.html` のトーン）
- フォントは Noto Sans JP / Bebas Neue / Oswald のみ使用
- 章立てナビゲーション（目次から各章へジャンプ）を実装
- スマホ・タブレットでも読めるレスポンシブ対応

### 5.2 文体ルール

- **数値は具体的に書かない**: 「trust 70以上」ではなく「高い信頼を得た選手」
- **断定を避ける**: 「必ず○○する」ではなく「○○する傾向がある」
- **理由を添える**: メカニクスの説明には設計意図を一文添える
- **キャラクターのセリフを引用**: できれば各章で関連するキャラのセリフを1つ引用して、ドラマ性とリンクさせる

### 5.3 仕様書の参照ルール

各章の最後に、開発者向けの参照仕様書をコメントとして残す（HTMLコメント `<!-- -->`）。これは将来のメンテナンス時に「この章はどの仕様書を翻訳したものか」を追えるようにするため。

例:
```html
<!-- このセクションは specs/trust-system-spec-v2.1.md §1.1〜§3.2 を元に翻訳。
     数式・閾値は意図的に隠してある。仕様変更時はこのコメントを参照。 -->
```

## 6. 進め方の選択肢

### 案A: 段階的（推奨）

1. **第0回**: 構成と粒度の方針を最終確定する（このドキュメントのレビュー）
2. **第1回**: 第4章「信頼度」だけ書く（最重要かつ難易度の指標になる）
3. **第2回**: 第4章のレビューを受けて文体・粒度を調整
4. **第3回以降**: 第1〜3章、第5〜8章を順次
5. **最終回**: 既存ガイドとの統廃合、リンクの整理、READMEの更新

**メリット**: 第4章で文体が固まれば、以降の章はパターン化できる。失敗時の手戻りが最小。

**デメリット**: 完成までの総ターン数が多い（5〜7ターン想定）。

### 案B: 一気に書き上げ

1 ターンで全章のドラフトを生成し、後から修正する。

**メリット**: 早い。
**デメリット**: 文体と粒度が章ごとにブレる可能性が高い。trust 章の品質が他章に引きずられる。

### 案C: 章単位の優先度実装

最重要の trust + 関係性の2章だけまず仕上げ、レビュアーの主要不満を解消。残りの章は後日。

**メリット**: 最小工数で最大効果。
**デメリット**: ガイドが「中途半端な状態」で公開される時期が発生。

→ **推奨は案A**。失敗リスクが低く、各回で見える進捗がある。

## 10. 一言メモ

レビュアーのコメントは長文だが、本質的な不満は2点しかない:

1. **データが消える不安**（→ セーブ警告強化＋README追記で対処済み）
2. **隠しメカニクスがどこにも説明されていない**（→ 本ガイドで対処）

レビュアーは「理解した上で批判している」プレイヤーであり、彼/彼女が満足するレベルのドキュメントを作れば、他のコアプレイヤーの満足度も大きく上がる。逆に言えば、**ライトユーザーには響かない作業**なので優先度判断は慎重に。ただし「数値が見えないこと自体は欠点ではない」というレビュアーの理解度から、設計思想は伝わっており、あとはそれを補強するドキュメントがあれば良い、という前向きな解釈ができる。
