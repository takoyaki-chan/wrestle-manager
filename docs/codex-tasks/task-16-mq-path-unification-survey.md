## 背景

MQ（試合クオリティ）の確定経路が **2本あり、結果が一致しない**。

| 経路 | いつ通るか |
|---|---|
| `App._finalizeShowImpl`（`src/app.js:6080-6104`） | プレイヤーが画面から興行を見るとき |
| `Engine.executeShow`（`src/management.js:11227`〜） | headless / auto-sim / AI興行 / PPV / 対抗戦 / 天頂戦 |

プレイヤー経路には +12外部キャップ・trustペナルティ・マイルストーン加算・ラストラン加算が**なく**、代わりに各加算段階で100にクランプする。headless 経路はその逆で、上限クランプを持たない。タッグはさらに別で、エンジン内部で素点を100へ丸めた後に headless が会場+6・ラストラン+5 を加えるため最終値が再び100を超える。

CLAUDE.md のアーキテクチャ5原則「UIはGameStateを直接変更しない／エンジン経由でのみ状態を更新する」にも反している。

**MQの再設計に入る前に、この経路を1本化する必要がある。**2本あるままでは「MQのこの数値をどうするか」を決めても、どちらの経路に効くのかが定まらない。

**本タスクは一本化そのものは行わない。**判断材料を揃えるための調査に徹する。

## 調査内容

### A. 完全な差分表

2つの経路が「同じ通常興行」を処理する際の**全ての違い**を、処理順に並べた表として出す。

各項目について:

- 項目名（因縁加算、タイトル加算、観客/会場、鮮度、trust、マイルストーン、ラストラン、キャップ、クランプ など）
- **`Engine.executeShow` での扱い**（適用される/されない、値、適用順、実装箇所 `ファイル:行`）
- **`App._finalizeShowImpl` での扱い**（同上）
- 両者が食い違う場合、**同じ試合でどれだけ値が変わるか**（実測。task-13 の構成を流用してよい）

task-11 のレポートに部分的な記述はあるが、**統合の観点で「何を揃えなければならないか」が一覧になっていない。**それを作るのが本項の目的。

### B. どちらへ寄せると何が壊れるか

一本化の方向は2つある。それぞれについて影響を試算すること。

**方向①: 画面経路を廃し、`Engine.executeShow` に寄せる**

- プレイヤーが見るMQがどう変わるか（実測。上がるのか下がるのか、平均何点動くのか）
- 画面経路にしか無い要素（鮮度: 初顔+2 / マンネリ-1〜-5、`src/app.js:6423-6432`）をどう扱うか。エンジン側へ移設する必要があるか
- 上限クランプが消えることで、画面表示に100超のMQが出るようになる。表示側で困る箇所はあるか

**方向②: headless を画面経路に合わせる**

- auto-sim / AI興行 / PPV / 天頂戦 のMQがどう変わるか（実測）
- headless にしか無い要素（+12キャップ、trustペナルティ、マイルストーン加算、ラストラン加算）が消えることの影響
- **これまでの較正・実測値がすべて headless 経路のものである**ため、過去の計測結果との連続性が失われる範囲

**どちらが良いかの推奨は書いてよいが、決定はしないこと。**

### C. 呼び出し元の一覧

`Engine.executeShow` と `App._finalizeShowImpl` を呼んでいる箇所をすべて列挙する（`ファイル:行`）。通常興行・AI興行・PPV・対抗戦・天頂戦・春タッグリーグ・秋の勝ち残り戦・ジュニア大会など、経路ごとにどれが通るかを明示すること。

一本化した場合に**呼び出し側の修正が必要になる箇所**も併せて洗い出す。

### D. 既存セーブとの整合

- 過去の試合結果として記録済みのMQ（`careerRecord` / 年代記 / 実績 / ニュース等）は、どちらの経路で確定した値か
- 一本化により、**同じ試合が違う値になる可能性があるか**。既存セーブの記録済みMQと新しい計算の間に不整合が生じるか
- 生じる場合、それは実害があるか（過去の記録は記録として残るだけか、再計算される箇所があるか）

### E. タッグの二重クランプ

タッグはエンジン内部で `clamp(round(...), 5, 100)` した後、headless 経路が外部補正を加えて再び100を超える（task-13 実測: 最終23.665%が100超、最大111）。

- この二重処理が**意図的なものか、単に揃っていないだけか**をコードとコミット履歴から判断すること
- 一本化の際にどう扱うべきかの選択肢を挙げること
