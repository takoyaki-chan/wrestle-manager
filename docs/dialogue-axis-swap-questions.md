## Q1. 【最優先】疎なアーキタイプ束で、口調と性格のどちらを優先するか

これが S5 に進む前に決めたい唯一の設計判断です。

セリフ表は全部が 7×7 埋まっているわけではなく、アーキタイプ側が疎なものが多くあります。
例えば `FACTION_F01_LEADER_LINES.ojousama` には `emotional` の行しか用意されていません。
そこへ「お嬢様 × 強気」のキャラが来たとき、どれを出すか。

| 案 | 出す行 | 結果 |
|---|---|---|
| **A（採用中）** | 同じ口調の `normal` → 無ければ標準口調の同性格 | お嬢様の言葉遣いは保つが、強気らしさは消える |
| B（入れ替え前） | 同性格の標準口調 | 強気らしさは残るが、お嬢様が「〜だぜ」寄りの行を喋る |

S1〜S4 では **A** を採用しました。この作業の目的が「お嬢様もヤンキーも同じ行を引いて
口調が揃ってしまう」の解消なので、口調を優先するのが筋だと判断しています。

実際に変わったのは全 2,112 組み合わせ中 **12件**（すべて `FACTION_F05_DISSIDENT_LINES`）:

```
[お嬢様 × 強気]  前: あの人のやり方、もう付き合いきれねえわ。
                 後: 率直に申し上げます。このままでは、わたくしたちは朽ちますわ。

[丁寧 × 寡黙]    前: ……もう、ついていけない。
                 後: 失礼ながら、意見を申し上げさせてください。

[ヤンキー × 感情的] 前: あたし、あの人のこと信じてたのに……ひどい！
                    後: 黙ってたけど、もう限界だっつーの。
```

**A でよければ S5 も同じ方針で進めます。** ただし S5 は対象が 211ヶ所・約9,300本なので、
影響を受ける組み合わせは 12件では済みません。ここで方針が変わると S1〜S4 もやり直しです。

なお、どちらの案も「両方を満たす行を書き足す」ことで解消できます（お嬢様×強気の行を
実際に用意すれば、フォールバックは発生しない）。今回の入れ替えは、その不足が
**Excel 上で見えるようになる**ための下準備でもあります。

## Q2. S5 に進んでよいか（分割できません）

残りは 211ヶ所 / 65テーブル / 約9,300本。**これは1段でしか動かせません。**

理由は `getDialoguePool`（`src/data.js:14879`）です。`data.js` / `management.js` /
`relationships.js` / `ui-common.js` / `app.js` の23ヶ所以上がこの1関数を通っており、
反転した瞬間に serve している全テーブルが同時に切り替わります。
S1〜S4 を系統ごとに切れたのは、それぞれ専用の読み手を持っていたからです。

「各段階で Excel を確認」という当初の進め方は、ここでは使えません。代わりに
S1〜S4 で使った全数 probe（全テーブル × 全 8×8 組み合わせで読み手の出力を突き合わせ、
差分を1件ずつ目視）で担保する形になります。

これで進めてよいか、それとも S5 の前に一度実機で S1〜S4 を触ってからにするか。

## Q4. `factions.js` の COMMON 系が旧語彙のまま

`getCommon1Line` / `getCommon5Line` / `getF02Line`（`factions.js:3189 / 3354 / 5528`）は
`fiery` / `grudging` / `flippant` / `airy` / `introverted` / `carefree` という
**現行の性格7種にもアーキタイプ7種にも属さない独自語彙**で分岐しています。

`_personalityLineKey()`（`factions.js:3152`）が
`bold→fiery` / `emotional→grudging` / `shy→flippant` のように橋渡ししていますが、
この体系のせいで `COMMON1_LINES` / `COMMON5_LINES` は Excel でも軸が解決できません。

今回の入れ替えの対象外にしてあります。現行体系に寄せるかどうかは別途判断が要ります。

## Q6. Excel の未反映16件をどうするか

`セリフ編集/ナレーション・記事/…黒田記者の目.xlsx` に未反映の改訂が16件残っています
（すべて `KURODA_HEADLINES`）。今回触ったテーブルとは重ならないので、**16件とも今も反映可能**です
（`apply --dry-run` で「16 resolved, 0 skipped」を維持しています）。

書き出し（`1_エクセルに書き出し.bat`）は破壊的なので、この16件を反映するまで一切実行していません。
順序としては **`3_ゲームに反映.bat` → `1_エクセルに書き出し.bat`** です。逆にすると16件が消えます。

S5 まで終わってから一度に書き出すか、S1〜S4 の時点で一度書き出して Excel を見るか。
