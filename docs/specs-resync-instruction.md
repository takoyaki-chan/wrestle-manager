# specs/ 再同期 作業指示書

## 目的

直近1ヶ月、仕様変更の指示書が `docs/` 側に書かれて完了後アーカイブされる運用になっていた結果、`specs/` が現在の実装・仕様と乖離している可能性が高い。
この指示書では、まず**ズレを洗い出し**、Keisukeさんの承認を得てから、**specs/ を現在の真実に再同期**する。

## 重要な前提

- **勝手に specs/ を書き換えない。** 各フェーズごとに必ず報告して承認を待つ。
- この作業は「コードを変更する」作業ではない。specs/ の記述を現状に合わせるだけ。
- 不明な点があれば必ず質問する。推測で specs/ を書き換えない。

---

## フェーズ1: 現状把握（まず読むだけ）

以下を読み、全体像を把握する。

1. `specs/` 配下の全ファイルを列挙し、各ファイルの最終更新日・行数・概要を1行で報告
2. `docs/` の直近1ヶ月に完了した指示書（アーカイブ含む）を列挙
3. `CLAUDE.md` および `game-system-roadmap.md` を読む

**この時点では何も変更しない。** 読み終わったら、以下の形式で報告すること。

```
### specs/ の現状
- specs/mq-system.md (最終更新: 2026-02-xx, 120行) - MQ計算式
- specs/trust-bond.md (最終更新: ..., ...行) - 信頼・絆システム
...

### 直近1ヶ月の docs/ 指示書（アーカイブ含む）
- docs/archive/2026-03-xx-coach-grade-adjustment.md - コーチ能力値再調整
- docs/archive/2026-03-xx-...
...
```

報告後、**次のフェーズに進んでいいか Keisuke さんに確認する。**

---

## フェーズ2: ズレ検出（差分レポート作成）

フェーズ1が承認されたら、以下を実行する。

### 2-1. specs/ vs 指示書の突き合わせ

各 docs/ 指示書について:
- その指示書が扱っているシステム（MQ、信頼、コーチなど）を特定
- 対応する specs/ ファイルを見つける
- 指示書の変更内容が specs/ に反映されているかチェック
- **反映されていない項目をリストアップ**

### 2-2. specs/ vs 実装コードの突き合わせ（可能な範囲で）

各 specs/ ファイルについて:
- そこに書かれた数式・定数・ルールを実装コードから検索
- 実装と specs/ の記述が一致しているかチェック
- **一致していない項目をリストアップ**

### 2-3. 差分レポートの出力

以下の形式で `docs/specs-drift-report.md` として保存する。
**specs/ 本体はまだ書き換えない。**

```markdown
# specs/ 乖離レポート (生成日: 2026-04-05)

## カテゴリA: docs/指示書が specs/ に未反映

### A-1. コーチ能力値の10値化 [指示書: docs/archive/2026-03-xx-coach-ability.md]
- 指示書の内容: 35コーチ、A/B/Cグレード、10能力値
- specs/coach-system.md の現状: 旧グレード定義のまま、能力値の記述なし
- 必要な更新: coach-system.md を全面改訂
- 重要度: 高

### A-2. ...

## カテゴリB: specs/ と実装コードの乖離

### B-1. MQ計算式の係数 [specs/mq-system.md]
- specs/ の記述: 減算係数 0.8
- 実装 (src/systems/mq.ts:42): 減算係数 0.75
- どちらが正しいか不明（要確認）
- 重要度: 中

### B-2. ...

## カテゴリC: 指示書にも specs/ にも明示されていないが実装で動いているもの

### C-1. ...

## サマリー
- カテゴリA（未反映）: X件
- カテゴリB（実装乖離）: Y件
- カテゴリC（未文書化）: Z件
```

レポート保存後、**Keisuke さんに差分レポートをレビューしてもらう。**
勝手に specs/ を更新しない。

---

## フェーズ3: 反映方針の決定（Keisukeさんの仕事）

Keisuke さんが差分レポートを見て、各項目について以下を決定する:

- **更新する**: specs/ を指示書/実装に合わせて書き換え
- **実装を直す**: 実装のほうが間違っている場合（これは別タスク）
- **判断保留**: どちらが正解か不明、後で議論
- **削除する**: その specs/ 項目自体が不要

Claude Code はこの決定を待つ。勝手に進めない。

---

## フェーズ4: specs/ 更新の実行

Keisuke さんから方針が返ってきたら、**1カテゴリずつ** specs/ を更新する。

- 1ファイル更新するごとに diff を報告
- 複数ファイルをまとめて commit しない
- 各更新の末尾に `<!-- 再同期: 2026-04-05, 指示書: docs/archive/xxx.md -->` のコメントを残す（どの指示書由来か追跡可能にする）

---

## フェーズ5: 今後の運用ルール追記

すべての反映が完了したら、`CLAUDE.md` に以下のルールを追記する。

```markdown
## specs/ 更新ルール (2026-04-05 追加)

### docs/ 指示書の完了フロー
1. 指示書に基づいて実装を完了する
2. **実装完了後、specs/ の該当箇所を更新する**
3. specs/ の更新 diff を Keisuke さんに確認してもらう
4. 承認されたら指示書をアーカイブに移す

**specs/ を更新せずに指示書をアーカイブしてはいけない。**

### specs/ の位置づけ
- specs/ = 確定仕様（現在の真実）
- docs/ = 計画・検討・指示書（未来形 or 過去形）
- アーカイブは「完了した指示書」置き場であり、仕様の真実ではない
```

追記後、diff を報告して完了。

## 作業時の注意

- **1フェーズ完了ごとに必ず停止して報告する。**
- 不明点は推測せず質問する。
- specs/ の文章を書き換える際、元の構造・トーンをなるべく保つ。
- 用語は現行の specs/ に合わせる（例: 「MQ」「信頼」「絆」「ライバル関係」）。
- 日本語で記述する。
