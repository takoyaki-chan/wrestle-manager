## 0. 要約(Keisuke 向け)

1. **選手ごとに「何番目の人生か」の番号を持たせる。** 引退した選手のIDが休眠プールへ戻る瞬間を唯一の関所にし、そこで番号を1つ進める。
2. **その関所で、前の人生の「生きた記録」を退避してから消す。** 対象は関係値・因縁・対戦成績・タッグ経験・呼び名・報道済みの印・各種の発火済み記録。新人は白紙で始まる。
3. **殿堂・年代記・王座史・新聞・記録タブには、書くときに人生番号を刻む。** 読むときは「ID+人生番号」で引く。前の人生の顔を押したら、その人生の殿堂詳細を開く(殿堂入りしていなければ押せない)。同じ名前が並ぶところには在籍年(S3〜S9)を添える。襲名の演出はしない。
4. **デビュー済みの選手は休眠プールに入れない。** AI団体が契約満了にしたベテランの若返りを含め、「引退を経ずに別人として作り直される」経路が11か所あり、今の転生の半分(263件中132件)はこれだった。デビュー済みの選手はFAに1季残り、拾われなければ「フリーのまま引退」する(殿堂判定と新聞に載る)。
5. **殿堂入り・戴冠経験・自団体OGの人生は、戻るまでの休みを5季→15季にする。**
6. **供給は減らさない。** 漏れを塞ぐとAI団体のロスターが37→31人に痩せた。一度もデビューしていない子は別人にならないので、適齢期を過ぎたらクールダウンを経ずにその場で若返らせる。この1点で、供給はほぼ元の水準に戻った(§1-2)。
7. **別件の発見: ロード時のセーブ修復が、通常プレイでもシーズン中のロードのたびに引退IDを最大12人まとめて休眠プールへ戻している。** auto-sim はロードしないので、実プレイの転生は計測よりさらに多い。K-4 ではこの経路にも同じ関所と休みの規則を通す。修復の発動条件の見直しは確認事項にする(§9 Q7)。

## 2. 人生の単位の定義(設計 §1)

### 2-1. 定義

- **人生** = あるIDの選手が、初めてどこかの団体(自団体・AI団体)と契約した時点から、引退するまで。
- 一度もデビューしていない見込み選手(休眠プール・FA・スカウト候補にいる子)は、まだ人生が始まっていない。作り直されても同じ子として扱い、番号は進めない。
- 同じIDの人生が時間的に重なることはない(引退から戻るまで最低5季空く)。

### 2-2. データ

| 置き場所 | 名前 | 意味 | 無いとき(fail-open) |
|---|---|---|---|
| 状態 | `lifeSerial` = `{ [id]: n }` | そのIDの「今の人生」の番号 | `{}`。IDが無ければ 1 |
| 選手オブジェクト | `lifeNo` | その選手が属する人生の番号 | `lifeSerial[id] ?? 1` |
| 選手オブジェクト | `debutSeason` | その人生で最初に団体に所属した季 | 推定値 `max(1, 季 − careerSeasons)`(§7) |
| 恒久記録の各項目 | `lifeNo`(対の記録は `lives: {id: n}`) | その記録がどの人生のものか | 旧データ扱い(§4-3 の季による判定) |
| 状態 | `retiredLives` = `{ [id]: {lifeNo, debutSeason, endSeason, lastOrgId, titleReigns, hof} }` | 引退した人生の要約。引退から転生までの間だけ保持(`retiredSeasons` と同じ寿命) | 休みの判定は殿堂・年代記から推定(§5) |

番号は内部の識別子で、画面には出さない(襲名しない)。欠番はあってよい。たとえば、ゲーム開始時に一度も生きずに引退枠へ置かれるID(`initRandomRoster` management.js:10188付近)は、最初の転生で 2 から始まる。

### 2-3. 番号を進める場所(唯一の関所)

`Engine.life.beginNewLife(state, id)` を新設する。引退枠から休眠プールへ移す3経路(A1 18708、A2 498、A3 tools/save-doctor.js:359)は、必ずこれを通す。中身は2つ。

1. `closeLiveRecords(state, id)`: 前の人生の生きた記録を退避・消去する(§3-A)。
2. `lifeSerial[id] = (lifeSerial[id] ?? 1) + 1`。

§6 で B1〜B8 を塞いだ後は、これが「人生の終わった ID が世界へ戻る」唯一の道になる。番号を引退の時点ではなく転生の時点で進めるのは、引退後に書かれる記録(年末の殿堂入り、翌季の引退記事、年代記の登録)を引退した人生の番号で刻むため。

### 2-4. 選手への印付け(後付け処理)

`Engine.life.stamp(state)` を新設する。何度呼んでも同じ結果になり、変化が無ければ同じ state を返す。

- 自団体ロスター・AIロスター・FA・スカウト候補・`retiredFighters` の選手のうち、`lifeNo` が無い選手に `lifeSerial[id] ?? 1` を付ける。
- 団体ロスターにいて `debutSeason` が無い選手に、`state.offSeason ? season+1 : season` を付ける(オフ中のドラフト・獲得は翌季デビュー)。

置き場所は4つ。**季中は tickWeek、オフは advanceWeek が別々に呼ばれるので両方に置く。**

- `tickWeek` の入口(management.js:14282。呼び名の更新 14295 の直前)
- `advanceWeek` の入口(18392)
- `repairOnLoad` の末尾(§7 の移行の後)
- `createInitialState`(全員 `lifeNo=1, debutSeason=1`)

誕生点(`makeAIFighter` の呼び出し元6か所)には手を入れない。見込み選手のオブジェクトは捨てられては作り直されるので、番号はオブジェクトではなく `lifeSerial` から決める必要がある。恒久記録を書く側は、印付けの前でも正しい番号を得られるよう `Engine.life.of(state, fighterOrId)`(= `f.lifeNo ?? lifeSerial[id] ?? 1`)を使う。

### 2-5. 不変条件(validateGameState management.js:27123 に追加)

- I-1: 現役・FA・スカウト候補の全選手で、`Engine.life.of(state, f) === (lifeSerial[f.id] ?? 1)`。
- I-2: 恒久記録で同じ `(id, lifeNo)` の殿堂エントリが2件ない。年代記アーカイブも同様。
- I-3(計測で見る): デビュー済み→休眠プールの移動が0件。転生の初見時点で、§3-A の保存先にそのIDが残っていない。

## 5. 戻ってくるまでの休み(設計 §4)

- 追加する値: `DORMANT_POOL_CFG.retiredCooldownNotable = 15`。通常は `retiredCooldown = 5` のまま。
- **休みを延ばす対象(「注目の人生」)**: その人生で (a) 殿堂入りした、(b) 王座を獲った(団体王座・統一王座・天頂戦優勝)、(c) 自団体に在籍した、のいずれか。
- **判定の材料**: 転生の時点では選手オブジェクトはもう無い。そこで引退時に `retiredLives[id]` を書く。書く場所は、引退者全員が必ず通る殿堂判定の3か所。
  1. 自団体: 年末の `finalizeRetireeBuffer` / `applyHallOfFame`(22369/22391)。季中の怪我・ラストラン・モチベ喪失による引退も `retiredFighters` 経由でここに来る。

  3. §6 で新設するFA引退。

  `retiredLives` が無いとき(旧データ・欠落IDの救済)は、殿堂と年代記アーカイブで (a)(c) だけを判定する。
- **3つの転生経路すべてに同じ判定を通す**: `Engine.life.returnCooldown(state, id)`。A2・A3 の非常補充(クールダウン無視)でも、**注目の人生は対象から外す**。通常の人生を先に使い、足りなくても注目の人生は戻さない。

## 6. デビュー済みの選手を休眠プールに入れない(設計 §5。AI契約満了ベテランの若返りを含む)

### 6-1. 規則

- **R1**: 休眠プールに入れてよいのは、今の人生でまだデビューしていない子だけ(`careerStage==='prospect'` で `debutSeason` が無い)。
- **R2**: デビュー済みの選手を手放すとき(放出・契約満了・解雇・押し出し・レンタル帰還)の行き先はFA。FAの上限(`ROSTER_CFG.fa=12`)は見込み選手にだけ掛ける。FAに入った季を `faSince` に記録する。
  - 手放す処理を `Engine.util.releaseToMarket(state, fighter)` 1本にまとめ、§1-1 の B2〜B6(15か所)をこれに置き換える。`redirectToDormantPool` はデビュー済みには使わない。
- **R3「フリーのまま引退」**: オフ第1週に、デビュー済みFAのうち FA入りが今季より前(丸1季どこにも拾われなかった)の選手を引退させる。
  - `ensureRetireEvent(reason: 'freeAgent')` で引退を記録し、`retiredLives` を書き、殿堂判定をする。殿堂は最後に所属した団体の欄に入れる(自団体なら player)。
  - 新聞はAIの引退と同じ格付け記事にする(所属は「前所属」)。
  - 位置は 18667 の「FA 22歳超→引退枠」を置き換える。
  - scout 仕様 §9.3 の「30歳以上のFAは年50%で引退」は、この規則に置き換える。
- **R4**: FAの月次入れ替えで外すのは、見込み選手だけ(14654)。
- **R5**: FA加齢の若返りは、見込み選手だけ(18608。監査②の直接の修正)。
- **R6(供給の補償)**: 休眠プールで21歳を超えた子(全員未デビュー)は、引退枠を経ずにその場で17〜19歳へ戻る(18656)。未デビューの子は別人にならないので、5季休ませる理由がない。これが無いとAI団体が痩せる(§1-2: 37→31)。

### 6-2. 効果(§1-2)

- 引退を経ない作り直しは132→0件。デビュー済み→休眠プールは147→0件。
- 供給はほぼ現状並み(AIロスター 35/33、S/A/B 16/12/9)。補充の年間上限(8)は変えない。
- AIキャリアの約半分を占めていた「放出→消息なし」は、FAでの再契約か「フリーのまま引退」(年3.4人。記事と殿堂判定つき)に変わる。
- 解雇された選手は、遺恨(`grudge`)を持ったまま同じ人物としてFAに残る。元の雇い主への挑戦(firedReturn)は、本来の「同じ人の逆襲」として働く。

### 6-3. 仕様の改定

scout-system-spec §9.3(加齢と引退)、§9.4(FA上限と退避先。「全6箇所」の記述)、§9.2(供給)。`AI_TURNOVER_CFG` の注記「他団体やプレイヤーが拾える」(data.js)は、この修正で事実になる。

## 付録: 計測の方法

- 計測版の作り方: test/auto-sim.js を一時領域に複製した。読み込み時に4点を差し込んでいる(src は無変更)。
  1. 各週の状態を観測するフック
  2. 最終状態の書き出し
  3. 変種の置換: 漏れ修正は management.js の11か所、休み15季は 18682付近の判定、補充上限は data.js
  4. 転生の検出: 選手オブジェクトに印を付ける。状態更新は `{...f}` で複製されるので同じ人生の間は印が残り、テンプレートから作り直された新しい人生には印が無い
- ロード時修復の確認: 最終状態と実セーブ棚6本に `Engine.saveDoctor.repairOnLoad` をメモリ上でかけ、戻ったIDの数と、関係値・対戦成績・殿堂を持つかを数えた(ファイルは書き換えていない)。
- 単一シード(424242)の40季。供給の差は±1〜2程度の揺れを含むので、実装時の合格判定は§5の基準で、採用する構成は100季で確認する。
