## 1. 結論(3分版)

1. **同じ興行前の状態・同じカード・同じ乱数シードから、実プレイ経路とエンジン経路の両方を実ブラウザで走らせ、状態 G の違いを項目ごとに列挙するテストを作った。**
   - 実行は `npm run test:k1:parity`(15本・約1.5〜4分)。
   - 既知の乖離は許容リストに登録してある。一本化で差が消えた項目はリストから外すと「差分ゼロ」に固定され、新しい差が出たら落ちる。
2. **乖離は許容リストに40項目で登録した。**
   - 根本の乖離が33項目(数値に効く20、表示・記録10、一時キー3)。残り7項目は、tickWeek を通った波及と乱数ずれの受け皿。
   - これとは別に、ハーネスの外でコード読解だけで確かめたものが11件ある(§7)。
3. **依頼時点で分かっていた8件は、すべて再現・確認できた**(§5)。
4. **監査 v0.1 に無かった重い発見**
   - 実プレイでは**怪我による引退が起きない**。重傷で消耗も上限を越えた選手が、長期離脱のままロスターに残る。「壮絶な幕切れ」も同じ理由で起きない。
   - 実プレイでは**突然の退団(信頼15未満)が起きない**。表示コードだけが残っていて、発生源が無い。
   - 実プレイでは**派閥抗争ポイントと派閥内ポイントが、試合から入らない**(F09 のスイープボーナスを除く)。
   - 実プレイでは、**タッグの歴代最高評価が別枠で記録されず**(シングルの記録と比べられる)、**記録更新の記事も出ない**。**自団体の王座移動の記事**も消えている。
   - 実プレイの**タッグでは敗者も勝者扱い**になる(勝利ボーナスの人気、連敗リセット)。
   - 結果画面の**「先読み tickWeek」が G を直接書き換えている**。W-1(憎い敵ゾーン)の回数が二重に数えられ、関係性モーダルも重複して積まれる。
   - F07 メイン推薦など派閥系の**信頼・人気の変化が、処理後半の roster 上書きで消えている**(実プレイ側)。
   - プロモ蓄積のリセット差は、この fixture で**週の収入の約3割(553/週)**の差になる。
5. **移す順番の推奨**(§8)
   - ① 副作用と取りこぼしを止める(数値はほぼ不変)。
   - ② 表示・記録だけの差を統一する。
   - ③ 両経路が呼ぶ純関数を切り出す。
   - ④ 数値が動くものを、裁定つきで1件ずつ寄せる。

**ページ側の計測(page-probe.js)で行う差し替えは次の3つだけで、どれもゲームの判定は変えない。**

1. `Math.random` を種付きの擬似乱数に置き換える。表示用の文選びを毎回同じにするため。数値の抽選は `Engine.rng` を使うので影響しない。
2. `Engine.rng.derive / create / _next` を「数えるだけ」の包みで覆う。戻り値は元の関数そのままで、ストリームごとの引き数だけを記録する。
3. 実プレイ経路の実行中だけ、`Engine.tickWeek` と `App.advanceFromWeekSummary` を包む。
   - closeShowResult が tickWeek に渡す状態と、受け取る状態を写し取る。
   - 週送りの直前で止める(次週へは進めない)。

**実行方法**

```
npm run test:k1:parity                          # 許容リスト照合(PASS / FAIL)
node test/k1-parity/run.js --report --verbose   # 全差分を例つきで表示
node test/k1-parity/run.js --scenario injury    # 1本だけ(「消えた既知差分」の判定は省略)
```

- 生データは `test/k1-parity/out/last-run.json` に出る(git 管理外)。
- 同じ入力なら毎回同じ結果になる(2回走らせて出力の一致を確認済み)。

**一本化を進めるときの使い方(差分ゼロへの固定)**

1. 項目を1つ直して差が消えると、テストが「消えた既知差分 K1-xxx」で落ちる。その項目を `allowlist.js` から削除する。以後その場所に差が出ると「未登録の差分」で落ちる。
2. 新しい差が出たら「未登録の差分」で落ちる。原因を調べ、直すか台帳に登録する。
3. B(tickWeek 後)の波及・乱数ずれの受け皿は、上流が消えれば一緒に消えるので「消えた」判定から外してある。

**package.json と .gitignore を変えた理由**

- `package.json`: 実行コマンドを `npm run test:k1:parity` で呼べるようにするため、scripts に1行足した。
  - Playwright を使う長めのテストなので、`npm test`(`test/*-test.js` を全部回す)には入れていない。UI走破(`test:ui:walkthrough`)と同じ扱い。
  - ファイル名も `-test.js` にしていない。
- `.gitignore`: 生データ JSON の出力先 `test/k1-parity/out/` を git 管理外にするため、1行足した。

## 3. 比べ方

### 3.1 入力

- fixture は、headless 進行で seed 42 の2年目14週(S2W14)まで進めた状態。
  - 実UIのタイトル画面「CONTINUE」と同じ経路(`App.titleContinue`)で読み込むので、セーブ移行処理も本番どおり通る。
  - ロスター12名、関係値672キー、派閥1つ。ロード時の移行で団体人気は56。
- シナリオごとに、この基準状態からカードと必要な条件だけを組んだ興行前の状態 G0 を作る。両経路にまったく同じ G0(同じ rngSeed)を渡す。
- 時計は固定する(Playwright の clock)。非同期のポップアップは進めない。

### 3.2 経路

- **エンジン経路**: `Engine.executeShow(G0)` → `Engine.tickWeek(...)`
- **実プレイ経路**: `App.executeShow()` → `App.skipAllMatches()`(または1試合ずつ `App.skipMatch`) → `App._finalizeShowImpl()` → `App.closeShowResult()` の中の `Engine.tickWeek` → 週送りの直前で止める
- 注: auto-sim は executeShow と tickWeek の間で、選択イベントの自動処理と一時キーの掃除(`clearTransients`)をしている。今回はその手当を挟まず、エンジンの関数どうしで比べた。auto-sim 自体の差(関係値の未初期化など)は監査 R1 のとおりで、別の課題として残る。

### 3.3 比べる時点

| 時点 | エンジン経路 | 実プレイ経路 | 見えるもの |
|---|---|---|---|
| **A 興行後** | executeShow の戻り値 | closeShowResult が tickWeek に渡す状態 | 興行後処理の差(本体) |
| **B tickWeek 直後** | tickWeek の戻り値 | closeShowResult の中の tickWeek の戻り値 | A の差が週次処理を通って広がったもの |
| **C 実プレイだけ** | — | tickWeek 直後 → 週送り直前 | closeShowResult の後半だけがやっていること |
| **P 先読み** | — | 結果画面の先読み tickWeek の前後の G | 画面を開いただけで状態が動く箇所 |

あわせて、実プレイの finalize 直後から tickWeek 入力までの差(closeShowResult の前半だけがやっていること)も出す。今回はラストランの後始末だけが該当した。

### 3.4 差の読み方

- **engOnly**: エンジンだけが基準から変えた(実プレイは基準のまま)。**処理の有無**の強い証拠になる。
- **appOnly**: 実プレイだけが基準から変えた。同上。
- **both**: 両方が変えたが値が違う。式・入力・乱数消費のどれかが違う。
- **乱数ストリームの引き数**: derive の引数(=用途)ごとに、両経路で何回引いたかを比べる。
  - 片方しか引かないストリームは「処理の有無」の裏付けになる。
  - 両方が引くのに回数が違うストリームは、それ以降の結果が**乱数消費のずれ**で変わる印になる(§6)。

## 6. 乱数消費のずれ

乱数ストリーム(derive の引数)ごとの引き数を両経路で数えると、差は3種類に分かれた。

1. **実プレイだけが引くストリーム**(処理の有無の裏付け)
   - ブレークスルー(0xB818)、敗戦スランプ(0x5C6)、スランプのモメンタム(0x5C7)、モチベ喪失(0x5C8)、乱入(8888)。
   - ラストランの台詞と関係(0xFAD3/0xBE3B)、密着取材(0xB4B4/0xBE56)。
2. **エンジンだけが引くストリーム**(同上)
   - 突然の退団(0xDE7A)と退団時の関係(0xBE3A)、怪我引退の関係(0xBE3C)と台詞(0xFAD2)。
   - tickWeek の中のプロモ行動のイベント名抽選(選手ID ^ 0xFEA5)。E01 の結果、エンジンではプロモに回った選手だけが引く。
3. **両方が引くのに回数が違うストリーム**(ここから先の結果が乱数消費のずれで変わる)
   - **tickWeek 本体の共有ストリーム**(season, week): 多くのシナリオでエンジン11〜12回/実プレイ26〜33回。
     - このストリームは週の行動(練習/プロモ/休養)の抽選に渡されている(management.js:13816 → processManage)。
     - 「プロモ(1〜2回)」か「練習(能力選び+伸び+体調で数回)」かで引き数が変わる。つまり K1-E01 の結果。
   - **週次の関係値の減衰・ストーリー**(0xBE1B): 1395 対 1401 など。自団体ペアの状態の差で分岐が変わり、同じストリームを後で引く **AI ペアの関係値までずれる**(K1-B04。§6.1 の実験で確認)。
   - **試合成長**(1732): injury シナリオでエンジン27回/実プレイ29回。
     - エンジンが怪我引退者をロスターから外したぶん、以降の選手の「伸びる能力の抽選」が1つずつずれる。
     - このシナリオの能力差(例: エンジン pw+2 対 実プレイ +1、実プレイだけ st+1)は、式の違いではなく乱数消費のずれ。
   - 試合の関係値(0xBE2A)91 対 92(injury)、スナップショット(0x5A30)107 対 120 など。入力の差で候補数が変わった結果。

**見分け方(ハーネスの出力)**

- 片方しか変えていない項目(engOnly / appOnly)は、処理の有無。
- 両方が変えた項目(both)は、同じシナリオの乱数表で、その値を決めるストリームの引き数を見る。
  - 引き数が一致していれば、式・入力の違い。
  - 食い違っていれば、乱数消費のずれ。
- 許容リストの category 欄に、この判断を項目ごとに書いてある。

## 10. 限界と注意

- **fixture は1つ**(seed 42 の S2W14、若いロスター)。
  - 年齢・条件はシナリオ側で設定して補っている。
  - 長期(数十季)の数値の違いは測っていない。§4 の数字は1興行ぶんの実測で、季・年単位の影響は見込みとして書いた。
- **比べているのは通常興行だけ。** 遠征・対抗戦・PPV・大会は §7 X11 に挙げるにとどめた。
- **実プレイ経路は「全試合スキップ」と「1試合ずつスキップ」で走らせている。**
  - 観戦(iframe)の経路は、シングルでは1試合ずつスキップと同じ関数で試合を作る(recordFrames の有無だけ)ので、状態は同じになる。
  - タッグの観戦は、1試合ずつスキップと同じ前処理をする。
- **ポップアップの中の選択で決まる処理は含まない**(節目イベントの選択、派閥イベントの選択など)。これらは非同期で、社長の操作で結果が変わる。
- **B(tickWeek 後)の受け皿は乱数に左右される。** src の別の変更で乱数の引き数が変わると、B の差の場所が増減することがある。
  - B の受け皿は「消えた」判定から外してある。
  - 新しい場所に差が出たときだけ落ちる。
- ハーネスはブラウザ(Chromium)を使う。
  - worktree で初めて回すときは `npm ci` が必要。
  - Playwright のブラウザは既存のものを使う。
