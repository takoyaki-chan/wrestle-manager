## ユーザーからのフィードバック（原文）

> 最後に観客のリクエストがほぼ同じ状態になるので、体験版みたいな感じで
> 一定数試合したら解除みたいな感じにしてもらえたらいいなと感じた

要するに **(a) 終盤になるとリクエストの顔ぶれが固定化する**、**(b) 体験版にあった「一定試合数で解禁」のような段階的な広がりが欲しい** という要望。

## 用語の確認

ゲーム内の「観客リクエスト」= コード上の **fanExpect**（ファン期待カード）。`Engine.fanExpect.generate()` で生成され、興行カードに含めると集客とメディア収入にボーナスが入る。

---

## 実コード調査で判明した現状

### 生成ロジック (`src/management.js` L13925-14010 `Engine.fanExpect.generate`)

候補は3つの優先度階層からのみ生成され、最後に `slice(0, 3)` で上位3件に絞られる:

| Priority | 種別 | ソース | 該当行 |
|:---:|---|---|---|
| **3** | 抗争系 | 既存 rivalries オブジェクト全件走査 | L13956-13982 |
| | bitter遺恨ペア | `pairState.resolvedType === 'bitter'` | L13971 |
| | good rival 再戦 | `pairState.resolvedType === 'goodRival'` | L13965 |
| | 高rivalry値ペア | `minRivalry >= 50` または `isOneSided` | L13975 |
| **2** | 王座挑戦 | 王者 vs 人気1位の eligible 挑戦者 | L13986-13998 |
| **1** | 人気上位対決 | TOP1 vs TOP2 | L14001-14004 |
| | 人気上位対決 | TOP1 vs TOP3 | L14005-14007 |

freshness チェック (L13945-13951): 同カードがウィンドウ内で4回以上組まれていたら除外、3回以下のマンネリは priority -1。

### なぜ固定化するか（分析）

**プールの天井がそもそも狭い:**

- **抗争系**: 既存 rivalries の中からしか出ない。新しい抗争が生えなければ顔ぶれは固定。エースが固まると抗争相手も固まる
- **王座挑戦**: 王者 × 「人気1位の非王者」固定。王者が変わらず、人気序列も安定すると永久に同じ組み合わせ
- **人気上位対決**: TOP1 × TOP2、TOP1 × TOP3 固定。エース層が固まると永久ループ

freshness で除外されても、フォールバックで出てくる候補が**同じプールの中の別のペア**でしかないため、根本的な多様性は生まれない。

## 体験版にあった「解禁」とは何か（推測）

ユーザーの言う「体験版みたいな解禁」は直接見ていないため推測だが、おそらく**興行数や進行段階で新タイプのリクエストが追加されていく**仕組みだったと思われる。前回会話ではユーザーに確認していない。

→ **新しい部屋で最初にユーザーに確認するか、git log や archive/ 配下の旧バージョンを掘って確認するのが安全。**

## 検討した対策の方向性（前回会話で話したもの）

### 提案: リクエスト種別を段階解禁する

現在の3タイプに加えて、`totalShows` / `season` / `orgPop` / 個別フラグで段階解禁される追加タイプを入れる。

| 解禁条件 | 新タイプ | 例文 |
|---|---|---|
| `totalShows ≥ 20` | 初遭遇マッチ | 「○○と××はまだ闘っていない！実現を望む声」 |
| `totalShows ≥ 40` | スタイル対決 | 「テクニシャンの○○と剛腕の××のスタイル対決が見たい」 |
| `season ≥ 2` | 世代闘争 | 「ベテラン○○と若手××の対決を望む声」 |
| `orgPop ≥ 30` | ヒール vs フェイス | 「悪役○○を懲らしめるのは××だ！」 |
| 引退発表後 | レジェンド送別 | 「○○の引退ロード、最後の対戦相手は誰だ」 |
| タイトル戦後 | リターンマッチ | 「○○のリターンマッチを望む声」 |
| ジュニアトーナメント後 | 新星挑戦 | 「優勝者○○の次の挑戦が見たい」 |

### コードの当て方の素案

`Engine.fanExpect.generate(state)` の中で、Priority 3/2/1 の生成のあとに段階解禁ブロックを挿入する想定:

```javascript
// Priority 2.5: 段階解禁タイプ
if (totalShows >= 20) {
  // 初遭遇マッチ候補（matchupLogに無いペア）
  // ...addCandidate(f1, f2, '初対決を望む声！', 2);
}
if (totalShows >= 40) {
  // スタイル対決
}
if ((state.orgPop || 0) >= 30) {
  // ヒール vs フェイス（personality archetype使用）
}
```

最終 `slice(0, 3)` の上限を 3 → 4 に増やすかは UI 幅次第（要検討）。

## 想定実装ボリューム

**中規模（2〜3時間）。** 新タイプ追加そのものは軽いが、各タイプの判定ロジック（ベテラン/若手の境界、スタイル対比など）を**既存の選手データから無理なく取れる属性で**実装する必要があり、ここで仕様レベルの判断が要る。**選手データに無い属性で判定しないこと**が鉄則。

## 注意事項（このプロジェクト共通の鉄則）

- **必ず実装ファイルを読んでから議論する。** 想像でルールや数値を語らない
