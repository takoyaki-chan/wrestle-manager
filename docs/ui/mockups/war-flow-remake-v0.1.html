対抗戦(War)フロー 再設計モックアップ v0.1 S3 対抗戦シーケンス / Stage(純黒) / baseline v0.8 準拠 — 実装なし・意匠確認用

前提

このモックが直そうとしている3点

① 受諾後に選手選択のターンが無い。 Engine.event.makeWarCard(management.js 15800) が OVR降順で自陣と敵陣を機械的に1位vs1位・2位vs2位…と組むだけで、社長は誰も選べない。 「社長は舞台を作る人」という三本柱に対して、対抗戦だけ舞台作りの手が入らない。
② 進行画面でカード全体が読み取れない。 renderWarMatchPreview(ui-common.js 764) は済んだ試合と次の試合を大きく描き、 その先を .pb-mrow.is-pending の1行テキストへ潰す。しかも並びが メイン→前座の降順なので、「次にどこへ進むのか」が上から下へ読めない。
③ 試合後セリフポップが規格違反。 _showWarVictoryChain(ui-common.js 1076) は getPortraitUrl(face・1:1・256×256)を .u3b-upper(132×194・2:3)へ object-fit:coverで入れており、顔の左右が確実に切れる。 加えて OVR・所属バッジが無く、外枠が --victory-panel-top/bottom の 紺のグラデーションパネルで、Stage(純黒)から浮いている。
直し方の方針。 3点とも「新しい様式を発明する」のではなく、 ゲーム内に既にある正しい様式へ寄せることで解く。 ①は E-4 4団体勝ち残り対抗戦の代表編成(_awEntryScreenHtml / .agw-entry-*)、 ②は E-4 のライブボードの「全員の状態が常に見えている」考え方、 ③は U3 で統一済みの顔出しブロック(_u3bSideHtml / .u3b-*)。 対応表はページ末尾。

判断が要る点（実装前に決めること）

  1. 試合数は3固定か。 ev.matchCount は挑戦状側が決めており、 makeWarCard は既定5。今回の指示は3試合前提で作ったが、5試合のとき画面2の行が5行になる。 行の縦を S 108×162 にしてあるので5行でも破綻はしないが、 「対抗戦は常に3試合」に寄せるなら仕様側の変更が要る。
  2. 相手の出場順を本当に先に開示するか。 開示すると「相性の良い相手にぶつける」最適化ゲームになりうる （数値哲学の「スプレッドシート化しない」に触れる）。 代案：3名は開示するが並び順は伏せる（E-4 と同じ「出場順は開戦時に公開」）。 その場合、画面2 の右列は chip の3名を横並びにして、行ごとの対戦相手は「?」にする。
  3. 選出の自由度に上限を設けるか。 何も縛らないと「格下3人を出して負けを最小化」も 「エース3人を出して勝ちに行く」も自由になる。E-4 は _eligible で怪我人だけ弾いている。 対抗戦でも同じで良いか（例：直近の興行で出場した選手は体調ペナルティ、など）。
  4. --victory-blue を残すか。 画面4 の名前色。対抗戦の自陣は --c-positive なので 青は文脈から外れているが、.u3b-theme-stage.is-victory は JT・天頂戦・特別興行の総括とも共有している。 対抗戦だけ外すか、全部まとめて見直すか。
  5. 因縁の見せ方。 画面2 で「⚔ 因縁 出羽鷹子」と名指ししているが、 社長が rivalry の数値を知っている扱いで良いか。数値は出さず「因縁あり」だけにしてある。
  6. おまかせの既定値。 現行の makeWarCard（OVR降順・メインが最強対決）をそのまま 既定にしてある。ここを変えると既存プレイヤーの体感が変わるので、変えないのが安全。
