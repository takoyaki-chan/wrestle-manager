# 3Dカスタム少女を使う技画像撮影・分離パイプライン v0.1

## 状態と目的

**状態：計画のみ。画像制作・GPT Image処理・ゲーム実装は開始しない。**

既存の2体ポーズデータを3Dカスタム少女で撮影し、試合エンジンに重ねる技画像の素材にする。どの技を作るかと優先度は [技イラスト・大技カバレッジ計画](move-illustration-coverage-plan-v0.1.md)、ゲームへ接続する手順は [試合エンジンへの技イラスト統合仕様](move-illustration-integration-spec-v0.1.md) を正本とする。本書はその前段の「撮影から透明パーツを書き出すまで」だけを定義する。

## 1. 担当と原則

| 担当 | 範囲 |
|---|---|
| 人間 | 3Dカスタム少女へ2体ポーズを読み込み、技として読める構図・カメラを確認してPNGを書き出す。初回のポーズ・構図確認は必ず人間が行う。 |
| Codex | 入力PNGをGPT Imageで基本3面図キャラの白線画マネキンへ変換し、その後はローカルの決定的な画像処理で分離・透過・輪郭抽出・命名・QAを行う。 |

- GPT Imageを使うのは、ポーズ・カメラ・接触位置を保ったまま素材を単純化する人形化までとする。
- **人形化の完成様式（2026-08-12 Keisuke裁定で明文化）**: `assets/moves/reference/mannequin_turnaround_master.png` の**基本3面図キャラに統一**する。白ボディ+黒線画、簡略化した衣装（レオタードの線・ニーパッド・編み上げブーツ）、卵型の顔なし頭、淡いグレー陰影。旧世代30枚のmasterと同系統。**ベタ塗りグレー2トーンの人形化は誤解釈であり不採用**（2026-08-12のPhase A初回試作で発生）。
- 人形化の後に、完成絵を生成AIで描き直さない。分離、背景透過、輪郭抽出、サイズ変換、命名、原本比較は可能な限り決定的なローカル処理に限定する。
- 顔、髪、選手固有の衣装装飾、文字、余計な小物、不要な影は、人形化後の素材へ残さない（3面図キャラの標準装備＝レオタード・ニーパッド・ブーツは残す）。
- **攻守の判別は単体撮影パスとの照合で行い、ベタ塗り色分けを完成絵へ持ち込まない**。作業用中間物（work/）に限り色分けを使ってよい。線幅・陰影の濃さは最初の試作で固定し、技ごとに変えない。
- **最終3枚のレイヤー役割**（`image/moves/README.md` のゲーム側色付け仕様に対応）: `attacker`/`receiver` はゲーム実行時にティント（色付け）される白ボディのフィルレイヤー、`outline` は黒線画・影をまとめて両者の上に重ねるレイヤー。黒線を役割レイヤーに焼き込むとティントで汚れるため、線は outline 側へ寄せる。

## 2. 1ポーズの撮影契約

1技につき、同一カメラ・同一解像度・無地背景・UI非表示で、次の3撮影パスを推奨する。

| 撮影パス | 必須度 | 内容 |
|---|---|---|
| 2体完成構図 | 必須 | 攻め手と受け手を、技の接触位置・前後関係を含めて撮影する。`<pose>_source.png` の原本になる。 |
| 攻め手のみ | 推奨（完全分離時は必須） | 同じカメラのまま攻め手だけを撮影する。重なりで隠れた攻め手の部位を確認する。 |
| 受け手のみ | 推奨（完全分離時は必須） | 同じカメラのまま受け手だけを撮影する。重なりで隠れた受け手の部位を確認する。 |

完成構図1枚だけでも処理はできる。ただし、重なりで隠れた部位を完全に復元できる保証はない。最終的に攻め手・受け手の完全な個別像が必要なら、単体の攻め手／受け手パスを必須とする。

## 3. ファイル契約

`<pose>` はカバレッジ計画の永続`assetId`に対応する英字IDを使う。例：`16_powerbomb`。このファイル構成は**制作中のPNG**であり、ゲーム配置用の512px WebPとは区別する。

```text
assets/moves/<pose>/
  <pose>_source.png             # 3Dカスタム少女の2体完成構図。再処理用原本
  <pose>_attacker-capture.png   # 3Dカスタム少女の攻め手のみ撮影。完全分離時に必要
  <pose>_receiver-capture.png   # 3Dカスタム少女の受け手のみ撮影。完全分離時に必要
  <pose>_master.png             # 2体完成構図をグレー人形化した再処理用完成画像
  work/<pose>_attacker-gray.png # 単体撮影を人形化した作業用入力。納品物ではない
  work/<pose>_receiver-gray.png # 単体撮影を人形化した作業用入力。納品物ではない
  <pose>_attacker.png           # 最終の透過PNG：攻め手
  <pose>_receiver.png           # 最終の透過PNG：受け手
  <pose>_outline.png            # 最終の透過PNG：輪郭・影
```

- 最終の基本3画像は`attacker`、`receiver`、`outline`である。`source`と`master`は再処理用中間物であり、最終3枚には数えない。
- 原本も納品物へ含める場合、1ポーズの保存物は4枚以上になる。この数を「最終3枚」と混同しない。
- ゲームへ置く時は、`receiver.png`を実行時名称の`NN_slug_defender.webp`へ変換・対応付ける。制作工程の`receiver`とReplay実装の`defender`は同じ受け手を指す。

## 4. 人形化から最終PNGまで

1. 人間が3つの撮影パスを確認し、`source`と可能なら単体2枚を渡す。
2. CodexがGPT Imageへ渡し、ポーズ・カメラ・接触位置を保った基本3面図キャラ様式（白線画マネキン）へ変換する。2体版を`master`、単体版を`work/*-gray.png`として保存する（単体作業パスは判別用の色分け可）。
3. ローカル処理で、`master`の色分けと単体人形パスを照合し、攻め手と受け手を透過PNGへ分離する。単体パスは隠れた部位の形を補助するために使う。
4. `master`から輪郭を抽出して`outline`を作る。輪郭はGPT Imageで別生成しない。線幅、白黒反転、外周のみか内部線も含めるかを共通設定として管理する。
5. `attacker` + `receiver` + `outline`を再合成し、`master`と比較して位置・接触・前後関係・シルエットが一致するかQAする。
6. QAを通過したPNGだけを、統合仕様の`image/moves/NN_slug_{attacker,defender,overlay}.webp`へ決定的に変換する。変換後も`source`と`master`は残し、再処理を可能にする。

## 5. QA基準

| 観点 | 合格条件 |
|---|---|
| ポーズ | `master`が`source`の技の形、接触位置、カメラを保つ。 |
| 攻守 | 攻め手／受け手が色とファイル名で一意に分かれ、標準向き（攻め手は右・左向き）で読める。 |
| 分離 | 再合成が`master`の人物シルエットと前後関係に一致する。単体パスがある場合、隠れた部位が不自然に欠けない。 |
| 人形化 | 顔・髪・服の細部、文字、小物、不要な影が残らない。人物内部に穴、半透明、孤立ノイズを作らない。 |
| 輪郭 | `outline`は`master`から抽出され、採用済みの線幅・反転・内部線方針に一致する。 |
| サイズ | 同一ポーズのsource、単体撮影、master、最終PNGは同じキャンバスサイズ・カメラ基準を守る。 |

## 6. 将来のバッチ運用

目標は、撮影PNGを`assets/moves/<pose>/`へ置いて処理を依頼するだけで、Codexが人形化→分離→輪郭→命名→原本比較QAまでを行える運用である。

ただし、3Dカスタム少女のポーズ読込・構図決め・反復撮影の自動操作は、本パイプラインの前提にしない。DirectX／独自UIでの画面操作が安定していることを別タスクで確認してから、自動化できる範囲だけを追加する。初回のポーズ・構図・カメラ確認は人間担当を維持する。

## 7. 再開手順

1. [技イラスト・大技カバレッジ計画](move-illustration-coverage-plan-v0.1.md)から次のP0技を選ぶ。
2. 本書の撮影契約に従い、3Dカスタム少女で2体＋可能なら単体2枚を撮影する。
3. `<pose>`と撮影PNGを示して、Codexへ「3D技画像パイプラインで処理」と依頼する。
4. Codexは本書のファイル契約・QAを満たすまで処理し、統合仕様のPhase 0以降で初めてゲーム配置を検討する。
