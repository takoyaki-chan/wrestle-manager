## 共通原則

- **JA出力は1バイトも変えない**(ja-goldenが番人・--update禁止)。P3aは「同じ文章を、翻訳可能な構造から生成する」工事
- **完全文テンプレート化の方法**: 条件分岐で断片を連結している箇所は、**分岐の組み合わせごとに完全な一文のテンプレート**へ展開する(例: `{turns}ターンに及ぶ接戦の末、{phase}に{winner}が{finish}で{loser}を下した。`)。連結結果と1バイト一致するように各変種を列挙する
  - 変種数の上限目安は12。超える場合は既存の「。」境界でのみ文を分割してよい(文中での分割は不可=JA出力が変わる)
  - テンプレート置き場は data.js(NEWS_HEADLINE_TEMPLATES と同じ流儀)。プレースホルダは `{name}` 形式(WM_I18N.t仕様)
- **Engineは WM_I18N を呼ばない**。テンプレ選択と整形はEngine内でよい(データ駆動になっていれば、ENはStage Bでテーブルに英語列を足して表示時に引ける)

## バッチ3: gameLog構造化+キーワードスニッフィング根絶(監査1-5/2-9)

**設計判断**:
- **D-G1**: 新形式エントリ `{ type: '<英数キー>', data: {...}, s: <season>, w: <week> }`。表示文は data.js の **GAMELOG_TEMPLATES**(type→完全文テンプレ。絵文字込みで現行文と1バイト一致)から表示時整形。`G.transferLog`(app.js:5571)が先例
- **D-G2**: **既存セーブの文字列エントリはそのまま許容**(計画決定#4「過去生成分は生成時言語のまま」)。表示側は「stringならそのまま表示 / objectならテンプレ整形」の二刀流
- **D-G3**: ログのUI分類フィルタ(ui-render.js:1014,4330等の `.includes()`)は新形式では `type` の族で判定。**旧文字列エントリに限りキーワード判定を残す**(レガシーはJA固定なので英語化しても壊れない)
- **D-G4**: 財務ラベル(ui-render.js:1816,1819)・タグ戦実況のCSSクラス判定(tag-battle-main.js:640-648)も同法: 生成元に category/type フィールドを足し、表示文の部分一致判定を消す
- **D-G5**: 約50箇所のpushは**機械的に一括変換**(1箇所=1 type)。typeキーは英数スネーク(例: `contract_signed`, `save_loaded`)。**Gに保存するのは type+data のみ**
- 派閥ロール・診断ラベル逆引き(監査2-8の6箇所)も本バッチで: 上流の生成箇所に中立キーを併記し、逆引き比較を消す

検証: ja-golden完全一致(gameLogは焼き込み→表示時整形に変わるが、**表示される文字列**は不変。goldenがdebugLog/gameLog文字列を直接スナップショットしている場合はスナップ対象を「表示時整形後の文字列」へ合わせる修正を同時に行い、その正当性を報告で説明すること)/ 既存セーブ読込の後方互換テスト(旧文字列エントリ混在セーブで例外なし)/ npm test / auto-sim 40 / ratchet非増加
