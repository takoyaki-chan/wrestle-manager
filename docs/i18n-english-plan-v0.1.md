## 2. アーキテクチャ方針: 5層に分けて別々に扱う

| 層 | 対象 | 方針 |
|---|---|---|
| 1. ロジックキー層 | `injury.type==='重傷'`、コーチ能力`'新人育成'`、trait`'早熟'`、headline`'戴冠'`、personality等。比較箇所53件+データ定義 | **キーは日本語のまま維持**し、画面に出る直前でのみ辞書を通す。キー英語化はセーブ互換破壊+最大のバグ源なのでやらない。「翻訳」ではなく「表示とロジックの分離」 |
| 2. UIクローム層 | ボタン・ラベル・システム文(約4,700本) | `t()` 関数+辞書で機械的に移行 |
| 3. テンプレ層 | ニュース・新聞・記録(約6.1万字) | パラメータ化済み(業界ニュースは type+データ保存・表示時整形 = management.js `_pushNews`)。英語テンプレは語順・冠詞・複数形があるため**英文として書き下ろす**。単語置換は不可 |
| 4. セリフ層 | 約30.6万字/17,600本 | **英語トーンバイブル**(archetype毎の英語の声)を先に設計・承認 → Excel往復パイプライン(GLIMPSE_B統一の資産)に**英語列を追加**して制作 |
| 5. 固有名詞層 | キャラ98・技160・コーチ35・会場・ベルト・団体・大会名(data.js内 日本語name定義174件+技名) | 英語表記辞書。ドラフト→一覧承認→辞書化 |

### 「いつでも切替可」の含意

- セーブ(G)には原則として**言語非依存のキーとパラメータのみ**を保存する(業界ニュースは既にこの形)
- 整形済み文章をGに焼き込んでいる箇所(新聞記事・年代記・記録の疑い)はP2で全数監査し、
  可能なら「表示時整形」へ寄せる。寄せられない分は生成時言語のまま残る仕様として明記

### 既存「多言語対応憲章 v1.0」との関係(`docs/i18n-charter-v1.0.md`, 2026-07-10)

憲章は次回作向け(本作には非適用)として書かれたが、原則は本計画にそのまま流用する:

- **そのまま採用**: 第2条(文は丸ごと一文で持つ・断片連結禁止)/第5条(台帳が正、状況メモ必須)/
  第6条(英語は1.5〜2倍長い前提)/疑似ローカライズ。セリフ・テンプレ層のExcel台帳+英語列は第5条そのもの
- **新規テキストには全面適用**: 第1条(コードはキーのみ)。移行完了ファイルはラチェットで直書き再発を防止
- **意図的な逸脱(本作の後付け事情)**: ロジックキー(`'重傷'`等)は言語中立IDへ改名**しない**。
  セーブ互換を守るため日本語キーのまま維持し、表示時マッピングで分離する。
  第1条の精神(表示とロジックの分離)は満たす
- P2監査に**断片連結(第2条違反)箇所の検出**を含める。語順が日本語で焼き付いた連結文は英語化できないため、
  該当箇所はテンプレ化(完全な一文+プレースホルダ)に直してから翻訳する

## 3. バグ・手戻り防止装備(実装する場合、P1で最初に作る)

1. **JAゴールデンテスト** — 抽出作業の前後で日本語版の出力(固定シードのニュース/セリフ/画面文言)が完全一致することをスナップショット検証。「英語対応で日本語版が壊れる」を構造的に防ぐ
2. **擬似ロケール** — 翻訳ゼロの段階から `⟦…⟧` 括り疑似英語へ切替可能にする。翻訳漏れ(日本語が残る箇所)と英語長文でのレイアウト溢れ(吹き出し・ボタン)を**翻訳を書く前に**洗い出す
3. **ラチェットガード** — ファイル毎の「日本語生文字列本数」基準値を保持し、増えたらテスト失敗(`test/i18n-scan.js` を流用)。移行済み箇所への直書き再発を防ぐ
4. **翻訳漏れログ** — 辞書に無いキーは console + フライトレコーダーに記録
5. **機械検査** — EN文のプレースホルダ欠落(`${name}`落ち)・用語集逸脱・文字数上限(吹き出し幅)をExcelパイプライン側で検査
6. **UI走破ハーネスを両言語で実行**。auto-sim(不変条件)は文字列非依存なのでそのまま有効

## 4. フェーズ計画と見積もり

### 二段構え(2026-08-19 Keisuke方針)

翻訳と構造工事を分離し、**Stage A「翻訳可能化工事」を独立マイルストーン**とする。

- **Stage A(構造)= P1+P2+P3a**: コード内に直書きされたセリフ・ナレーション・システム文を台帳/テーブルへ分離し、
  断片連結を完全文テンプレート(プレースホルダ入り)に直す。**日本語版の見た目・挙動は不変(JAゴールデンテストで保証)**。
  翻訳を1文字も書かなくても、憲章準拠・直書き負債の成長停止・次回作への資産として単独で価値がある
- **Stage B(翻訳)= トーンバイブル+P3b+P4+P5+P6**: Stage A完了時点の姿は「台帳に英語列を埋めるだけ」。
  着手判断は英語トーンバイブル試作を見てから別途行える

実測では、構造分離が必要なのは UI・システム4.8万字+エンジン内2.7万字+観戦実況0.6万字 ≒ **8.1万字(全体の17%)**。
残り83%(data.jsテーブル群・セリフ専用ファイル)は既にデータ分離済みで、Stage Aの対象はコード側に限られる。

1セッション=Claude/Codexの1作業単位(概ね半日相当)。P4/P5の執筆はCodex/Opus委譲で並行化可能。

### 段階リリースの選択肢

P3完了時点で「UIは英語・セリフ/記事は日本語」の中間状態が技術的には作れるが、
このゲームの魂はセリフなので**中間状態での対外リリースは非推奨**。P5完了までは開発内マイルストーンとする。

## 5. 既知のリスク・論点

- **日本語=ロジックキーの混在**(§2層1)。personalityには `'aggressive' || '強気'` の英日併記比較が既にあり、過去移行の名残で揺れている。P2で全数確定が必要
- **レイアウト溢れ**: 英語はUIラベルで日本語の1.5〜2倍長くなりがち。吹き出し・ボタン・隊列ラベルが危険箇所。擬似ロケールで先行検出
- **英語の「声」の設計**: お嬢様言葉・語尾・一人称の差は英語に直訳できない。archetype毎に英語での話法(語彙水準・リズム・口癖)を再設計する必要がある。トーンバイブルの中核課題であり、ここの出来が英語版の品質を決める
- **通貨・単位**: 世界観は日本の団体なので**円表記維持を提案**(英語圏の読者にも日本物として自然)。承認事項
- **黒田記者の英文体**: 記事3.1万字の翻訳は「新聞記事の英語」として別の文体設計が要る
- **Steam展開との連動**: ストアページ・実績等は本計画の対象外(project_steam_i18n_interest 参照)。ただし英語版の完成はSteamページ先行公開案の前提を満たす
- **配布サイズ**: 英語データ追加は+1MB未満。問題なし。`release/manifest.json` への新規ファイル追記を忘れないこと
