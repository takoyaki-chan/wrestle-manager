## 2. AI団体のメンバー放出ロジック（既存）

### 2.1 自然引退（processSeasonEnd L4715-4723）
- **毎シーズン末**にwearベースの引退判定
- 加齢(+1/年) + wear蓄積(23歳以上、baseWear 10±3 - durability補正)
- 引退した選手はロスターから除去 → 殿堂入り判定へ

### 2.2 trust不満退団（processAIContracts L4782-4897）
- **毎シーズン末**に trust < 40 の選手を判定
- trust 30-39: 15%退団 / trust 15-29: 40%退団 / trust 0-14: 70%退団
- **ロスター最小値 5名** を下回らないガード
- 退団先: 他AI団体(50%) / FA化(30%) / 引退(20%, 28歳以上のみ)

### 2.3 怪我引退（processAIWeek 週次）
- 毎週の怪我判定で重傷→引退のパスあり
- `_weekRetiredIds` に蓄積

### 2.4 削除される選手の年間規模（推定）
- 自然引退: 1-3名/シーズン（ロスター規模による）
- trust退団: 0-2名/シーズン
- 怪我引退: 0-1名/シーズン
- **合計: 年間1-6名程度がロスターから抜ける**

## 3. ドラフトでのAI新人追加 — ロスター上限チェック

### 問題: **ドラフト中にロスター上限チェックがない**

| 処理 | 関数 | 上限チェック |
|------|------|:---:|
| 非選択候補の裏セリ | `startDraftNegotiation` L4054 | **なし** |
| AI自動落札(1社のみ) | `startDraftNegotiation` L4066 | **なし** |
| 交渉UIでのAI落札 | `draftNextCandidate` L4349 | **なし** |
| EMPRESS安全網 | `_finalizeDraft` L4148 | **なし** |

**対比**: ドラフト以外の既存処理は上限チェック済み

| 処理 | 関数 | 上限チェック |
|------|------|:---:|
| AI団体間移籍 | `aiInterTransfer` L5139 | `>= idealRoster` |
| AI FA獲得 | `aiFAAcquire` L5225 | `>= idealRoster` |

### 何が起きるか
ドラフトで org_s(理想16名) が例えば5名獲得した場合:
- 引退前のロスターが14名 → ドラフト後に19名
- シーズン末引退で2名減 → 17名（理想+1）
- offWeek 4 の aiInterTransfer / aiFAAcquire は上限チェックで追加をスキップ
- **結果: 1シーズンで解消されるが、ドラフト直後は一時的に上限超過**

## 4. spec §5.5 ロスター充足度補正の効き方

`draft-negotiation.js` `_getRosterFillMul()`:

| 充足度 (gap=現在-理想) | 倍率 | 効果 |
|:---:|:---:|:---|
| gap ≥ 0 (理想達成済み) | 0.5 | 参加率を**半減** |
| gap -1～-2 | 1.0 | 変化なし |
| gap -3～-4 | 1.3 | 参加率+30% |
| gap ≤ -5 | 1.6 | 参加率+60% |

### 具体例

理想達成済み(gap=0)の org_s が superElite 候補に:
- base参加率 0.95 × fillMul 0.5 = **0.475** (47.5%)
- → 約半数のケースで不参加

理想-4名(gap=-4)の org_b が promising 候補に:
- base参加率 0.50 × fillMul 1.3 = **0.65** (65%)
- → 積極参加

### 補正の限界
- 参加率を半減しても **参加すること自体は防げない**
- 参加した後の `obsessionScore`（執着度）は充足度の影響を受けない
- つまり「ロスター満杯でも参加した団体は全力で粘る」状態

## 6. 設計上の問題点と推奨修正案

### 問題点A: ドラフト中のロスター上限チェック欠落
- **深刻度: 中** — ゲーム破綻はしないが、不自然なロスター肥大が起きる
- AI団体が理想以上の選手を抱えても、翌シーズン末の引退・退団で自然解消はされる
- しかし「16人団体が20人になる」のはプレイヤーから見て不自然

### 問題点B: 充足度補正が参加率のみで執着度を制御しない
- **深刻度: 低** — §5.5は「参加するかどうか」の制御で設計意図通り
- 参加後の粘り強さまで制御すると、ドラマ性が失われる

### 問題点C: ドラフト後のロスター整理パスがない
- **深刻度: 中** — offWeek 3(ドラフト) → offWeek 4(移籍) → offWeek 5(新シーズン) の間に「ロスター整理」がない
- 既存の processAIContracts は offWeek 1（次シーズン末）なので、1シーズン丸々ロスター過剰状態

### 推奨修正案

#### 案1: ドラフト中にロスター上限チェックを追加（最小工数）
- `startDraftNegotiation` と `draftNextCandidate` で AI落札時に `roster.length >= idealRoster` をチェック
- 上限到達なら落札をスキップ → 次に粘った団体に権利移動 or 流札
- **懸念**: セリエンジン内部に上限チェックを入れると、セリの結果が事後的に覆る不自然さ

#### 案2: assignInterest で上限到達団体を不参加にする（推奨）
- `assignInterest` 内で `currentSize >= idealRoster` なら `participating: false` を強制
- セリ開始前に「この団体はもう枠がない」と決まるので自然
- 充足度 0.5倍の代わりに 0 倍（完全不参加）にするだけ
- **利点**: セリエンジンの内部ロジックを変えずに済む

#### 案3: ドラフト後にロスター整理パスを追加（大工数）
- offWeek 3 ドラフト完了後に `processAIRosterPruning` のような処理を追加
- 理想超過分の最弱選手を release → FA化
- **懸念**: AI団体が「獲得したばかりの選手を即放出」するのは不自然

#### 推奨: 案2（上限到達→不参加）+ 案1の軽量版（安全弁）
- 主ロジック: `assignInterest` で `gap >= 2`（理想+2以上）なら不参加強制
- 安全弁: `pushUniqueFighter` 呼び出し前に `roster.length < idealRoster + 2` チェック
- 理想超過を+2名まで許容（引退見込み分のバッファ）
