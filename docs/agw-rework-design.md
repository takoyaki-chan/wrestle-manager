## 2. 現行構造の問題

### 2.1 画面所有権がない

- 代表編成は `#mdlAOverlay` を使い、背後のOffice画面を残したまま重なる
- 大会進行は `#showResultOverlay` / `#showResultBox` を借り、`renderAutumnWarBoard()` がDOMのstyleを直接上書きする
- 興行結果用オーバーレイの見た目と閉じ方にAGWが依存している
- Stage中にOfficeのChromeを隠す責務が明確でない

### 2.2 大会の判断材料が不足する

- 布陣ボードはOVRを表示しない
- condition 0〜80をそのままパーセント幅へ使い、満タンでも80%に見える
- 選手名・顔画像から詳細を開けない
- 編成候補が上半身カードの流用で、先鋒・中堅・大将という意思決定が主役に見えない

### 2.3 観戦経路がない

- `_agwFocusHtml()` は「結果を見る」だけ
- `simulateNextBout()` は `recordFrames` を渡さず、観戦用結果を作れない
- 一方、JT/天頂戦共通の `_jtcFcCore()` と、春タッグの観戦開始・復帰パターンは既にある

## 3. シーケンス設計（R-5）

### 3.1 所属シーケンス

**S9 秋の陣シーケンス（暫定）** とする。

- S4 ジュニアトーナメントの「段階的な勝ち上がり」
- S8 春タッグリーグの「大会固有ボードを逐次更新」
- S3 対抗戦の「団体同士のStage対峙」

これらを参照するが、どれかの子画面にはしない。毎年固定開催・4団体・勝ち残り消耗という独自の体験キーを持つため、独立した年次大会シーケンスとして扱う。

**共通ビジュアルキー**：純黒Stage、秋エンブレム、`var(--ev-autumn)` と `var(--gold)`、縦の勝ち上がり線、勝者が中央に残る構図。OfficeのCream Panelは週35の事前準備だけに限定する。

### 3.2 週34〜36の全体遷移

```text
週34 Office / 告知バナー
  └─ 参加4団体・準決勝カード・開催週を予告

週35 Office / 事前編成
  └─ 代表3名と順番を仮登録（閉じて後回し可）

週36 Stage takeover
  導入 → 布陣確認/未登録なら編成 → 大会進行
      → 観戦または結果確認をフォールごとに反復
      → 決勝前再編成（該当時のみ）
      → 決勝 → 大会結果 → MVP一言 → Office復帰
```

週35で登録済みでも週36の導入を飛ばさない。「どの大会が始まるか」「どう勝つか」を理解してから、登録済み布陣を確認して開戦する。週35を未操作なら同じ編成部品をStage版として強制表示し、自動編成だけで知らないまま始まらないようにする。

### 3.3 専用DOM

`src/index.html` に次の専用ルートを新設する。

```text
#autumnWarOverlay.agw-overlay
  #autumnWarScreen.agw-screen
    .agw-screen__header
    .agw-screen__body
    .agw-screen__footer
```

- `#showResultOverlay` / `#showResultBox` は使わない
- phaseは `data-phase="intro|entry|board|reorder|result|mvp"` で表し、JSからstyle文字列を代入しない
- `agw-screen--office` と `agw-screen--stage` を画面単位で切り替え、同じ画面内にカテゴリを混在させない
- `intro` 以降のStage phaseではトップバーとナビを隠す
- 閉じる操作は週35 entryだけに許可し、週36開始後は大会完了までOfficeへ戻さない
- focus trap、Escape可否、復帰先focusを専用オーバーレイが所有する

### 3.4 phase別画面

| phase | カテゴリ / パターン | 主情報 | 主操作 |
|---|---|---|---|
| `intro` | Stage / P7 | エンブレム、4団体、準決勝カード、3ステップルール | `布陣を確認する` |
| `entry` | 週35はOffice、週36はStage / P5 | 候補、選出3名、先鋒・中堅・大将、相手強度 | `この布陣で開戦` |
| `board` | Stage / P7 | 4団体ボード、小型クライムライン、現在対戦 | `観戦する` / `結果を見る` |
| `reorder` | Stage / P5 | 回復後condition、OVR、決勝順 | `決勝布陣を確定` |
| `result` | Ceremony寄り / P7 | 優勝団体、決勝スコア、MVP、最多勝 | `MVPへ` |
| `mvp` | Ceremony / P7 | MVPスタンド画像、一言 | `大会を終える` |

### 3.5 観戦中の所有権（R-1）

1. `board` で `_jtcFcCore()` を使い、`観戦する` / `結果を見る` を同じフォーカスカードへ出す
2. 観戦時だけ `simulateNextBout` の再生用経路で `recordFrames:true` の結果を生成する
3. AGW overlayを一時的に非表示にし、既存 `#battleOverlay` と `battle-engine.html` へ `START_MATCH` を送る
4. 終了通知を受けたら、その観戦で既に確定した1フォールをGameStateへ一度だけ反映する
5. `#battleOverlay` を閉じ、AGW overlayの `board` を再描画し、起動ボタンへfocusを戻す

二重進行防止のため、観戦開始時に `{sessionRngBefore, leftId, rightId, resolvedBout}` を一時保持し、受信側は一度だけ消費する。観戦中はAGWの両ボタンを無効化する。結果を見る経路と観戦経路は、最終的に同じ「解決済みboutを1回適用する」関数へ合流させる。

## 4. 編成画面の複数案（R-6）

### 共通要件

- `getStandUrl(id, Engine.util.ov(f))` のスタンド画像を使う
- OVR、condition、スタイル、怪我/レンタル不可理由を文字でも示す
- 先鋒・中堅・大将を単なる選択順ではなく、常時見える3枠として扱う
- 選手画像または名前から `showFighterPopup(fighterId, source)` を開ける
- 並べ替え操作と詳細操作を分離する。詳細は画像/名前だけ、drag handleまたは上下ボタンだけが並べ替えを担当する
- 相手の団体平均OVRとOVR幅を表示する。ただし決勝の最終順は確定まで伏せる

### L1. 中央3枠 + スタンド候補棚（推奨）

```text
┌ 候補棚：スタンド画像を横スクロール/折返し ─────────────┐
│ [候補][候補][候補][候補][候補]  OVR / condition        │
├─────────────────────────────────────────────────────────┤
│ 先鋒                 中堅                 大将            │
│ [大スタンド]  →     [大スタンド]  →     [大スタンド]     │
│ OVR / condition      OVR / condition      OVR / condition │
│ [↔移動]              [↔移動]              [↔移動]         │
├─────────────────────────────────────────────────────────┤
│ 相手: 平均OVR 78 / 幅72〜84       [おまかせ] [確定]       │
└─────────────────────────────────────────────────────────┘
```

長所：3人の順番が一枚絵になり、スタンド画像の存在感と意思決定を両立する。ドラッグできない端末でも左右移動ボタンで完結する。

注意：候補が多い時は棚だけをスクロールし、画面全体の横スクロールは発生させない。

### L2. 戦略レーン

```text
┌ 先鋒レーン ─ 自軍スタンド ─── VS ─── 相手傾向 ┐
├ 中堅レーン ─ 自軍スタンド ─── VS ─── 相手傾向 ┤
├ 大将レーン ─ 自軍スタンド ─── VS ─── 相手傾向 ┤
└ 候補ドロワー / おまかせ / 確定                 ┘
```

長所：誰をどの役割へ置くかと相手との力関係が最も読みやすい。

注意：相手の実順を見せると情報過多かつ決勝の伏せ情報を壊す。右側は「先鋒候補」ではなく団体傾向とOVR幅に限定する。375pxでは3レーンが縦に長くなる。

### L3. 1人ずつ決めるステップ式

```text
STEP 1/3 先鋒を選ぶ → STEP 2/3 中堅 → STEP 3/3 大将
                最後に3名の並びを一覧確認
```

長所：375pxで操作しやすく、役割の説明を選択時に読ませやすい。

注意：3人を同時比較できず、入れ替えの試行回数が増える。デスクトップで空間が余り、勝ち抜き順を俯瞰する体験が弱い。

### レスポンシブ方針

- 1024px以上：L1の候補棚 + 3枠を一画面に表示
- 701〜1023px：候補棚を2段、選出枠は3列を維持
- 700px以下：候補棚は横スナップ、選出枠は縦3段。「先鋒→中堅→大将」の矢印は下向きへ変更
- `.agw-opponent-panel` は非表示にせず、モバイルでは平均OVR・幅・団体名の1行要約へ縮約する
- タップ対象は36px以上、詳細ボタンと並べ替えボタンを重ねない

## 5. ルール提示（R-7）

### 5.1 導入画面の3ステップ図

文章を読む前に次の流れが分かるCSS図を置く。

```text
[各団体3名]  →  [勝者はリングに残る]  →  [3名全員OUTで敗退]
 ●●●             ○ VS ●                  OUT OUT OUT
```

各ステップはアイコンだけにせず、短い見出しと1文を持つ。

- `3名を先鋒・中堅・大将の順に送り出す`
- `勝者は消耗したまま次の相手と連戦する`
- `相手3名を先に脱落させた団体が勝ち上がる`

### 5.2 進行ボードの常設マイクロ説明

- フォーカスカード上：`勝者はリングに残り、敗者側の次の選手が登場`
- team card：`残り 2/3` と、各選手の `RING` / `NEXT` / `OUT`
- condition横：`元気` / `疲れが見える` / `消耗大` を併記
- 初回フォールだけ、次に誰が出るかを矢印で強調する

説明用モーダルは追加しない。導入を読まなくても、ボードの残り人数・リング表示・矢印で規則を推測できる状態を目標にする。

## 6. tier 1化の数値比較（R-2）

### 6.1 計測方法

`test/agw-tier-comparison.js` を使い、2,000個の同一シード（190019〜192018）について現行tier 2とtier 1を比較した。

- 各シードで4団体・準決勝2試合 + 決勝1試合を完走
- 各チーム戦の第1〜3フォールを集計（各行6,000試合）
- 残HPは引き分けを除く勝者の試合終了HP
- `tier2_hp_pct` / `tier1_hp_pct` は勝者残HP ÷ 勝者最大HP
- tier 1側は第4引数だけでなく、開始 `_hpOverride` の基準も `ENG.hpBase / hpScale` へ換算
- tier差で1試合目以降の乱数消費と勝者が分岐するため、同一シードの集団比較であり、全フォールが同一カードの一対一比較ではない

実行コマンド：

```text
node test/agw-tier-comparison.js 2000 190019
```

### 6.2 結果

| フォール | tier 2 平均残HP | tier 1 平均残HP | tier 2 残HP比 | tier 1 残HP比 | tier 2 平均ターン | tier 1 平均ターン | tier 2 勝者次condition | tier 1 勝者次condition |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 292.05 | 174.06 | 55.27% | 53.68% | 16.27 | 10.99 | 58.70 | 58.35 |
| 2 | 245.21 | 143.93 | 46.31% | 44.32% | 14.52 | 9.98 | 47.02 | 46.57 |
| 3 | 202.07 | 117.66 | 38.35% | 36.62% | 14.06 | 9.64 | 46.64 | 46.59 |

### 6.3 解釈

- HP実値はHP上限差に応じて約40%小さくなるが、消耗計算がHP比率を使うため、比率差は各フォール1.59〜1.99ポイントに留まる
- 勝者の次戦condition差は0.05〜0.45で、40のfloorも含む現行消耗カーブは実質維持される
- 第1→第3フォールの残HP比はtier 2で16.92ポイント低下、tier 1で17.06ポイント低下し、連戦による下り方は同等
- 平均ターンは5.28 / 4.54 / 4.42短く、tier 1はtier 2より約31〜32%短い

**結論**：消耗カーブは壊れないため、`wear = 12 + (1 - hpRatio) × 20`、floor 40、準決勝後回復+15は補正しない。補正するとtier 1だけを過剰に疲れさせる可能性が高い。

ただし9〜15フォールを観戦した時の大会テンポは明確に速くなる。長さを戻す必要が出た場合はwearを変更せず、観戦再生速度、フォーカスカードの間、決着演出で調整する。

### 6.4 Phase 2で同時に変える箇所

`simulateNextBout()` と検証用 `runLegacy()` の両方で次を揃える。

- `BIGMATCH_ENG.hpBase / hpScale` → `ENG.hpBase / hpScale`
- `simulateMatch(..., 2)` → `simulateMatch(..., 1)`
- specのtier記述と計測根拠を更新

第4引数だけを1へ変え、BIGMATCH基準の `_hpOverride` を残す実装は禁止する。通常最大HPを超える開始HPが入り、比較条件と消耗の意味が崩れるためである。

## 9. Phase 2の検証計画

### 自動テスト

- 観戦と結果確認が同一シードで同一boutを1件だけ進める
- 観戦終了通知の重複受信でもフォールが二重進行しない
- `recordFrames:true` の観戦結果にframesが存在する
- OVRと選手詳細ハンドラが全指定箇所にある
- condition 80がバー幅100%、40が50%になる
- 専用overlayを使い、`showResultOverlay` のstyleをAGWが変更しない
- 700px以下でも相手団体情報がDOMから消えない
- tier 1で通常最大HPを超える `_hpOverride` がない
- `node test/auto-sim.js 200 <seed>` を複数シードで実行し、違反0件を確認

### 実機確認順

1. 週34：告知に4団体・組合せ・開催週が見える
2. 週35：スタンド候補から3名を選び、先鋒/中堅/大将を入れ替え、詳細を開ける
3. 週36導入：3ステップルールだけで勝ち残り形式を理解できる
4. 大会進行：4団体の残数、OVR、condition、RING/NEXT/OUTが読める
5. 観戦：battle画面へ遷移し、終了後に同じフォールを二重進行せずボードへ戻る
6. 結果確認：観戦しない経路でも1フォールずつ進む
7. 決勝前：回復後conditionを見て並びを再確定できる
8. 結果：優勝・決勝スコア・MVP・最多勝が出る
9. MVP：スタンド画像と一言の後、Officeへ戻る
10. 375px / 700px / 1024px：横スクロールなし、相手情報あり、focus可視
