## §0 問題の定量分析

### 0.1 プレイヤーのスクリーンショットが示す現実

> 「3〜4年で資金ジャブジャブ、ヒートマックス、人気100」

### 0.2 団体人気（orgPop）の成長シミュレーション【現行】

**前提**: 年26興行（2週に1回）、年次減衰-3

現行の団体人気変動（applyShowPopularity L2870）:
  avgMQ ≥ 80 → +2
  avgMQ ≥ 65 → +1

| 年 | 平均MQ想定 | 興行あたり | 年間蓄積 | 年末orgPop |

|:------:|:-------:|:------:|:----------------:|:-----:|:----:|

### 0.4 Heat（ヒート）のシミュレーション【現行】

```
現行のHeat変動（heat.calcUpdate L549）:
  avgMQ ≥ 75 → +2
  avgMQ ≥ 60 → +1
  avgMQ ≥ 40 → ±0
  avgMQ ≥ 25 → -1
  avgMQ < 25 → -2
  + 慣性補正（正→負で-0.5、負→正で+0.5）

```

S3（MQ65〜75平均）の2週サイクル:
- 興行週: +1（MQ65+）
- 非興行週: -1.0 decay
- **差し引き±0〜+0.5**。中盤でWARM〜HOT（+2〜+9）は安定して維持可能。

S4以降（MQ75+平均）:
- 興行週: +2
- 非興行週: -1.0
- **純増+1/2週**。On Fire（+10）への到達は容易。

**問題**: Heatは-10〜+10の狭い範囲で、MQが安定すれば簡単に上限に張り付く。「勢いの維持が難しい」はずが、MQ75+の安定供給で自動解決される。

### 0.5 個人人気のシミュレーション【現行】

個人人気には**既に良い減衰カーブが入っている**（getDiminishingMultiplier）。

```
人気80+: rawGain × 0.10 → +10が+1になる
人気65+: rawGain × 0.13 → +10が+1
人気50+: rawGain × 0.18 → +10が+2
```

しかし、**メインイベント枠（×1.5）＋MQ80+（rawGain +8）＋勝者（+2）= raw +15 × 1.5 = +23** という巨大な入力があるため、人気80帯でも `+23 × 0.10 = +2` で毎試合上がる。26試合/年で +52 → 減衰があっても1〜2年で100到達。

**問題**: 減衰はあるが、**入力値が大きすぎて減衰が効ききらない**。

## §2 施策A: 団体人気の収穫逓減

### 2.1 概要

orgPopの変動に**個人人気と同じ思想の減衰カーブ**を導入する。orgPopが高いほど上がりにくく、下がりやすい。

### 2.2 逓減カーブ

```javascript
Engine.orgPop = {
  getDiminishingMultiplier(orgPop) {
    if (orgPop < 20) return 1.0;    // 創設期: そのまま上がる
    if (orgPop < 40) return 0.60;   // 地方団体: やや鈍化
    if (orgPop < 55) return 0.35;   // 中堅の壁: 大幅鈍化
    if (orgPop < 70) return 0.20;   // メジャーの壁
    if (orgPop < 85) return 0.12;   // トップ級
    return 0.08;                     // 覇権級: ほとんど上がらない
  },

  applyOrgPopChange(rawDelta, orgPop) {
    if (rawDelta > 0) {
      const mult = Engine.orgPop.getDiminishingMultiplier(orgPop);
      // 最小保証: rawDeltaが正なら端数切捨てでも0にはしない
      // ただし mult < 0.15 の帯では確率的に+1（期待値 = rawDelta * mult）
      const effective = rawDelta * mult;
      if (effective < 1.0) {
        // 確率的丸め: effective=0.3 → 30%の確率で+1、70%で+0
        return Math.random() < effective ? 1 : 0;
      }
      return Math.round(effective);
    }
    // 下落には逓減を適用しない（高人気ほど落ちやすいまま）
    return rawDelta;
  }
};
```

### 2.3 効果シミュレーション

**前提**: 年26興行、平均raw popDelta = +1.2/興行（MQ65-75平均）、年次減衰-3

| orgPop帯 | 倍率 | 実効/興行 | 年間 | 年末net | 帯通過に要する年数 |
|:--------:|:----:|:--------:|:----:|:------:|:---------------:|
| 0→20 | ×1.0 | +1.2 | +31 | +28 | **約0.7年** |
| 20→40 | ×0.60 | +0.72 | +19 | +16 | **約1.3年** |
| 40→55 | ×0.35 | +0.42 | +11 | +8 | **約1.9年** |
| 55→70 | ×0.20 | +0.24 | +6 | +3 | **約5年** |
| 70→85 | ×0.12 | +0.14 | +4 | +1 | **約15年** |
| 85→100 | ×0.08 | +0.10 | +3 | ±0 | **事実上不可能** |

**累積タイムライン**:

| マイルストーン | 現行 | **改善後** |
|:------------:|:----:|:--------:|
| orgPop 20 | S1 | **S1** |
| orgPop 40 | S2 | **S2〜S3** |
| orgPop 55 | S3 | **S4〜S5** |
| orgPop 70 | S4 | **S9〜S10** |
| orgPop 85 | S5 | **S15+** |
| orgPop 100 | S5〜S6 | **到達困難** |

### 2.4 「確率的丸め」について

逓減が強い帯域（orgPop 70+）では、rawDelta +1.2 × 0.12 = 0.144 となり、毎回0に丸められてしまう。これだと**全く上がらない**のでつまらない。

確率的丸めにすることで「14.4%の確率で+1」が実現し、**26興行中3〜4回は+1になる**。年間+3〜+4 - 減衰3 = +0〜+1。ゆっくりだが着実に上がる感覚が残る。

### 2.5 applyShowPopularity の改修案

```javascript
applyShowPopularity(roster, results, orgPop, rng) {
  if (results.length === 0) return { roster, orgPop, popDelta: 0 };
  const avgMQ = Math.round(results.reduce((s, r) => s + r.mq, 0) / results.length);

  // rawDeltaは現行と同じロジック
  const rawDelta = avgMQ >= 80 ? 2 : avgMQ >= 65 ? 1 : avgMQ >= 45 ? 0 : -1;

  // 逓減適用（新規）
  const effectiveDelta = Engine.orgPop.applyOrgPopChange(rawDelta, orgPop, rng);

  return {
    roster,
    orgPop: Engine.util.clamp(orgPop + effectiveDelta, 0, 100),
    popDelta: effectiveDelta
  };
}
```

## §3 施策B: 団体人気の下落圧力

### 3.1 設計思想

個人人気には5種の下落要因（連敗・スキャンダル・怪我忘却・ME凡戦・移籍リセット）があるのに、団体人気には**年次-3しかない**。個人人気の下落が団体に波及しない構造は不自然。

「上がりにくくする」だけでなく「落ちやすくする」ことで、**orgPop 70+帯の維持コスト**を高める。

### 3.2 下落要因一覧

#### B-1. 年次減衰の強化（orgPop比例）

**現行**: 一律-3/シーズン
**改善**: orgPop帯に応じて減衰量が増える

```javascript
Engine.orgPop.calcAnnualDecay(orgPop) {
  if (orgPop < 30) return 2;    // 弱小はあまり落ちない
  if (orgPop < 50) return 3;    // 中堅は現行と同じ
  if (orgPop < 70) return 5;    // メジャー: 維持が難しくなる
  if (orgPop < 85) return 7;    // トップ: かなり落ちる
  return 10;                     // 覇権: 激しく落ちる
}
```

**設計根拠**: 高人気の団体ほどファンの期待が高く、「普通」では満足されない。現実のプロレス団体でも、トップ団体の凋落は速い（WCWの崩壊、全日本の低迷期など）。

#### B-2. エース引退の団体打撃

エース格（個人人気50+）の選手が引退した際、団体人気にもダメージ。

```javascript
Engine.orgPop.applyAceRetirement(orgPop, retiringFighter) {
  const pop = retiringFighter.popularity || 0;
  if (pop < 50) return 0;   // 中堅以下は団体には影響なし

  // 人気に比例したダメージ
  let damage;
  if (pop >= 80) damage = 8;    // 大エース引退
  else if (pop >= 65) damage = 5;  // 主力引退
  else damage = 3;                  // 準主力引退

  return -damage;
}
```

**発動タイミング**: 引退処理（全4ルート）の直後

| エース人気 | orgPopダメージ | 演出テキスト例 |
|:--------:|:------------:|-------------|
| 80+ | -8 | 「看板選手の引退…団体に大きな衝撃が走る」 |
| 65〜79 | -5 | 「主力の引退がファンに惜しまれる」 |
| 50〜64 | -3 | 「中堅の引退…団体の層が薄くなった」 |

**設計意図**: 高orgPop帯でエース引退が起きると、年次減衰(-7〜-10) + エース引退(-5〜-8) = **1シーズンで-12〜-18の急落**が起こりうる。この「谷」を第二世代で埋め直すのが世代交代の核心。

#### B-3. 不祥事・団体危機（ランダムイベント）

団体レベルのランダム下落イベント。個人のスキャンダルとは別枠。

```javascript
Engine.orgPop.checkOrgCrisis(rng, orgPop, season) {
  // 低人気帯では発生しない（落ちるものがない）
  if (orgPop < 30) return null;

  // 基本確率: シーズン末に5%
  // orgPop 70+で確率上昇（注目度が高い=叩かれやすい）
  let chance = 0.05;
  if (orgPop >= 70) chance = 0.10;
  if (orgPop >= 85) chance = 0.15;

  if (Engine.rng.float(rng) >= chance) return null;

  // ダメージ: -5〜-12
  const damage = -(5 + Engine.rng.int(rng, 0, 7));

  const events = [
    { msg: '📰 週刊誌が団体の内部問題を報道…イメージダウンは避けられない', type: 'scandal' },
    { msg: '🏛️ スポンサー企業が契約を見直し…団体運営に暗雲が立ち込める', type: 'sponsor' },
    { msg: '📺 看板番組の視聴率が低迷…メディア露出が減少している', type: 'media' },
    { msg: '⚡ 選手間のトラブルが表面化…ファンの間に動揺が広がる', type: 'internal' },
  ];

```

| orgPop帯 | 年間発生確率 | ダメージ |

#### B-4. マンネリペナルティ（新メカニクス）

同じ顔ぶれのメインイベントが続くと、ファンが飽きて団体人気が下がる。**世代交代を促す直接的なメカニクス**。

```javascript
// GameStateに追加
// mainEventLog: 直近12興行のメインイベント出場者IDを記録
// [{leftId, rightId, week}, ...]

Engine.orgPop.calcStalenessePenalty(mainEventLog) {
  if (!mainEventLog || mainEventLog.length < 6) return 0;

  // 直近12興行のメイン出場者をカウント
  const recent = mainEventLog.slice(-12);
  const pairCounts = {};
  for (const entry of recent) {
    const key = [entry.leftId, entry.rightId].sort().join('-');
    pairCounts[key] = (pairCounts[key] || 0) + 1;
  }

  // 同一カードが3回以上 → マンネリ
  let penalty = 0;
  for (const [pair, count] of Object.entries(pairCounts)) {
    if (count >= 4) penalty += 2;     // 12回中4回以上: 深刻なマンネリ
    else if (count >= 3) penalty += 1; // 12回中3回: 軽度のマンネリ
  }

  return -Math.min(penalty, 4); // 最大-4
}
```

**適用タイミング**: 興行後のorgPop変動時に加算
**演出**: 「同じ顔ぶれのメインに、ファンからマンネリの声が…」

## §4 施策C: 経済の逓減（economy-rebalance-spec-v5bの補足）

### 4.1 v5bとの関係

economy-rebalance-spec-v5bは**会場単価の逓減**と**変動運営費**を提案している。本設計書はv5bの内容を前提として、**追加で必要な調整**を提案する。

### 4.2 集客計算の調整

**現行の問題**: `(orgPop/100)² × 10000` は二乗カーブで、orgPop 50→70で集客が2倍近くに跳ね上がる。

**提案**: 二乗カーブを**亜線形（平方根混合）**に変更

```javascript
// 現行
const baseAttendance = Math.round((orgPop / 100) * (orgPop / 100) * 10000);

// 提案: 線形と二乗の中間（指数1.5）
const baseAttendance = Math.round(Math.pow(orgPop / 100, 1.5) * 8000);
```

**比較**:

| 10 | 100 | 25 | ↓75% |
| 20 | 400 | 72 | ↓82% |
| 30 | 900 | 131 | ↓85% |
| 40 | 1,600 | 202 | ↓87% |
| 50 | 2,500 | 283 | ↓89% |
| 60 | 3,600 | 372 | ↓90% |
| 70 | 4,900 | 469 | ↓90% |
| 80 | 6,400 | 572 | ↓91% |
| 90 | 8,100 | 683 | ↓92% |
| 100 | 10,000 | 800 | ↓92% |

**→ 激しすぎる**。集客が極端に少なくなり、会場がガラガラになる。

### 4.3 代替案: 二乗カーブを維持しつつ係数を下げる

```javascript
// 提案B: 二乗カーブ維持、係数6000に縮小
const baseAttendance = Math.round((orgPop / 100) * (orgPop / 100) * 6000);
```

| 50 | 2,500 | 1,500 | ↓40% |

一律40%削減。v5bのチケット単価逓減と組み合わせれば、後半ほど利益が圧縮される。

## §5 施策D: 個人人気100の到達困難化

### 5.1 現行の問題

減衰カーブ×0.10（人気80+帯）は存在するが、メイン枠×1.5でrawGainが巨大になり、減衰が効ききらない。

### 5.2 提案: rawGainの圧縮

カード位置補正を**乗算から加算**に変更し、rawGainの上限を下げる。

```javascript
// 現行
rawGain = Math.round(rawGain * slotMult);  // slotMult = 1.5 for main
// → raw+10 が +15 になる

// 提案
rawGain = rawGain + slotBonus;  // slotBonus = +3 for main, +1 for semi
// → raw+10 が +13 になる
```

**比較（MQ80+、勝者、メインイベント）**:

| 項目 | 現行 | 提案 |
|------|:----:|:----:|
| MQベース | +8 | +8 |
| 勝者 | +2 | +2 |
| メイン補正 | ×1.5 = **+15** | +3 = **+13** |
| 人気80帯（×0.10） | **+2** | **+1** |
| 人気50帯（×0.18） | **+3** | **+2** |

### 5.3 提案: 減衰カーブの強化

個人人気80+帯の減衰をさらに強くする選択肢もある。

```javascript
// 現行
if (currentPop >= 80) return 0.10;

// 提案
if (currentPop >= 90) return 0.05;  // 90+は極めて困難
if (currentPop >= 80) return 0.08;  // 80+もより困難に
```

**効果**: 人気80到達は現行より遅い程度だが、**90超えがほぼ不可能**になる。全キャリアを通じて名勝負を連発し続けた伝説級の選手だけが90台に到達。

### 5.4 人気90+の特別感

人気90超えの選手にUI上の特別演出を入れることで、「到達困難だからこそ価値がある」を強調。

- 人気80+: ★★★★ アイコン（現行と同様）
- 人気90+: 🏆 **「レジェンド」ラベル** + 金色の名前表示
- 人気95+: 💎 **「殿堂級」ラベル** + 専用エフェクト

## §6 施策E: Heatの維持困難化

### 6.1 現行の問題

Heat値域が-10〜+10と狭く、MQ75+の安定供給でOn Fire(+10)に張り付く。

### 6.2 提案: Heat上限帯の減衰

Heat値が高いほど上がりにくくする。orgPopと同じ思想。

```javascript
Engine.heat.calcUpdate(G, avgMQ) {
  let rawDelta = avgMQ >= 75 ? 2 : avgMQ >= 60 ? 1 : avgMQ >= 40 ? 0 : avgMQ >= 25 ? -1 : -2;

  // 新規: Heat上限帯の減衰
  if (rawDelta > 0 && G.heatScore >= 6) {
    rawDelta *= 0.5; // HOT以上では上昇量半減
  }

  // 慣性補正（現行通り）
  if (G.heatScore > 0 && rawDelta <= 0) rawDelta -= 0.5;
  if (G.heatScore < 0 && rawDelta >= 0) rawDelta += 0.5;

  return Engine.util.clamp(
    Math.round((G.heatScore + rawDelta) * 10) / 10, -10, 10
  );
}
```

**効果**: On Fire(+10)への到達には、MQ75+を10興行以上連続で出す必要がある。「一時的な爆発」は可能だが「維持」は困難。

### 6.3 提案: 非興行週のdecay強化

```javascript
// 現行: 0方向に-1.0
// 提案: Heat高いほど速く冷める
Engine.heat.calcDecay(G) {
  let hs = G.heatScore;
  const decayRate = Math.abs(hs) >= 6 ? 1.5 : 1.0; // HOT以上は冷めやすい
  if (hs > 0) hs = Math.max(0, hs - decayRate);
  else if (hs < 0) hs = Math.min(0, hs + decayRate);
  return Math.round(hs * 10) / 10;
}
```

1. **orgPop 100は到達可能にすべきか？**
   - ✅ **到達可能**。ただし到達しても維持は困難な設計にする。「到達できるが、すぐ下がる」が正解。到達そのものを不可能にする必要はない。

2. **難易度選択を設けるか？**
   - ✅ **難易度選択は設けない**。1本の難易度で勝負する。プレイヤー全員が同じ条件。
