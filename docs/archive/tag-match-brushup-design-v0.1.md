## 0. このドキュメントの位置づけ

シングルマッチに比べて見劣りしているタッグマッチ演出・文言の**5つの課題**を整理し、実装方針・タスク分解・完了条件を明記する。**ユーザー運用ルールに従い、このドキュメントでは設計と方針のみを定め、実装はClaude Codeセッションで行う。**

タスク間に依存関係があるため、後半の「実装順序」を必ず先に読むこと。

## 2. 課題別仕様

### T1. ダブルチーム攻撃のバリエーション追加

#### 現状
`src/tag-battle-lines.js` に `DOUBLE_TEAM_LINES`（21件程度）は存在するが、**技名のバリエーション自体が少ない**。現行のダブルチーム攻撃はパターンが限定的で、試合を通して似た技が繰り返される。

#### 要件
- ダブルチーム**技の種類**を増やす（最低でも現在の2-3倍、目標10種類以上）
- 各技に対応する演出セリフ・実況文を `DOUBLE_TEAM_LINES` に追加
- 技のカテゴリ分け（例: 打撃系コンビ / 投げ系コンビ / 関節系コンビ / フィニッシュ系コンビ）
- トリガー条件（スタミナ、タッグ経験値、信頼度など）との紐づけがあれば拡張

#### 実装ポイント
- まず `tag-battle-main.js` の現行ダブルチーム発動ロジックを確認し、技名配列がどこに定義されているか特定
- 技名リストとセリフリストの紐づけ方式を決める（ID指定 / ランダム選択 / カテゴリ選択）
- `tag-battle-lines.js` 拡張時はExcel連携を見据え、命名規則を `DOUBLE_TEAM_*_LINES` のように分解可能にしておく

#### 完了条件
- 1試合中に同じダブルチーム技が連続で出ない
- 実況セリフと技名が自然に噛み合う
- auto-sim で例外が出ない

---

### T2. 試合完了時の締めセリフ

#### 現状
タッグ試合が終わった瞬間の「選手の一言」「実況の締めセリフ」が不足、または単調。シングルでは勝利演出がしっかりあるのに、タッグだと余韻なく終わる。

#### 要件
以下3種類のセリフを用意:
- **勝利チームのコメント**（パートナーへの言及を含むのが必須）
    - 例: 「{partnerName}と組んで勝てた。ありがとう」
    - 例: 「やっぱりウチらが最強のタッグってことよ」
- **敗北チームのコメント**（責任論 / 次への意欲 / パートナーへの詫び）
    - 例: 「{partnerName}、ごめん。わたしが決められてたら…」
- **実況の締め**（勝者名＋決め技＋タッグ関連の言及）
    - 例: 「{winnerName}組、見事なコンビネーションで勝利！」

#### データ構造案
```javascript
// tag-battle-lines.js 内
const TAG_MATCH_WIN_LINES = {
  // パートナーへの感謝系
  partner_thanks: [...],
  // 単独自慢系
  solo_proud: [...],
  // クール系
  cool_minimal: [...],
};
const TAG_MATCH_LOSS_LINES = {
  apology_to_partner: [...],
  self_blame: [...],
  next_time: [...],
};
const TAG_MATCH_COMMENTARY_WIN = [...]; // 実況締め勝利側
```

- 性格×属性のマトリクスに乗せるか、単純配列にするかは件数次第で判断
- `{partnerName}` プレースホルダを確実に扱えるように

#### 完了条件
- 勝者・敗者・実況の3種が連動して表示される
- パートナー名が正しく埋め込まれる
- 性格/属性に応じた文体（既存セリフ系の流儀）

---

### T3. 丸め込み演出の主体明示

#### 現状
`tag-battle-main.js` L853 で `seq.push({ kind: 'count', text: 'なんと！丸め込みだーっ！', cls: 'rollupIntro' })` とあり、**誰が誰を押さえ込んだのかが文言・UIのどちらからも読み取れない**。

#### 要件
- 「丸めこみだーっ！」の前後に、**押さえ込んだ側（defender → 一転攻勢の側）と押さえ込まれた側（元の攻撃側）** を明示
- 表示要素:
    - `{rollupSide}選手が{opponentSide}選手を丸め込んだ！`
    - もしくはUI上で矢印・ハイライトで方向を示す
- 3カウント中も「{rollupSide}が押さえ込んでいる！」の状態表示を継続

#### 実装ポイント
- `tag-battle-main.js` L850-870 周辺のピン演出シーケンスを拡張
- `seq` に `rollupSubject` / `rollupObject` のようなメタ情報を持たせる
- 該当UI（`tag-battle.html` のピンカウント表示エリア）で主体名をレンダリング

#### 完了条件
- 丸め込み発生時、押さえ込み主体と対象がテキスト／ビジュアル両方で即座に判別可能
- シングルの同種演出（match-engine.js 側）との一貫性が取れている

---

### T4. カウント・決着寸前の表記統一

#### 現状
- カウント演出の**文言がシングルと違う**（ワン/ツー/スリー の出し方が別実装）
- **クリックで促進する仕組み**がシングルと違う、もしくは存在しない
- プレイヤーの操作感覚が試合ごとに変わる

#### 要件
- シングルマッチの「カウント」「ギブアップ寸前（ロック／極まっている／タップorエスケープ）」の表記・演出ルールに**完全準拠**
- クリック操作の仕様も揃える（進行速度・促進効果・演出）

#### 実装ポイント
- **まずシングル側の現行仕様を棚卸し**（`match-engine.js` + 関連UI部分）
- 抽象化できるなら共通関数化を検討（ただし影響範囲が大きいため、**今回は「タッグ側をシングルに揃える」に限定**）
- 両側のカウント関連文言・クラス名・クリックハンドラを比較し、差分を潰す

#### 完了条件
- 同じ状況（ピンカウント / ギブアップ寸前）でシングルとタッグの**文言・UI・操作感**が一致
- ピンカウント中のクリック効果も同一

### T5. 攻撃方向・カウンター演出の視覚化

#### 現状
攻撃者→被攻撃者の方向、カウンター成立時の切り返しが文字だけで表示される。**どっちがどっちに何をしたのか、一瞬では読めない**。

#### 要件

##### (A) 通常攻撃時
- 攻撃者側から被攻撃者側へ**矢印**または**方向性のあるアニメーション**
- 矢印の向き: 左→右 または 右→左（選手の配置に応じて）
- 技名テキストがこの矢印と連動して流れる

##### (B) カウンター発動時（**最重要**）
二段階の演出:

**段階1（元の攻撃）**
- 攻撃者A → 被攻撃者B へ右向き矢印
- 元の技名「{techA}！」をその矢印と共に表示
- 一瞬で画面に入る

**段階2（カウンター返し）**
- 矢印が**逆転**（左向き）でドーン！と入る
- カウンター技「{techB}でカウンター！」を逆向き矢印と共に表示
- 段階1の矢印より目立つエフェクト（サイズ大、フラッシュ等）

この二段階構成により、「攻撃→返し」の関係が視覚的に理解できる。

#### 実装ポイント
- **CSSアニメーション中心の実装**（パフォーマンス・メンテナンス性）
- HTML構造:
    - 既存の演出ログ領域に矢印要素を追加
    - または独立した「演出ビューア」レイヤーを新設
- アニメーション方向制御:
    - CSSクラス `.arrow-left-to-right`, `.arrow-right-to-left` で切り替え
    - カウンター時は既存演出の直後に `.counter-reversal` クラスで上書き
- 段階1と段階2の間に短い間（100-200ms）を挟むと見やすい

#### UIモックアップ方針
実装前に `archive/prototype/` に**モックアップHTMLを作成**し、動きを確認してから本実装へ進むのが安全。既存の `archive/prototype/battle-effects-mockup.html` があれば参考になる。

#### 完了条件
- 通常攻撃で方向性が視覚的に判別できる
- カウンター発動時、段階1→段階2の流れが明瞭
- シングルマッチにも同じ演出を展開できる汎用的な実装（将来の統一を見据える）

## 3. 実装順序と依存関係

```
┌─ T4: カウント統一 (シングル仕様の棚卸しが必要)
│      ↓ ここで UI 基盤の仕様がハッキリする
├─ T3: 丸め込み主体明示 (T4 の棚卸し結果を使うとスムーズ)
│      ↓
├─ T5: 矢印演出 (モックアップHTML → 本実装) ← 最重要かつ工数大
│      ↓ 演出系の基盤ができてから文言拡充
├─ T1: ダブルチーム追加 (技名 + 演出 + セリフ)
└─ T2: 締めセリフ (単独タスクなので並行可能)
```

**推奨順序: T4 → T3 → T5 → T1 → T2**

T5が最大の工数だが、ここで作った矢印演出は T3 の丸め込み主体表示にも流用できるため、T5 の設計段階で T3 の要件も考慮すると二度手間を防げる。

## 4. 注意事項

### タッグマッチのステータス
- **現在プロト段階**（v0.1 spec）。本実装入りは未確定
- レッスルマネージャー本編の次期バージョンで正式採用の可能性あり
- **シングル側に影響を与えない変更範囲に留める**（共通化は後日の別タスク）

### Excel 連携との兼ね合い
- `tag-battle-lines.js` の定数拡充は、将来 `dialogue-all-tag-battle.xlsx`（引き継ぎ書類 残作業C）に展開する前提
- **新規定数は `XXX_LINES` 命名規則に揃える**（独立定数として分離可能に）
- 大きなオブジェクト（`EVENT_QUOTES` の前例）を作らないこと

### 動作確認
- タッグマッチは `src/tag-battle.html` を直接開くと独立動作する
- `test/` 配下に auto-sim はないため、目視確認が中心
- シングルとの一貫性確認は両方を開き比べる

### 既存シングル側のリファクタ提案
T4 でシングル側の実装を棚卸しした結果、**共通化した方が保守性が上がる**と判明した場合は、**別タスクとして提案**すること。今回のスコープには含めない。
