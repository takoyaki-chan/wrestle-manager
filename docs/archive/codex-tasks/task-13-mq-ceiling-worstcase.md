## 背景

「MQの上限100がはみ出した分を押し込めているのではないか」という問題意識に対し、task-11 の実測では **最終MQが100を超えた試合は 0/6,812件、観測最大は96、外部キャップ+12への到達も0件**だった。

**しかしこの計測には穴がある。**auto-sim の自動プレイでは **タイトルマッチが1件も発生しなかった**（レポート §「タイトル・2種マイルストーン・ラストランはこの自動プレイでは一度も発動しなかった。コード到達不能という意味ではなく、auto-simのカード/イベント選択が経路を覆っていない」）。

つまり **MQが最も高くなる条件の組み合わせが検証範囲に入っていない。**本タスクはそこを狙い撃ちで測り、当初の問いに正面から答える。

## 計測内容

### ① 最悪ケース（＝最高MQケース）の構成

MQを押し上げる要素を意図的に重ねたカードを人工的に構成し、最終MQを測る。

重ねるべき要素（`docs/mq-inventory-report.md` の §1 を参照して、MQに正方向で効く全要素を洗い出すこと）:

- **高OVR同士の対戦**（OVシーリングを最大化。avgOV 95〜100 の帯を含めること）
- **タイトルマッチ**
- **因縁**（最大値の帯。好敵手/宿怨を含む）
- **超満員 / 最上位会場**
- **ドラマ減点が最小になる展開**（キックアウト・カウンター・逆転・大技が多い試合。乱数を振って上位の試合を拾えばよい）
- **Climax決着**（決着減点0）
- レポートで正方向に効くと判明したその他の要素（マイルストーン、ラストラン、コーチ等）

**組み合わせは網羅せず、「積めるだけ積んだ構成」を作ることが目的。**理論上の最大値に迫る構成を人工的に作り、そこで何が起きるかを見る。

### ② 両方の経路で測ること（必須）

task-11 の最重要発見は、**MQの確定経路が2本あり結果が一致しない**ことである。

| 経路 | 特徴 |
|---|---|
| `App._finalizeShowImpl` | プレイヤーが画面から興行を見る本番経路。**各段階で100にクランプする**。+12キャップ・trustペナルティ・マイルストーン加算・ラストラン加算は**ない** |
| `Engine.executeShow` | headless / auto-sim / AI興行 / PPV / 天頂戦。**上限クランプなし**。+12キャップ等は**ある** |

**両経路で同じ構成を通し、結果を並べて報告すること。**task-11 が `test/auto-sim.js` に追加した「画面経路の非接続再構成」を流用してよい（ただしそれはコード順序の再現値であり、DOM/UIを実行した値ではない点を報告に明記すること）。

### ③ 報告してほしい数値

各経路・各構成について:

- **最終MQの分布**（平均・中央値・最大・99パーセンタイル）
- **100を超えた試合の割合**と、超えた場合の**超過量の分布**（平均・最大）
- **外部キャップ（+12）に到達した割合**と、切り捨てられた量
- **クランプ前の素点＋補正の合計**（＝もし上限が無ければいくつだったか）
- 各要素の寄与内訳（どの要素がどれだけ積み上がったか）

### ④ 併せて確認してほしいこと

- **上限に到達しうる構成が実在するのか、それとも理論上も100に届かないのか。**後者なら「上限撤廃は無意味」という結論になり、再設計の論点が1つ減る
- タッグマッチ（`5〜100` にクランプされる唯一の経路）でも同様に測ること
- **プレイヤーが現実に組みうるカードで到達するのか、それとも人工的に積まないと到達しないのか**についての所見
