## A. 静的棚卸し（コードを読んで書き出す）

MQ に影響を与えるすべての要素を、**計算順序どおりに**列挙する。各要素について:

- 実装箇所（`ファイル:行`）
- 何を入力に、どういう式で、いくら動かすか
- 取りうる値の範囲（最小・最大）
- 発動条件

判明している出発点（これで全部とは限らない。**自分で走査して漏れを探すこと**）:

1. **素点（OVシーリング）** — `match-engine.js`。avgOV から天井を算出
2. **ドラマ減点** — 基本-30 を KO / カウンター / 逆転 / 大技で回復
3. **ペーシング減点** — Tier別の下限。特性「引き出し上手」で緩和
4. **決着減点** — `finishPhase` 連動（Climax=0 / End=1 / 他=3）、技種別
5. **エンジン側のクランプ** — `mq = Math.max(5, Math.round(mq))`
6. **外部ボーナス** — `management.js`（`r.mq = ...` の各所、L11399 / L11456 付近）。因縁・タイトル・コーチ・超満員/大入り・会場。**キャップ +15**
7. **タイトルマッチ格差ペナルティ** — キャップ後に別途減算
8. **trust 由来のMQペナルティ** — `trustMQPenalty`
9. **特性による効果** — 「名勝負製造機」「引き出し上手」ほか。**MQに触る特性を全部洗い出すこと**

### 特に確認してほしい食い違い

`docs/design-decisions.md` は MQ を **`clamp(15, 100)`** と記録しているが、`match-engine.js` の実装は **`Math.max(5, ...)`** である。**下限が 15 なのか 5 なのか、上限 100 のクランプが実際どこで行われているのかを特定すること。**

同様の「ドキュメントと実装の食い違い」が他にもある可能性が高い（2026-07-20 にペーシング減点で1件発覚済み）。**見つけたらすべて報告書に列挙すること。**

## B. 実測寄与（各要素が実際にどれだけ効いているか）

`node test/auto-sim.js 100 42` 相当の規模で計測する。

エンジン側は `matchResult.mqDetail`（`ceiling` / `dramaPenalty` / `pacingPenalty` / `finishPenalty`）が既に返り値に含まれているため、**`match-engine.js` を変更せずに取得できる。**

### 報告してほしい統計

各要素について:

- 平均値・中央値・標準偏差
- **発動率**（0でない値を取った試合の割合）
- 最終MQへの寄与の大きさ順ランキング

### 最重要: 死んでいる要素・効きすぎている要素の特定

- **一度も発動しなかった要素**
- **ほぼ常に同じ値を取る要素**（実質的に定数になっており、差を生んでいない）
- **キャップに張り付いている要素**（外部ボーナスの +15 キャップに何%の試合が到達しているか）
- **想定より桁違いに効いている要素**

2026-07-20 にペーシング減点が「試合長が変わって機能停止していた」ことが判明した実例がある。**同種の死んでいる項目が他にもある前提で探すこと。**

## D. 下流への波及範囲
