# 目的

ゲーム制作の一般原則を、権威による命令ではなく設計ミスを発見する判断ゲートとして使う。

# 優先順位

1. ユーザーの最新の明示指示
2. プロジェクト固有方針
3. 既存仕様・コード・データ・制作制約
4. プレイテスト・実際の操作・測定結果
5. このスキルの原則

桜井氏の考え方を絶対的な正解として扱わない。

# 毎回の進め方

1. タスクをゲームループ、UI、演出、実装、プレイテスト、広報に分類する。
2. 守る既存方針と競合の有無を確認する。
3. 最小の安全な変更、または比較可能な少数案を出す。
4. 実物、画面、ログ、テスト、プレイ結果で検証する。
5. 提案を「採用・一部採用・今回は不採用」で分類する。

# 中核原則

## プレイヤー体験

- プレイヤーの時間を無駄にしない。
- 入力、決定、技、数値変化を無反応にしない。
- 直近の目標、進捗、報酬を見えるようにする。
- CPUや内部処理を理不尽に見せない。
- 意図的な間と単なる遅さを区別する。
- 面白い部分を後半まで出し惜しみしない。
- チュートリアルは必要な瞬間に実際のプレイの中で教える。
- 色だけに意味を持たせず、文字、操作、点滅等へ配慮する。

## ゲーム設計

- ゲームの核を先に成立させ、小さく遊べる形で検証する。
- リスク、リターン、報酬、失敗の重さを釣り合わせる。
- 反復には変化、上達、判断、利益のいずれかを持たせる。
- 開発者の想定解だけを強制せず、複数の戦略を許す。
- ランダム性は変化に使い、確率・前兆・対処・保険で納得感を保つ。
- キャラクター性を数値、挙動、選択、勝ち方、負け方へ反映する。
- 管理作業を題材、利益、次の判断へ結びつける。
- 評価値は意味と改善方向を理解できる形で示す。
- 進行に停滞、飛躍、危機、回復などの波を作る。
- 守る核と変える部分を分ける。

## UI

- 読みやすさと世界観を両立する。
- 色の役割を一貫させる。
- 重要な項目ほど位置、大きさ、余白、太さで見つけやすくする。
- ヘルプは用語の言い換えでなく、影響を平易に説明する。
- 情報は消す前に、階層、配置、縮小、履歴、強調で整理する。
- 結果の理由を後から確認できる履歴を残す。
- 処理中、保存中、読込中を明示する。
- 頻繁な操作にはショートカットを検討する。
- 破壊的操作だけ確認を厚くする。

## 演出・手触り

- 輪郭だけでも攻守、向き、行動を読めるようにする。
- 命中、成功、失敗を即座に識別できるようにする。
- 決定的な衝撃に時間的アクセントを置く。
- エフェクトで人物や重要情報を隠さない。
- 音の強さと余韻を出来事の重要度に合わせる。
- 一般的なスピーカー、小音量でも確認する。
- 画風、色、陰影、素材感の規則を統一する。
- 人物や重要物を背景に埋もれさせない。
- 素材単体でなく、ゲームに組み込んだ最終画面で評価する。
- 入力、表示、処理遅延を体験上の問題として扱う。
- 写実性を目的化せず、理解と迫力のための省略・誇張を許す。

## 開発運用

- 問題に気づいたら早く共有し、可能なら修正案も添える。
- 完璧な確信待ちで止めず、必要なら後で修正する。
- 文章だけで考え続けず、まず動くものを作る。
- 調整数値をコードから分離する。
- 特定状態を即時再現できるデバッグ経路を用意する。
- 実装前に「何を変えるか、なぜ、何を守るか、完了条件」を共有する。
- 初期は細部で止まらず形にし、後で検証する。
- 追加だけでなく、核でない機能を削る。
- コンセプトの幹を明示的な判断なしに変えない。
- ファイル名・データ名を一貫させる。
- 一般的な操作・表記を学習コスト低減に使う。

## 広報

広報タスクのときだけ適用する。

- 説明より先に、核のゲーム体験を見せる。
- 最新情報へ辿れる基準ページを一つ持つ。
- 体験版、実演、プレイ動画を重視する。
- 開発者が継続的に直接伝える。
- 市場データは参考にするが、企画の決定権にはしない。

# 禁止事項

- プロジェクト固有方針を一般論で上書きしない。
- 全原則を毎回機械的に適用しない。
- アクションゲーム固有技法を別ジャンルへ無理に移植しない。
- HUDを少なくすること自体を目的にしない。
- 初心者向けを理由に、ゲームの深さや個性を安易に削らない。
- 「遅さは悪」と一括せず、演出上の溜めと無意味な待ちを分ける。
- 桜井氏の発言として、確認していない文言を引用しない。

# 最終報告

- 判断: 採用 / 一部採用 / 今回は不採用
- 適用した原則
- 守ったプロジェクト固有方針
- 理由
- 例外・副作用
- 確認方法と結果
- 確信度: 高 / 中 / 低
