```
ドーム到達マイルストーンイベント（first_dome_show / first_dome_sellout）を
feature/dome-milestone ブランチで実装してほしい。

### 最初に必ず読むこと（この順序で）
1. CLAUDE.md
2. specs/dome-milestone-spec-v0.3.md ← 今回の仕様（最重要・精読）
3. plans/dome-milestone-task.md ← ステップ単位の実装指示書（精読）
4. docs/ui/mockups/mockup-dome-milestone-v0.6.html ← 確定UI（CSS/JS構造の参考）
5. specs/dome-milestone-dialogues-v0.1.js ← 294行のダイアログ辞書（data.js にそのまま組み込み）

### 絶対ルール
- plans/dome-milestone-task.md の「実装手順」ステップ1〜11の順序で進めること
- 「触ってはいけない既存コード」セクションに挙げたファイル・CSS・関数は一切変更しない

- BGM 制御は既存の Audio.fileBgm API を使用（独自実装しない）

### 実装の核心（要約）
- 新 D層（演出イベント）カテゴリ：選択肢なし・報酬なし・セレモニー演出のみ
- 2イベント：興行前 first_dome_show / 興行後 first_dome_sellout
- 興行前フックは新機構（既存マイルストーンは post-show のみ）
- 新規汎用関数 showCeremonyEvent を作成（今後の殿堂入りなどでも共用基盤）
- ダイアログ辞書は 7 personality × 7 archetype × 3 lines × 2 events = 294行
- BGM：興行前 bgm_kaimaku_v1.mp3 / 興行後 8bit-ending-theme_Loop.ogg

### 完了の定義
plans/dome-milestone-task.md 末尾の「完了チェックリスト」11項目すべて ✅。
特に動作確認シナリオ5件は手動テストで必ず通すこと：
- 初ドーム興行・不入り（興行前のみ発火）
- 初ドーム興行・超満員（興行前+興行後 連続発火）
- 2回目ドーム興行・初の超満員（興行後のみ発火）
- 3回目ドーム興行・超満員・過去達成済み（何も起きない）
- メイン2名がロスターpop上位の場合（ベテラン代表はpop3位）

### 作業開始前の宣言
実装に入る前に、以下を口頭で宣言してから着手してほしい：
1. 仕様書とタスクファイルを読み終えたこと
2. 特に不明瞭な点・矛盾・追加判断が必要な点があるか
3. 既存コードで触れる予定のファイル一覧（grep で確認した結果）

着手前に Keisuke の確認を挟みたい重要判断があれば、ここで列挙すること。

では開始してください。
```

## 📝 プロンプト設計の意図

**短く、ファイル参照を主軸に**：
- タスクの詳細は全部 `plans/dome-milestone-task.md` に書いてあるため、ここに再掲しない
- 長文で手順を繰り返すと「指示プロンプトとタスクファイルの齟齬」が発生しやすい
- Claude Code は「必ず読むこと」と書かれたファイルを優先して読む傾向があるので、順序指定が効く

**「絶対ルール」を列挙**：
- 仕様書を逸脱しやすいポイント（RNG 決定論化、BGM API、勝手に推測しない）を先に釘を刺す
- コミット戦略も明示してコミット粒度のブレを抑制

**「作業開始前の宣言」を要求**：
- 実装に入る前に必ず仕様理解を確認する step を入れる
- 不明瞭な点を早期に洗い出すことで、的外れな実装になる前に軌道修正できる
- このパターンは過去にも有効だったはず（Keisuke が「一番いいようにやれよ」と言ったときに Claude Code が勝手な推測で進まないためのガード）

**完了の定義を明確に**：
- タスクファイルの「完了チェックリスト」への参照だけで十分
- 動作確認シナリオ5件は一番重要なので再掲した

## 🚨 避けるべきプロンプトパターン

参考までに、こういう書き方はしない方がいい：

- ❌ 「ドームイベントを実装して」だけ投げる（情報不足で Claude Code が想像で埋める）
- ❌ 仕様書の内容を全部プロンプトに書く（タスクファイルと重複し齟齬の原因）
- ❌ 「いい感じで」「よしなに」（判断軸が曖昧、勝手な推測を誘発）
- ❌ 複数の目的を一つのプロンプトに混ぜる（実装+リファクタ+ドキュメント更新を同時に頼むなど）
