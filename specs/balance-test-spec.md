## 問題一覧と原因分析

### ❶ HEAT上がりっぱなし

**症状**: HEATが一度上がると下がらず、On Fire(2.0倍)に張り付く

**原因**: 減少要因が増加要因に全く追いついていない

| 増加要因 | 量 | 頻度 |
|----------|:--:|------|
| 興行MQ75+ | +2 | 隔週（毎興行） |
| 興行MQ60+ | +1 | 隔週 |
| 超満員 | +2 | 隔週 |
| 大入り | +1 | 隔週 |
| フレーバーTV出演 | +2〜3 | 12%/週 |

| 減少要因 | 量 | 頻度 |
|----------|:--:|------|
| 非興行週decay | **-0.3** | 隔週 |
| 低MQ(<25) | -2 | まず起きない |
| ガラガラ | -2 | 中盤以降は起きない |

**計算例**: 普通にプレイするだけで毎興行+3程度、decayは-0.3。週あたりnet +1.35。7週で-10→+10に到達し、以降下がらない。

**コード箇所**: `engine.js` lines 541-552（heat.calcUpdate / calcDecay）

**対策案**:
- decay を -0.3 → -1.0〜-1.5 に引き上げ
- On Fireの維持が難しくなるよう、高HEAT帯で追加decayを入れる
- 超満員のheat+2は過剰（集客計算にheatが乗ってるので正のフィードバックループ）→ +1に下げるか廃止
- フレーバーTVのheat+2〜3も過剰 → +1に下げる

### ❷ 経済バランス崩壊（中盤以降無限黒字・17,129万円）

**症状**: 序盤を抜けると何も考えず次を押すだけで圧倒的黒字

**原因**: 収入バフが**掛け算で重複**している + パッシブ収入が膨大

#### 集客への掛け算スタック
```
rawAttendance = (baseAttendance + cardBonus) 
  × heatMult(最大2.0) 
  × titleMult(1.15) 
  × champMult(1.10) 
  × charismaMult(1.05)
```
**最大乗数: 2.0 × 1.15 × 1.10 × 1.05 = 2.66倍**

さらにチケット収入に occupancy ticketMult(最大1.5) が乗る:
```
ticketRev = attendance × 0.5万 × ticketMult(最大1.5)
```
**実質最大: 2.66 × 1.5 = 3.99倍**

#### パッシブ収入（毎週・興行の有無にかかわらず）
| orgPop | スポンサー | 放映権 | 合計/週 | 年間（48週） |
|:------:|:----------:|:------:|:-------:|:----------:|
| 60 | 120 | 0 | 120万 | 5,760万 |
| 80 | 250 | 100 | 350万 | 16,800万 |
| 95 | 400 | 400 | 800万 | **38,400万** |

orgPop 95で **パッシブだけで年3.8億**。

#### 支出が安すぎる
| OVR帯 | 給料/週 | 10人の年間人件費 |
|:------:|:-------:|:---------------:|
| 65-79 | 35万 | 16,800万 |
| 80-89 | 60万 | 28,800万 |
| 90-99 | 100万 | 48,000万 |

固定費: 施設30 + 事務20 = 50万/週 = 2,400万/年

**コード箇所**: 
- `engine.js` lines 496-512（calcAttendance — 掛け算スタック）
- `data.js` lines 559-562（SALARY_TABLE）
- `data.js` lines 616-623（SPONSOR_TABLE / BROADCAST_TABLE / FIXED_COSTS）
- `data.js` lines 574-582（OCCUPANCY_BONUS — ticketMult 1.5）

**対策案**:
- 掛け算スタックを**加算方式**に変更するか、上限キャップを設ける
  - 例: totalMult = min(1.0 + (heat-1) + titleBonus + champBonus + charismaBonus, 2.0)
- SALARY_TABLE を大幅引き上げ（OVR80: 60→120、OVR90: 100→250 等）
- スポンサー/放映権テーブルを縮小、または維持費・税金を導入
- 高orgPop帯でスキャンダル・不祥事の発生率UP等のマイナスイベント追加検討
- occupancy ticketMultの超満員1.5→1.2に緩和

### ❸ 給料がバカ安（能力値が上がっても安い）

**症状**: OVR80台の一流選手でも60万/週。稼ぎに対して人件費が誤差レベル。

**原因**: SALARY_TABLE がゲーム経済のスケールに合っていない

**現行テーブル** (`data.js` line 559):
```javascript
const SALARY_TABLE = [
  {max:49, pay:8}, {max:64, pay:18}, {max:79, pay:35}, {max:89, pay:60},
  {max:99, pay:100}, {max:109, pay:150}, {max:999, pay:200}
];
```

**対策案**: 全体を2〜4倍にスケールアップ
```javascript
// 例（要テストプレイで調整）
const SALARY_TABLE = [
  {max:49, pay:15}, {max:64, pay:40}, {max:79, pay:80}, {max:89, pay:150},
  {max:99, pay:250}, {max:109, pay:400}, {max:999, pay:600}
];
```

これで10人OVR80台チームの人件費は 150×10 = 1,500万/週 = 72,000万/年。収入とぶつかるレベルになる。

### ❹ プラス要素が多すぎてマイナスがない

**症状**: 人気もヒートもorgPopも全部上がり続け、下がる要因がほぼない

**具体例**:
- 人気: プロモ、試合勝利、フレーバーイベント、タイトル獲得 → 全部+
- 人気下落: スキャンダルのみ（低確率）
- orgPop: ランキング経由で上昇 → 下がる仕組みが弱い
- ヒート: ❶の通り上がりっぱなし

**対策案**:
- 人気の自然減衰（毎週-0.5等、試合に出ないとさらに-1）
- ヒートの自然減衰強化（❶と連動）
- 連敗ペナルティの強化
- 「飽きられる」メカニズム（同じカード連続で人気down）
- orgPopにも軽いdecay（年間-3〜-5程度）

### ❺ FAの20歳以上が引退していない

**症状**: フリーエージェントにいつまでも選手が残っている

**原因**: dormantPool → FA変換時に年齢がリセットされる

`engine.js` line 2258:
```javascript
const fighter = Engine.rival.makeAIFighter(template, faRng, null, 18 + Engine.rng.int(faRng, 0, 6));
```

dormantPoolのキャラがFAに入る際、**毎回18〜24歳で新規作成**される。
さらにFA月次ローテーション（4週ごと）でFAから外れた選手はdormantPoolにID化して戻る。
次にpoolからFAに入るときまた18〜24歳で作り直し。

つまり**同じキャラがdormant⇔FAを行き来しながら永遠に若返り続ける**。

**対策案**:
- dormantPool をIDだけでなく年齢も保持するか、キャラの初期年齢を記録して使う
- または: dormantPool再入場時に前回の年齢を引き継ぐ（FAオブジェクトをそのまま保管）
- または: dormantPoolに対しても年次エージングを適用
