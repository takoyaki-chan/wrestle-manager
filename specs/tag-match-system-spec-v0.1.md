## 1. 設計方針

### 1.1 基本思想

- 既存シングルエンジンの**データ層・評価層**は流用する（選手能力値、関係性データ、コンディション等）
- 試合の**進行層・構造層**はタッグ専用に新規設計する
- タッグの醍醐味（タッチ攻防、孤立、ホットタグ、連携）をシステムの判定から自然に生成する
- 手間は度外視。タッグとして成立する品質を最優先する

**数値設計原則（全体に適用）：**
- **全て線形傾斜。段階式にしない。** 例えば「bond 50〜80は同じ効果」のような閾値方式は禁止。全ての値が1刻みで意味を持つ
- **能力値が高いことが不利に働く設計を作らない。** 特にMNT
- **影響度の大きさには論理的な優先順位をつける。** 例：介入成功率ではHP（体が動くか）＞ bond（気持ち）

### 1.2 プレイヤーの役割

- **プレイヤーが操作できるのは「誰と誰を組ませるか」の編成のみ**
- 試合が始まったら一切介入できない。完全自動シミュレーション
- タッチのタイミング、介入の判断、全て選手のスタッツ・HP・ケミストリーから自動で決まる
- これはシングルマッチと同じ設計思想であり、WMの根幹原則
- プレイヤーチームもNPCチームも同一のロジックで処理される（AI統一原則）

### 1.3 既存システムからの流用

| 項目 | 流用方法 |
|------|---------|
| 選手能力値（OVR, PWR/SPD/TEC/STA/MNT） | そのまま使用 |
| フィニッシャーデータ（技名、威力、カテゴリ） | そのまま使用。タッグフィニッシャーは新規追加 |
| 関係性データ（bond/rivalry） | ケミストリー算出に使用 |
| コンディション | 試合前の状態として共通 |
| MQの概念 | 算出ロジックはタッグ用に再設計 |
| personality / archetype | セリフ・演出で使用 |
| スタイル（fighting style） | スタイル相性テーブルで使用 |

### 1.4 タッグ用に新規設計するもの

- ポジション管理（リーガルマン / エプロン）
- セグメント構造（タッチによる区切り）
- タッチロジック（4種のタッチ + 判定分離）
- エプロン行動（回復・介入）
- ケミストリー（bond + タッグ経験 + スタイル相性）
- ドラマイベント（条件付き発生）
- タッグMQ算出
- 勝敗帰属（誰がフォール勝ち/負けしたか）
- 試合後イベント接続（ドラマイベント → 関係性変動）

## 2. 試合進行構造

### 2.1 セグメント

タッグマッチの試合は**セグメント**という単位で区切られる。

**セグメント ＝ 同じリーガルマン同士が戦っている区間**

```
セグメント1: A vs C （開始）
  ↓ タッチ発生
セグメント2: A vs D
  ↓ タッチ発生
セグメント3: B vs D
  ↓ ドラマイベント発生（ホットタグ等）
セグメント4: A vs D （爆発展開）
  ↓
  …決着
```

**セグメントは固定数ではない。** セグメントの長さ（内部ターン数）もセグメントの総数も揺らぐ。タッチが起きる条件が満たされたらそこで区切りが生まれ、決着条件が満たされたら試合が終わる。

- 序盤の探り合い → 短いセグメントでタッチが回る
- 中盤の孤立展開 → 長いセグメントが発生
- 終盤の攻防 → ドラマイベントを挟んで決着へ

結果として、短い試合なら4〜5セグメント、名勝負なら10以上になる。

### 2.2 ターン処理フロー

各セグメント内はターンの繰り返しで進行する。

```
ターン開始
  ├─ 1. リーガルマン攻防判定 → ダメージ処理
  ├─ 2. エプロン回復（自動・確定）
  ├─ 3. エプロン介入判定（条件付き）
  ├─ 4. タッチ判定
  │    ├─「タッチしたい」判定（HP閾値・ターン経過）
  │    └─「タッチできる」判定（スタッツ比較・阻止判定）
  │         ├─ 成功 → セグメント遷移（リーガルマン交代）
  │         └─ 失敗 → 孤立カウント加算
  └─ 5. 決着判定
       ├─ フィニッシャー成功 → カットイン判定
       │    ├─ カットイン失敗 → 決着
       │    └─ カットイン成功 → 試合続行
       └─ 未達 → 次ターンへ
```

## 3. 各処理の詳細

### 3.1 リーガルマン攻防判定

既存シングルエンジンの資産を活用する部分。

**流用するもの：**
- 各スタッツ（PWR/SPD/TEC/STA/MNT）の比較による優劣判定
- 攻撃成功 → ダメージ算出
- スタイル別の技選択分布（categoryWeights）
- フィニッシャー発動条件と成功判定

**タッグ用の調整：**
- HP残量によるスタッツ減衰: 前セグメントからのダメージ蓄積を反映する
- この減衰があることで、フレッシュな選手（タッチで入ってきた選手）との差が自然に出る

#### 3.1.1 HP減衰曲線（後半急降下型）

HP残量に応じた実効スタッツの補正。中盤までは耐えられるが、閾値を超えると一気にガタが来る。

```
HP 100〜50%: スタッツほぼ維持（95〜100%）
HP  50〜30%: 急激に低下（95% → 75%程度）
HP  30〜 0%: さらに低下（75% → 60%程度）
```

**設計意図：**
- 「まだ大丈夫に見えたのに急に崩れた」が自然に発生する
- タッチ交代の判断に深みが出る（HP60%で引っ張ると50%割った瞬間リスク急増）
- フレッシュな選手との差がドラマチックに出る
- MNTが高い選手はこの減衰が緩やか（精神的に折れにくい）

#### 3.1.2 エプロン回復量

控えにいる選手は毎ターン少量のHP回復（自動・確定）。

- 回復量: 1ターンあたり約1.5〜2.0（HP最大100基準）
- 1セグメント（5〜8ターン）控え → 約8〜10回復
- 3〜4セグメント（約20ターン）控え → 約30〜40回復

**狙うバランス：**
- HP30%（瀕死）の選手が20ターン控えてHP60〜70%まで戻る → 「まだ戦える」ゾーン
- 満タンには戻らない → フレッシュな選手との差は残る
- タッチの明確なメリット（回復）と、引っ張るリスク（減衰）のトレードオフ

### 3.2 エプロン選手の行動

控えの選手は毎ターン何かするわけではない。基本は見ているだけで、条件を満たしたときだけ介入が発生する。

#### 3.2.1 回復（自動・確定）

- エプロンにいる選手は毎ターン少量のHP回復（確定発生）
- これが「タッチして控えに回す」メリットの根拠
- 回復量は微量（具体値は実装時に調整）

#### 3.2.2 介入（カットイン）（条件付き発生）

以下のトリガーで介入判定が走る：

| トリガー | 基本成功率（仮） | 内容 |
|---------|---------------|------|
| パートナーがピンされている | 70% | カウント2.9で返すお馴染みの場面 |
| パートナーがフィニッシャーを受けそう | 40% | 予測して飛び込む必要がある |
| 相手エプロンが介入してきた | 60% | 相手が動いたから反応しやすい |

**介入成功率の算出：**

```
介入成功率 = 基本成功率 + HP補正 + bond補正 - 介入回数ペナルティ
```

**設計原則：**
- **全て線形傾斜**。段階式にしない。全ての値が1刻みで意味を持つ
- **HP補正 ＞ bond補正**。体が動くかどうかが、助けたい気持ちよりも優先する
- 具体的な係数はプロトタイプで調整する。以下は仮置き

**修正要素（仮置き値）：**

| 要素 | 計算式 | 影響幅 | 優先度 |
|------|-------|-------|-------|
| HP補正 | (HP - 50) × 係数 | 約38%幅 | **最重要** |
| bond補正 | (bond - 50) × 係数 | 約23%幅 | 重要 |
| 介入回数 | -回数 × 定数 | 回数に比例して積む | 補助 |

**カットインの回数が増えるほど成功しにくくなる**ことで、カットイン無限ループによる試合停滞を防止する。

### 3.3 タッチ判定

毎ターン「タッチが起きるか」を判定する。**「したい」と「できる」を分離する**のがポイント。
プレイヤーは介入できない。全て自動判定。

#### 3.3.1 タッチの種類

| 種類 | 発生条件 | 演出的な意味 |
|------|---------|-------------|
| 戦術タッチ | HP中程度 + 攻防均衡 + ケミストリー高め | チームワークでうまく回している |
| 消耗タッチ | HP低下 + 数ターン劣勢が続いた | 追い込まれて交代 |
| ホットタグ | 長期間タッチ不可 + HP低い + タッチ成功判定クリア | ドラマの山場（条件付き発生） |
| タッチ封じ（失敗） | 相手がコーナーから引き離す + HP不足 | 孤立の継続 |

#### 3.3.2 「タッチしたい」判定

| 条件 | 閾値（仮） | 意味 |
|------|----------|------|
| HP低下 | HP60%以下 | ダメージ蓄積を感じ始める |
| 連続劣勢 | 3ターン以上攻撃を受け続けた | 流れが悪い |
| HP危険域 | HP35%以下 | 強制的にタッチしたい |

戦術タッチはHP80%でも発生しうる（ケミストリーが高いチームの「いいリズムで回す」表現）。

#### 3.3.3 「タッチできる」判定

成功率の主要因は**HP**。スタッツ差は微調整程度。

```
成功率の構成：
  HP由来:      70%の影響力（HP高い＝成功しやすい）
  スタッツ由来:  30%の影響力（SPD差等の微補正）
```

| 要素 | 影響度 | 内容 |
|------|-------|------|
| 自分のHP | **大** | HP高い＝体が動く＝成功しやすい。HP低い＝失敗しやすい |
| SPD差 | 小 | 素早い選手はやや戻りやすい程度 |
| 相手のPWR/TEC | 小 | 阻止能力として微補正 |
| MNT | **影響しない** | タッチ判定には関与しない |

**設計意図：** HPが低いほどタッチが難しくなる悪循環が自然に孤立状態を生む。これはスタッツの問題ではなくダメージ蓄積の結果なので、納得感がある。

#### 3.3.4 孤立カウントとホットタグ

「タッチしたい」が立ったのに「タッチできない」が連続すると**孤立カウント**が加算。
孤立カウントが閾値（仮: 3〜5回）に達すると、次のタッチ成功時に**ホットタグ**として扱われる。

#### 3.3.5 ホットタグの効果

ホットタグの価値は**「交代できたこと自体」**にある。

- 演出としての盛り上がり: **100%発生**（試合ログ・MQにドラマ要素としてプラス）
- パートナーのHP優位: **自然発生**（エプロン回復の結果。特別処理なし）
- 気迫バフ: **約20〜25%の確率**で発生。短時間の微補正。起きたらラッキー程度

**設計意図：**
- バフを期待して「もっと孤立してほしい」とはならない発生率
- 孤立は純粋に不利な状況。タッチ成功は純粋に嬉しい
- breakthroughと同じ「おっ、出た！」というサプライズの位置づけ

### 3.4 決着判定

基本条件：**HPが閾値以下 ＋ フィニッシャー成功**

タッグ特有の要素：
- フィニッシャー成功後に**カットイン判定**が入る。エプロンの相手パートナーが阻止する可能性がある
- カットインを突破して初めて決着
- **勝敗の帰属を記録**: フォール勝ちした選手 / フォール負けした選手を明確に記録（試合後イベントに影響）

## 4. ケミストリー（チームとしての強さ）

### 4.1 構成要素

```
ケミストリー = bond × 0.5 + タッグ経験値 × 0.3 + スタイル相性値 × 0.2
```

| 要素 | 重み | 説明 |
|------|-----|------|
| bond | 50% | 既存の関係性データをそのまま使用（0〜100）。信頼の深さ |
| タッグ経験 | 30% | 同じペアで組んだ試合数で蓄積（0〜100に正規化）。息の合い方 |
| スタイル相性 | 20% | 相性テーブルから変換した値（20〜100） |

**設計思想：**
- スタイル相性が悪くても、bondが高くてたくさん組んでいれば強いチームになる
- スタイル相性が良くても、初タッグでは活かしきれない
- bondが最重要。スタイル相性は「組んでみたら意外と噛み合った」のような物語を生む土台

### 4.2 タッグ経験の蓄積関数

指数減衰カーブ。1試合目から30試合目まで全ての値に意味がある。

```
タッグ経験値 = 100 × (1 - e^(-試合数 / 7))
```

| 試合数 | 経験値 | 感覚 |
|-------|-------|------|
| 0 | 0 | 初タッグ |
| 1 | 13 | まだぎこちない |
| 2 | 25 | 少し慣れた |
| 3 | 35 | だいぶ慣れてきた |
| 5 | 51 | 息が合ってきた |
| 7 | 63 | 安定感が出る |
| 10 | 76 | ベテランタッグ |
| 15 | 88 | ほぼ完成 |
| 20 | 94 | 上限付近 |
| 30 | 98 | 実質上限 |

**設計意図：**
- 序盤の伸びが早い → 5試合も組めば実用レベル
- 後半は緩やかに上限に近づく → 長く組むほどじわじわ良くなるが劇的な差は生まない
- 100には実質到達しない → 「完璧」は存在しない

### 4.3 ケミストリーの影響範囲

ケミストリーは**試合の勝敗を大きく左右するものではなく、試合の「質」と「安定性」に効く**。
勝敗を決めるのはあくまで個人の能力値。

| 場面 | 高ケミストリーの効果 | 影響の大きさ |
|------|------------------|------------|
| 戦術タッチの発生率 | スムーズに回せる | 小〜中 |
| ダブルチーム発生率 | たまに2対1の大技 | 小 |
| タッグフィニッシャー解禁 | 合体技が使える | 条件付き |
| 同士討ち・見殺し抑制 | 事故が起きにくい | 小（低ケミストリー時のペナルティ側） |

### 4.4 スタイル相性テーブル

#### 4.4.1 相性の種類と数値変換

| 種類 | 意味 | 相性値 |
|------|------|-------|
| 補完 | お互いの弱点を埋め合う。対応幅が広い。チームとして最も強い | **100** |
| 共鳴 | 同じ方向性で圧倒。連携精度が高いが弱点が共通する | **75** |
| 普通（0） | 特筆なし | **50** |
| 噛み合わない（-1） | リズムが合いにくい | **20** |

補完と共鳴は両方プラスだが、効果の出方が異なる：
- **補完型ボーナス**: 相手チームのどちらが出てきても対応できる確率が上がる
- **共鳴型ボーナス**: ダブルチーム技の発生率UP、タッグフィニッシャーの威力UP

#### 4.4.2 相性マトリクス

人数分布: Gra(12), Aer(6), Sub(14), All(25), Str(14), Bra(9)

| | Gra(12) | Aer(6) | Sub(14) | All(25) | Str(14) | Bra(9) |
|---|---|---|---|---|---|---|
| **Gra** | 共鳴 | 補完 | 共鳴 | 0 | 0 | -1 |
| **Aer** | 補完 | 共鳴 | 0 | 補完 | 0 | 0 |
| **Sub** | 共鳴 | 0 | 0 | 0 | 補完 | 補完 |
| **All** | 0 | 補完 | 0 | 0 | 0 | 0 |
| **Str** | 0 | 0 | 補完 | 0 | 共鳴 | 共鳴 |
| **Bra** | -1 | 0 | 補完 | 0 | 共鳴 | 共鳴 |

**設計根拠：**

| 組み合わせ | 種別 | 理由 |
|-----------|------|------|
| Gra × Aer | 補完 | 地上戦と空中戦を両方カバー |
| Gra × Sub | 共鳴 | グラウンド支配力。捕まえて極める |
| Gra × Gra | 共鳴 | 投げの連携。重厚なタッグ |
| Aer × Aer | 共鳴 | テンポの速い空中連携 |
| Aer × All | 補完 | 万能型が土台を作りAerialが跳ぶ |
| Sub × Str | 補完 | 打撃で崩して関節で仕留める |
| Sub × Bra | 補完 | 荒く倒してから関節技へ |
| Str × Bra | 共鳴 | 打撃の嵐。ダブルチーム破壊力 |
| Str × Str | 共鳴 | 打撃コンビネーション |
| Bra × Bra | 共鳴 | 荒さの相乗効果 |
| Gra × Bra | -1 | テンポが重くなりすぎる。唯一のマイナス |

**少数スタイルへの配慮：**
- Aerial（最少6名）: マイナス相性ゼロ。良相性の相手43名（Gra+Aer+All）
- Brawler（9名）: マイナスはGrappler(12名)のみ。良相性37名（Sub+Str+Bra）
- Allrounder（最多25名）: 良相性はAerial(6名)のみだがマイナスもゼロ。「誰とでも無難、Aerialと特に光る」

### 4.6 各スタッツのタッグにおける役割

| スタッツ | タッグでの役割 |
|---------|-------------|
| PWR | 攻防判定（流用）。タッチ阻止に微影響 |
| SPD | 攻防判定（流用）。タッチ成功率に微影響 |
| TEC | 攻防判定（流用）。タッチ阻止に微影響 |
| STA | 攻防判定（流用）。HP最大値やダメージ耐性に影響 |
| MNT | 孤立時のスタッツ減衰を緩和（精神的に折れにくい）、ホットタグバフの持続、同士討ち・見殺しの抑制 |

**MNTの設計原則：MNTが高いことが不利に働く場面を作らない。** タッチ判定にはMNTは関与しない。

## 5. ドラマイベント（条件付き発生）

全て「たまに起きるもの」。条件を満たしたときだけ発生して試合にアクセントをつける。毎試合起きたら陳腐化するので、発生率は抑える。

### 5.1 イベント一覧

| イベント | 発生条件（概要） | 効果 |
|---------|---------------|------|
| ホットタグ | 孤立セグメントが一定数続いた後のタッチ成功 | 演出盛り上がり（確定）＋気迫バフ（20〜25%確率・微補正） |
| ダブルチーム | ケミストリー高 + 確率 | 一時的に2対1の攻撃。汎用タッグ技による大ダメージ。決着技になることもある |
| カットイン | フィニッシャー/ピン時にエプロンから割り込み | 決着を阻止 |
| 同士討ち | ケミストリー低 + 稀 | パートナーに誤爆。自チームにダメージ |
| 見殺し | bond低 + 稀 | パートナーを助けに行かない。カットイン放棄 |
| タッグフィニッシャー | ペア固定技あり + ケミストリー高 + 条件達成 | 専用合体技。稀。将来的な拡張要素 |

#### 5.1.1 決着技の優先度

タッグマッチでも**決着は基本的に個人フィニッシャー**で決まる。プロレスのタッグマッチの実態に合わせた設計。

| 優先度 | 決着手段 | 頻度 | 説明 |
|-------|---------|------|------|
| 1 | 個人フィニッシャー | 最多 | シングルと同じ。これがメイン |
| 2 | 汎用タッグ技 | たまに | ダブルチームイベントから発展。スタイル組み合わせで自動選択 |
| 3 | ペア固定タッグフィニッシャー | 稀 | 特別なペアのみ。プロトタイプ後に追加 |

#### 5.1.2 汎用タッグ技のデータ構造

2人のスタイルの組み合わせから自動選択される連携技。合体ボディスラム、片方が持ち上げてもう片方が蹴る、等のよくあるタッグ技。

```
styleTagMoves: {
  "Striker+Grappler": { name: "打投コンビネーション", power: 値 },
  "Aerial+Allround": { name: "アシスト式ダイビングアタック", power: 値 },
  ...（スタイル組み合わせごとに定義）
}
```

技名・威力の具体値はプロトタイプで設定。

ペア固定型は将来的な拡張として構造だけ用意する：
```
pairFinishers: {
  "選手ID_A + 選手ID_B": { name: "合体技名", power: 値 }
}
```

#### 5.1.3 ドラマイベント発生率

全て線形。ケミストリーやbondの値が1刻みで発生率に影響する。具体的な係数はプロトタイプで調整。

| イベント | 判定タイミング | 基本発生率（仮） | 修正要素 |
|---------|-------------|---------------|---------|
| ダブルチーム | セグメント内の毎ターン | 5〜8% | ケミストリーが高いほど上昇（線形） |
| カットイン | フィニッシャー/ピン発生時 | §3.2.2の算出式 | HP・bond・回数（確定済み） |
| 同士討ち | セグメント内の毎ターン | 2〜3% | ケミストリーが低いほど上昇（線形） |
| 見殺し | カットイン判定時 | bond依存 | bondが低いほど発生（線形） |
| ホットタグバフ | ホットタグ成功時 | 20〜25% | 固定確率 |

算出例（ダブルチーム）：
```
ダブルチーム発生率 = ベース値 + ケミストリー × 係数
```

### 5.2 試合後イベントへの接続

ドラマイベントは試合中の演出にとどまらず、試合後の関係性変動のフラグとして機能する。

| 試合中イベント | 試合後の影響 |
|-------------|------------|
| 見殺し発生 | bond大幅下落。チーム解散フラグの可能性 |
| タッグフィニッシャー成功 | bond上昇。Glimpseでパートナーへの特別セリフ |
| 同士討ち | rivalry発生の種 |
| ホットタグからの逆転勝ち | 勝った側の選手にbreakthrough判定ボーナス |
| カットインでパートナーを救出 | bond微増 |

## 6. タッグMQ（試合の質の評価）

シングルMQとは評価軸が異なる。タッグならではの「良い試合だった」を測る。

### 6.1 算出構造

```
タッグMQ = 攻防品質ベース
         + 見せ場分配ボーナス
         + タッチ多様性ボーナス
         + ドラマイベントボーナス
         + 決着説得力ボーナス
         - ペナルティ
```

全要素線形。全ての値が1刻みで意味を持つ。具体的な係数はプロトタイプで調整。

### 6.2 MQを上げる要素

| 要素 | 算出方法の方針 |
|------|-------------|
| 攻防品質ベース | シングルMQロジック流用。能力拮抗度ベース |
| 見せ場分配 | 4人の出場ターン数の偏差が小さいほど加点（線形） |
| タッチ多様性 | タッチ種類が複数混在していると加点 |
| ドラマイベント | 発生した種類数に応じて加点 |
| 決着説得力 | カットイン突破しての決着、タッグ技での決着で加点 |

### 6.3 MQを下げる要素

| 要素 | 算出方法の方針 |
|------|-------------|
| 一方的な展開 | 最長セグメントが長すぎる＝片方が孤立させられ続けた（線形） |
| 出番の偏り | 1人の出場率が極端に低い（線形） |
| 時間切れ引き分け | 制限時間内に決着がつかなかった場合のみ減点 |

**注意：試合時間の長さ自体はペナルティにしない。** 制限時間ギリギリで決着がついた試合はむしろ名勝負。問題は長さではなく、決着がつかないこと。

## 7. AI側のタッグ編成ロジック

NPCプロモーションがどうペアを組むか。

### 7.1 基本方針

- ケミストリーの算出式（§4.1）をそのまま編成の判断基準に使う
- ロスターの中からケミストリーが高くなる組み合わせを選択
- 初期はタッグ経験がゼロだから、bond＋スタイル相性で判断。結果的にタッグ経験も積まれていく
- 特別なロジックは不要。ケミストリー算出式が編成AIを兼ねる

### 7.2 プロトタイプ段階

ランダム編成またはケミストリー上位ペアの選択式で十分。AI編成の賢さは後から磨ける。

## 10. Phase 4a — ビジュアル観戦（実装済み 2026-04-17）

タッグ試合の「試合を観る」ボタンで `src/tag-battle.html` iframe が開き、4選手レイアウトで試合を再生する。

### 10.1 アーキテクチャ: Replay方式
シングル `battle-engine.html` の Port 方式（iframe 内で同一 RNG シードで再シミュレーション）ではなく、Replay 方式を採用。
- `App._watchTagMatch(idx)` が `Engine.tagMatch.simulateTagMatch(..., { recordFrames: true })` を事前実行
- `sp.results[idx]` に結果を格納（skipMatch と同一経路）
- iframe には postMessage で完全な結果 + frames 配列を送信
- iframe 側（tag-battle-main.js）は受け取った frames を時系列に再生するだけ

メリット：エンジン単一ソース原則を維持、iframe 側はエンジンコード重複なし、`skipMatch` と `watchMatch` で完全同一結果が保証される。

### 10.2 Engine 拡張: recordFrames オプション
`Engine.tagMatch.simulateTagMatch(teamA, teamB, rng, options)` の options に `recordFrames: true` を指定すると、返り値 `result.frames` にターンごとの snapshot 配列が含まれる。デフォルト off（auto-sim / AI団体週次処理は無影響）。

snapshot 構造:
```
{
  turn, phase, legalA, legalB, apronA, apronB, // ID
  hp: {[fighterId]: hp, ... x4},
  grit: {...x4}, hotTagBuff: {...x4},
  mom, logLines: string[], events: Event[],
  action: { attackerId, defenderId, atkSide, move, moveD, kind: 'miss'|'hit'|'counter', dmg, isCrit },
  segmentIdx, winner, finType, finMove, finishPhase, pinnedBy, pinnedWho
}
```

- `App.watchMatch(idx)`: `matchType === 'tag'` 検出時に `App._watchTagMatch(idx)` に分岐
- `App._watchTagMatch(idx)`: simulateTagMatch(recordFrames:true) 実行 → sp.results[idx]格納 → iframe src を `tag-battle.html?t=<ts>` に切替 → postMessage (START_TAG_MATCH) 送信
- `App.receiveBattleResult(data)`: `m.matchType==='tag'` ならタッグ経路で iframe を閉じるだけ（結果は事前計算済みを尊重、決定論保証）
- `App.escapeBattle()`: 既存 show context 経路でタッグも正しく処理（sp.results[idx] が埋まっているので finalizeShow 判定に入る）
- 他コンテキスト（PPV/war/JT/B2/B3）の iframe.src を `battle-engine.html?t=<ts>` にハードコード（直前のタッグ観戦で src が `tag-battle.html` に切替わっている場合の復帰）

### 10.7 スコープ外（Phase 4c 以降）
- シングル battle-engine.html の Replay 方式移植（権威モデル統一）
- PPV / 対抗戦 / B2 / B3 / JT でのタッグ観戦（これらの card には現状タッグ枠なし）
- ペア固定タッグフィニッシャー演出（spec §5.1.2）
- タッグ専用 BIG MATCH 演出（現状タイトル戦タッグ禁止）
- 演出シーケンス単位の共通化 (bigmove 溜め→技名→フラッシュ→ダメージ / counter スライドイン / touch swap など。setTimeout ツリーの共通ヘルパー化)

## 11. Phase 4b — 演出層の single 統合（実装済み 2026-04-19）

### 11.1 背景
Phase 4a 時点で tag-battle は single battle-engine とは別ファイルで SFX / CSS / カットインを独自実装しており、**single 側で演出を改修しても tag 側に伝わらない**ドリフト問題を抱えていた。Phase 4b はこのドリフトを**見た目・音・タイミングのレベルで**一方向に解消することを目的とする（権威モデルの統一はスコープ外）。

### 11.2 共有ファイル構成
| ファイル | 役割 | 参照元 |
|---|---|---|
| `src/battle-sfx.js` | SFX (音源ファイル / Web Audio 合成 / ミックス値 / drone / hitSE / guessCategory) | battle-engine.html + tag-battle.html |
| `src/battle-shared.css` | デザイントークン (:root) / リセット / スクロールバー / 共有キーフレーム (9種) | battle-engine.html + tag-battle.html |
| `src/battle-anim.js` | `BattleAnim.renderCutin({overlay, fighter, side, text, variant})` / `BattleAnim.dismissCutin(overlay, onAfterClear?)` | battle-engine.html + tag-battle.html |

### 11.3 Step 1 — SFX 共通化
- 両者が約90%重複していた SFX 定義を `battle-sfx.js` に superset で集約。
- drone (suspense 用 BGM oscillator) の state を iframe の `S.droneNodes` から module-local `_droneNodes` に逃がして衝突回避。
- 削除: `src/tag-battle-audio.js` (battle-sfx.js にリネーム相当)。

### 11.4 Step 2 — CSS トークン・キーフレーム共通化
- `:root` デザイントークン superset を shared 側に集約。tag の text-sub/dim を `#888`/`#555` から `rgba(232,230,224,0.5/0.25)` に single 準拠で統一。
- 共有キーフレーム: `waitSpin` / `shakePanel` / `shakeHard` / `movePop` / `counterFlash` / `cutinSlideIn` / `cutinSlideInR` / `flashScreen` / `dmgNumPop`
- drift 補正:
  - `counterFlash`: tag「2段階」→ single「0→30%ピーク→100% 3段階」
  - `cutinSlideIn/R`: tag `-40px` → single `-50px`
  - `movePop`: tag `scale(1.15)` → single `scale(1.20)`
  - `flashScreen` (旧 tag: `flashScr`): `opacity 0.15` → `0.18`
- 名称統一: `dmgPop` → `dmgNumPop` / `flashScr` → `flashScreen` (tag 側の参照を更新)

### 11.5 Step 3 — カットインの DOM/SE レンダリング共通化
- `BattleAnim.renderCutin` が innerHTML 組立 + `.show` 付与 + SE 再生を担当 (`damage-voice` 時のみ `sfx.dmgVoice()`、他は `sfx.cutinSlide()`)。
- 各 iframe は自前で text を選定してから呼ぶ (line table 引きはそれぞれ保持)。
- tag 固有の state 管理 (`S.pendingCutin` / `nBtn` disabled / pin seq 連動) は `showCutin` ラッパに残す。
- 付随修正: single の `showDamageVoice` で SE が鳴っていなかった不整合が共通化により自動解消。

### 11.6 共通化していないもの (Phase 4c 送り)
- 演出シーケンス (bigmove / counter / touch swap の setTimeout ツリー) の共通化
  - 理由: single=streaming (iframe 内で RNG を回してターンを進める) / tag=Replay (親で事前計算した frames を再生する) の**権威モデル差**があり、setTimeout 呼び出し側のループ制御が構造的に異なる。sequence 単位の共通ヘルパー化は権威モデル統一と合わせて設計する必要がある。
- ダメージ数字ポップ (single=固定要素再利用 / tag=動的 append) の統合 — DOM 戦略が異なるためどちらかを書き換える必要がある
- shake / banner / pin-count の共通ヘルパー化 (現状インライン、drift リスク低い)

### 11.7 期待効果
- single battle-engine.html で以下を変更すると tag にも自動反映される:
  - SE 音源ファイル差替え / ミックス値調整 / 合成フォールバックの改変
  - カラートークン (`--gold` 等) / 共有キーフレームの timing/strength 調整
  - カットインの variant 追加 / SE の紐付け変更
- ドリフトが起こりうるのは「演出シーケンスの setTimeout 値」だけに限定される (Phase 4c で潰す)
