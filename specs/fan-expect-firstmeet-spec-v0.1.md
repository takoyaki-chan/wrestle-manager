## なぜこの仕様が存在するか

現行の `Engine.fanExpect` (management.js L13925-14010) は3つの優先度階層から候補を生成しており、終盤になるほど顔ぶれが固定化する。引き継ぎ #3 では「タイプを増やす」方向で対策が検討されていたが、議論を進めた結果、**問題の本質はタイプ数ではなく「実現しても数字が増えるだけで何も起きない」体験設計にある**ことが判明した。

`r.fanExpectMatch = true` のフラグは集客・メディア収入の計算にしか使われず、プレイヤーには**演出も波及も返ってこない**。結果として、ファン期待カードは「数字合わせの煩わしい制約」として体感される。マンネリペナルティも同様の縛り感を生んでいる。

本仕様は、この問題に対する**最小実装での感触検証**を目的とする。タイプを1つだけ追加し、それを「数字ではなく体験で報いる」設計に振り切る。手応えがあれば他タイプに展開する。

---

## 設計原則

1. **数字ではなく瞬間を返す** — ファン期待カードの実現に対する報酬は、新しい数字ボーナスではなく、顔・声・状態変化の3点セットの「瞬間」とする
2. **既存資産だけで作る** — 全127名分のface画像、personality×archetypeセリフ生成器、スナップショット通知システムは既に存在する。新規アセットゼロで成立させる
3. **波及は1回で完結させない** — 試合直後のスナップショットだけでなく、1〜2週後のフォローアップでも余韻を返す。「あの試合のせいで今これが起きている」が成立する
4. **検証スコープに集中する** — 本仕様では「初顔合わせドリーム」1タイプのみを実装する。他タイプ追加・数字バランス調整・マンネリ仕様見直しは別仕様に分離する

## §1 スコープ

### §1.1 本仕様で実装するもの

- ファン期待カード新タイプ `firstMeetDream` の生成ロジック (`Engine.fanExpect.generate` への追加)

- 集客・メディア収入の数値バランス調整
- スナップショット通知システム本体のリファクタリング

## §2 生成ロジック

### §2.1 新タイプ `firstMeetDream` の定義

`Engine.fanExpect.generate(state)` (management.js L13925-14010) の Priority 2 と Priority 1 の間に **Priority 2.5 ブロック** を追加する。

```
[既存] Priority 3: rivalry系
[既存] Priority 2: 王座挑戦
[新規] Priority 2.5: 初顔合わせドリーム  ← 本仕様
[既存] Priority 1: 人気上位対決
```

### §2.2 候補抽出条件

ロスター内の全ペア（負傷者・レンタル除外、L13929 と同条件）から以下を満たすものを抽出：

1. **初顔合わせであること** — `Engine.freshness.calc(matchupLog, id1, id2, ...)` の `isFirstMeet === true`
2. **両者にドラマ性があること** — どちらか一方が以下のいずれかを満たす：
   - 人気 (`popularity`) ≥ **40** 🔧
   - OVR ≥ **150** 🔧（1パラメータ平均30相当の上位）
   - タイトル保持中
3. **同部屋・同ユニットの同期ではないこと**（後述 §2.3 — 必要なら相性的にすぐ組まれそうなペアの除外）

条件2は「誰でも初顔合わせ」を防ぎ、「**ファンが待っていた組み合わせ**」の質感を担保するためのフィルタ。閾値は試遊で詰める。

### §2.3 同期除外（任意・初期実装ではOFF）

`debutSeason` が同一かつ同じバックストーリー（`backstoryType === '同期入団'` など）のペアは「ファンが待ち望んだドリームマッチ」とは言いにくいので除外候補となる。**ただし初期実装ではフィルタを入れず、生成結果を見て判断する**。先入観で除外を増やすと候補プールがさらに痩せる懸念がある。

### §2.4 優先度・上限

- 1興行あたり生成上限: **1件** 🔧（複数あっても1興行内で消化できないため）
- 最終 `slice(0, 3)` の上限変更: **しない**。本タイプが選ばれた場合、既存タイプ3件のうち優先度最低のものを押し出す形になる
- 優先度値: **2**（Priority 2 と同等扱い、王座挑戦と同レベルの存在感）

### §2.5 reason 文言

```
🌟 まだ実現していないドリームマッチ: ${f1.name} vs ${f2.name}
```

絵文字は既存 reason との視覚的差別化のため。文言は仮で、UIに合わせて調整する 🔧。

### §2.6 freshness チェックの扱い

初顔合わせなので `isFirstMeet === true` であり、`countInWindow === 0`。`Engine.freshness.calc` はこの場合 `firstMeetBonus` を返すため、`addCandidate` 内のマンネリ判定 (L13946-13951) には**絶対に引っかからない**。これは設計上正しい挙動。

## §3 実現の検出

### §3.1 既存フローへの統合

既存の実現検出 (management.js L6935-6939) は `r.fanExpectMatch = true` を立てるだけ。**この検出ロジックは変更不要**。

代わりに、興行実行直後の処理で「実現された fanExpect のうち、`firstMeetDream` タイプだったもの」を抽出する新しい処理を追加する。

### §3.2 タイプ識別のための拡張

現在の `fanExpects` 配列の各要素は `{leftId, rightId, leftName, rightName, reason, priority}` の形。タイプ識別子がない。

→ **`type: 'firstMeetDream'` フィールドを `addCandidate` の引数に追加する**。既存タイプは `type: 'rivalry' | 'titleChallenge' | 'topPopular'` に整理する。これは既存タイプの動作を変えない純粋な追加情報。

### §3.3 実現直後のフック

`management.js` 内、`r.fanExpectMatch = true` を立てる箇所 (L6939) の直後または興行終了処理の中で、以下を実行：

```javascript
// 擬似コード
fanExpects.forEach(exp => {
  if (exp.type !== 'firstMeetDream') return;
  const realized = results.some(r =>
    (r.left.id === exp.leftId && r.right.id === exp.rightId) ||
    (r.left.id === exp.rightId && r.right.id === exp.leftId)
  );
  if (!realized) return;
  // ① スナップショット即時発火
  // ② rivalry 付与
  // ③ フォローアップキュー登録
});
```

## §5 状態への波及

### §5.1 rivalry 付与

実現直後、以下を実行：

```javascript
// 擬似コード
const key1 = `${Math.min(id1, id2)}-${Math.max(id1, id2)}`;
const key2 = `${Math.max(id1, id2)}-${Math.min(id1, id2)}`;
state.relationships[key1].rivalry += 12; // 🔧
state.relationships[key2].rivalry += 12; // 🔧
// 既存のクランプを通す（_clampAxisValue 相当）
```

付与量 **12** 🔧 は、既存のチェック閾値 `minRivalry >= 50` (Priority 3 rivalry系の発火条件) には届かない値。「次もまた組みたくなる種」程度の量。試遊で調整する。

### §5.2 試合の MQ や結果との連動

**初期実装では MQ 連動はしない**。試合が好試合だったかどうかに関わらず、実現すれば固定で rivalry を付与する。これは複雑度を抑えるため。

将来拡張: MQ ≥ 70 なら rivalry +18、MQ < 50 なら +6 のような階調を入れる余地はあるが、本仕様では扱わない。

## §6 フォローアップ機構

### §6.1 `state._pendingSnapshots` キュー

state に新フィールドを追加：

```javascript
state._pendingSnapshots = [
  {
    fireOnAbsWeek: 145,         // Engine.util.absWeek(season, week) で計算
    source: 'firstMeetDream_followup',
    fighterId: 12,
    fighter2Id: 47,
    contextRef: { /* 元のfirstMeetDream発火情報 */ },
  },
];
```

### §6.2 登録タイミング

実現スナップショット発火と同時に、`_pendingSnapshots` に1件追加する。発火予定週は **現在週 + 1〜2週後** 🔧（ランダム）。

### §6.3 発火タイミング

`Engine.snapshot.generate` の冒頭、もしくは `tickWeek` の中で、`_pendingSnapshots` の各要素について `fireOnAbsWeek <= currentAbsWeek` のものを発火させる。発火後はキューから除去。

実装としては `Engine.snapshot._collectCandidates` (L1709) の冒頭で pending を candidates に注入するのが既存システムへの差し込みが少なく綺麗。

### §6.4 フォローアップ発火時の表示

R4「因縁勝利」と同様の slot 型スナップショット（テキストログのみ）として表示する。モーダルではない。理由は、既に試合直後のモーダルで派手に演出済みなので、フォローアップは「あの試合の余韻が今ここに残っている」という静かな質感の方が良いから。

### §6.5 フォローアップのセリフ

```javascript

    'ロッカールームで{name}が{name2}の名前を口にした',

  voice: {
    // personality × archetype 別のセリフ
    bold: { _default: ['もう一度、あいつとやりたい', 'まだ終わってない'] },
    quiet: { _default: ['…もう一度', '…あの試合がずっと'] },
    earnest: { _default: ['学ぶことが多すぎた一戦でした', 'もう一度向き合いたいです'] },
    emotional: { _default: ['…思い出すだけで震える！', 'もう一回！もう一回やりたい！'] },
    easygoing: { _default: ['また、やろうね', 'ふふ、楽しかったな'] },
    normal: { _default: ['もう一度…向き合ってみたい', 'あの一戦が忘れられない'] },

```

### §6.6 フォローアップから次の fanExpect への接続

フォローアップが発火した時点で、当該ペアは既に `matchupLog` に存在するため `firstMeetDream` の候補にはならない。**ただし将来的に「再戦希望」タイプを追加すれば、ここから自然に接続できる**。本仕様ではこの接続は実装しない（次仕様の責務）。

## §8 受け入れ条件（試遊検証項目）

最小実装が完了したとき、以下を試遊で確認する：

1. **発生する**: シーズン1〜2 の通常プレイで、`firstMeetDream` カードが平均 1〜2興行に1回程度は出現する
2. **発生しすぎない**: 初顔合わせは無数にあるが、§2.2 のフィルタにより「ドラマ性のあるペア」だけが選ばれている
3. **モーダルが心を動かす**: プレイヤーが実現したとき、顔画像とセリフを見て「やった」と感じる
4. **波及が伝わる**: rivalry +12 の通知を見て、「この試合のせいで関係が動いた」と理解できる
5. **フォローアップが余韻を残す**: 1〜2週後にスナップショットが流れて、「ああ、あの試合のことだ」と思い出せる
6. **強制感がない**: このカードを組まなくても罰がない。組みたくなるのは数字ではなく「何が起きるか見たい」という好奇心

このうち1つでも満たさなければ、仕様レベルで再設計する。

## §10 オープンアイテム

実装着手前に決めるべきこと、または実装中に判断が必要なこと：

1. **顔画像のパス解決関数** — 既存ロスター描画で使われている `face_*.png` のパス解決ロジックを ui-render.js から特定する必要がある
2. **モーダルのSE** — 既存サウンドアセットを棚卸しして、適切なものを選ぶ
3. **同期除外フィルタ (§2.3)** — 初期実装ではOFFだが、試遊で「同期同士の初顔合わせがドリームマッチに見えない」問題が出たら有効化を検討
4. **`_pendingSnapshots` の永続化** — `state` に乗せる以上、セーブデータに含まれる。既存のセーブ/ロード処理で配列が問題なくシリアライズされるか確認
5. **複数 `firstMeetDream` の同時発火** — 1興行に2つ実現された場合（§2.4 で生成上限1なら原則起きないが、保険として）モーダルを連続表示するか、1つに絞るか

## このスペックの精神

> ファン期待カードを「組まないと損をするカード」から「組んだら何かが起きるかもしれないカード」に変える。
>
> 数字での誘導をやめて、好奇心での誘導に切り替える。プレイヤーが「次は何が起きるか見たい」と思えれば、固定化の問題は自然に消える。
