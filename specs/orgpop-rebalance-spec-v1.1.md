## §0 背景と問題意識

### 0.1 ユーザーフィードバック（原文）

> 人気の上げ方難しい。シーズン30くらいまでやってもドームでの興行ができなかった。
> 人気は上がったり下がったりするのは現実でもあるので分かるが、何が原因で上がったり
> 下がったりしているかが分からないので対策がとりづらいと感じた。

### 0.2 問題の構造

実コード調査と auto-sim/v2集客検証で判明した問題は **3 階構造** だった:

| 層 | 症状 | 原因 |
|---|---|---|
| 上層 | orgPop が 70 で頭打ち、シーズン30回しても突破不可 | 逓減カーブ70-85帯×0.12 + 年次減衰 -4 |
| 中層 | 仮にorgPop 100に到達しても、ドーム集客は理論上限 ≈24,500人 | reachCurve + soft cap の天井 |
| 下層 | ドーム(cap 30,000)が満員にならない設計、コスト 12,000で実質常時赤字 | キャパが理論天井を大幅超過 |

### 0.3 v1.0 ドラフトからの主要変更点

v1.0 ドラフト後の議論で以下の点が判明・確定した:

1. **`BASE_ATTENDANCE_CURVE` は dead constant** — `Engine.economy.calcAttendance` (v1)からのみ参照されるが、実機の興行処理は完全に v2 経路 (`Engine.attendanceV2.calcAttendanceV2`) を使っているため、`BASE_ATTENDANCE_CURVE` をいくら触っても実機集客は変わらない。**v1.0 §3 の「BASE_ATTENDANCE_CURVE 引き上げ」は無意味だった**。
2. **ドームは縮小すべき** — 30,000人キャパは絶対天井(24,500人)を超えており、設計上「物理的に満員にならない箱」だった。これは「埋まらない場所には存在意義がない」という設計原則に反する。
3. **ドームは「コンスタントに稼ぐ場」ではない** — 終着点・名誉のための聖地。金銭的メリットは"ほぼなし"でよく、代わりに非金銭メリット(殿堂入りポイント加点)を設ける。
4. **透明性UIで計算式を見せるのは逆効果** — 「計算式を見せられるほど冷めることはない」。v1.0 §5.1 の興行後内訳表示は完全削除。代わりに見せ方を「年始の小芝居」と「経営画面のグラフ」に集約する。
5. **成長ペースはもっと緩やかでよい** — 「年度後半に差し掛かったら目標値に近いところまで」のテンポ感。シーズン20で orgPop 80前後、シーズン25で 85前後、シーズン30前後でドーム圏内 (90+)。

### 0.4 実機検証データ

**auto-sim 30シーズン (seed=42) 実測**:

```
S 5: pop=50.3   ← 順調
S10: pop=68.3   ← 失速
S15: pop=68.5   ← 振動
S20: pop=68.3
S30: pop=64.2   ← 一度も 70 を恒常突破できず
```

**ドーム絶対天井測定 (cap無制限・全パラメータ最大)**:

| orgPop | 普通興行 | 良い興行 | 理想プレイ | 全盛り(★最大) |
|---:|---:|---:|---:|---:|
| 90 | 9,500 | 13,050 | 15,189 | 16,606 |
| 95 | 11,750 | 16,141 | 18,786 | 20,539 |
| **100** | **14,000** | **19,232** | **22,383** | **22,500** ← 絶対天井 |

→ **「全盛り条件 ≒ 22,500人」が本仕様の中核数字**。ドームキャパをこの数字に合わせれば「全部理想で満員になるかならないか」のバランスが自動的に成立する。

## §1 設計目標

### 1.1 ゴール

| シーズン | 期待 orgPop | プレイヤー体感 |
|---:|---|---|
| S5 | 50前後 | 順調に成長中 |
| S10 | 68-72 | 「壁」を感じ始める |
| S15 | 75前後 | じわじわ登る |
| S20 | 80前後 | メジャー入りの実感 |
| S25 | 85前後 | ドームを意識し始める |
| **S30前後** | **90+** | **ドーム挑戦圏内** |
| S35+ | 95+ | 頂点維持の戦い |

ゴールは **「シーズン30前後で、ある程度理想のプレイができれば、ドーム興行が打てる」** 状態。ただし打っても金銭的にはほぼ得しない。打つ意義は名誉と殿堂入りポイントにある。

### 1.2 デザイン原則

1. **壁ではなく坂にする** — 70+ 帯が「数学的純減ゾーン」になっている現状を、「努力すれば登れる急坂」に変える
2. **ドームは終着点・聖地** — コンスタントに稼ぐ場ではない。年1回の特別興行
3. **計算式は見せない** — 透明性は「結果の推移グラフ」と「ナラティブな小芝居」で担保する
4. **既存の「会場は選ぶもの」原則は維持** — popReq復活させない
5. **既存システムを尊重** — 殿堂入りシステム等、既にある仕組みに新要素を載せる(別建てしない)

### 2.2 提案値 🔧

```javascript
getDiminishingMultiplier(orgPop) {
  if (orgPop < 20) return 1.0;
  if (orgPop < 40) return 0.70;
  if (orgPop < 55) return 0.35;
  if (orgPop < 70) return 0.22;  // 0.20 → 0.22 (微緩和)
  if (orgPop < 85) return 0.18;  // 0.12 → 0.18 (★主要修正)
  if (orgPop < 95) return 0.15;  // 帯細分化、新設(0.08 → 0.15相当)
  return 0.06;                    // 0.08 → 0.06 (頂点はシビアに)
}

calcAnnualDecay(orgPop) {
  if (orgPop < 15) return 0;
  if (orgPop < 50) return 1;
  if (orgPop < 65) return 2;
  if (orgPop < 80) return 3;     // 4 → 3
  if (orgPop < 90) return 5;     // 7 → 5
  if (orgPop < 95) return 7;     // 帯細分化、新設
  return 10;                      // 15 → 10 (「触れたら罰」を解除)
}
```

→ **70-85帯では raw=1.3 以上のプレイヤーは確実に成長**、**85-95帯は raw=1.5 でほぼ均衡、raw=1.7 で微増**、**95+帯は厳しい維持戦** という曲線。

### 2.4 検証目標 (Step 1 後の auto-sim)

| 検証 | 期待値 |
|---|---|
| seed=42, 30シーズン | S20 で orgPop ≥ 78、S30 で orgPop ≥ 85 |

### 3.2 提案値 🔧


### 3.3 数値の根拠

cap 22,500 は **「orgPop 100 + 試合カード理想 + Heat On Fire + 勢い最大」の絶対天井 ≒ 22,500 人** から逆算した。

```
絶対天井 = reach @ orgPop100 (14,000)
         × draw cap (2.0)
         × heat mult max (1.30, On Fire!)
         × momentum cap (+15%)
         → soft cap 適用後: 約 22,500 人
```

これにより自動的に以下のバランスが成立する:

| orgPop | プレイヤー力量 | 集客 | occ% | 状態 |
|---:|---|---:|---:|---|
| 100 | 全盛り(★絶対上限) | 22,500 | **100%** | 完売(伝説の興行) |
| 100 | 理想 | 22,383 | 99% | あと一歩で完売 |
| 100 | 普通 | 14,000 | 62% | 半分以上空席 |
| 95 | 全盛り | 20,539 | 91% | 完売届かず |
| 90 | 全盛り | 16,606 | 74% | 「次は完売目指したい」 |
| 85 | 全盛り | 13,984 | 62% | 「ドームには早い」 |

cost 11,000 と組み合わせた収支(ドーム開催1回・グッズ&メディア概算込み):

| シナリオ | 集客 | 総収入 | net | 判定 |
|---|---:|---:|---:|---|
| 100+全盛り(満員) | 22,500 | 13,440 | **+2,440** | 🟢 達成感ある黒字 |
| 100+理想 | 22,383 | 13,382 | +2,382 | 🟢 |
| 100+良い | 19,232 | 11,155 | +155 | 🟡 ほぼトン |
| 95+理想 | 18,786 | 10,944 | -56 | 🟡 ほぼトン |
| 95+良い | 16,141 | 8,145 | -2,855 | 🟠 軽い赤字 |
| 90+理想 | 15,189 | 8,685 | -2,315 | 🟠 軽い赤字 |
| 90+良い | 13,050 | 6,196 | -4,804 | 🔴 大赤字 |

→ **orgPop 100 で完売したら +2,440万** = 年1のご褒美興行として丁度いい達成感。**95未満は赤字確定**で「まだ早い」のシグナル。**ドームは"博打"** で、上手くやらないと痛手。これがユーザー哲学「コンスタントに稼ぐ場ではない、終着点」の体現。

### 3.4 注: BASE_ATTENDANCE_CURVE は触らない

`BASE_ATTENDANCE_CURVE` (`src/data.js` L889) は `Engine.economy.calcAttendance` (v1) からしか参照されておらず、実機の興行処理は使っていない (v2 経路を使用)。**本仕様では同定数を一切触らない。**

dead constant の整理は本仕様のスコープ外とし、別途技術的負債整理タスクとしてバックログに記録する。

## §4 殿堂入りシステム拡張: ドーム加点

### 4.1 現状

`Engine.awards.calcHofPoints` (L10858) は以下のポイント体系で動いている:

| イベント | ポイント |
|---|---:|
| タイトル戴冠/防衛 | 各 1pt |
| ジュニアトーナメント優勝 | 4pt |
| **PPV GRAND FINAL 優勝** | **5pt** |
| 対抗戦勝利 | 1.5pt |
| MVP受賞 | 2pt |
| ベストマッチ受賞 | 1pt |
| メディア賞 | 1.5pt |
| ルーキー賞 | 1.5pt |

しきい値: 15pt = 殿堂入り(★1) / 22pt = ゴールド(★2) / 35pt = レジェンド(★3)

### 4.2 提案: ドームメイン加点を追加

新しいイベントタイプ `domeMain` を追加し、以下のルールで殿堂入りポイントに加算:

| 条件 | 加点 |
|---|---:|
| ドーム興行のメインイベント または タイトルマッチに出場、かつ **勝利** | **+3pt** |
| ドーム興行のメインイベント または タイトルマッチに出場、かつ **敗北** | **+1pt** |

### 4.3 ポイント体系内での位置付け

- **PPV GRAND FINAL優勝(5pt)** > **ジュニアトーナメント優勝(4pt)** > **ドームメイン勝利(3pt)** > **MVP受賞(2pt)** > **対抗戦勝利(1.5pt)** > **タイトル防衛(1pt)** > **ドームメイン敗北(1pt)** > **ベストマッチ(1pt)**

PPV/ジュニアトーナメントより少し下、対抗戦勝利より上の位置付け。シーズン1回のドーム出場で最大3ptなので、ドーム3〜5回出場(≒4〜5シーズン)で殿堂入りに大きく寄与する重みになる。

### 4.4 実装方針

```javascript
// Engine.awards.calcHofPoints に追加
const domeMainPt = hist.filter(e => e.type === 'domeMain' && e.result === 'win').length * 3
                 + hist.filter(e => e.type === 'domeMain' && e.result === 'lose').length * 1;
return titlePt + juniorPt + ppvPt + warPt + mvpPt + rookiePt + bestMatchPt + mediaPt + domeMainPt;
```

`domeMain` イベントの記録は、興行終了処理で以下の条件のときに `careerRecord.history` に push:
- `state.showVenue === 9` (ドーム)
- 該当試合がメインイベント枠 OR タイトルマッチ
- 出場選手それぞれに勝敗結果を付けて記録

### 4.5 「殿堂入り」関連の用語チェック

既存の `buildCareerHighlights` (L10881) でドーム出場をハイライトとしてテキスト化する処理も追加する想定:

```
S25 第10シーズン ドーム公演メインイベント 勝利
```

これは選手プロフィールや殿堂入り選手紹介画面で表示される。

## §5 ドーム年1回制限

### 5.1 ルール

- **ドーム会場(venue idx 9)での興行は、1シーズンに最大1回まで**
- 既に同シーズン内で打っている場合、会場選択UIでドームを選択不可(or 警告)

### 5.2 実装方針

`state` に `domeShowsThisSeason: 0` (シーズン開始時にリセット) を追加。

会場選択時のバリデーション:
```javascript
if (venueIdx === 9 && (state.domeShowsThisSeason || 0) >= 1) {
  // ドーム選択不可、UIで「今シーズンは既にドーム興行を開催済み」と表示
}
```

ドーム興行終了時に `domeShowsThisSeason++`、シーズン更新時に 0 にリセット。

### 5.3 設計意図

- ドームを「年1回の特別興行」として位置付ける
- 「ドーム連発戦略」を不可能にする
- プレイヤーがドーム興行のタイミングを慎重に選ぶ動機を作る (「いつ打つか」が戦略要素になる)

## §6 経営画面リネーム + orgPop推移グラフ

### 6.1 現状

「収支」画面でシーズン収入/支出の内訳を表示している。

### 6.2 提案

「収支」を **「経営」** にリネームし、サブセクションとして以下を統合:

```
[経営]
├ 収支         （現状の収支内訳）
├ 団体人気推移 （新設: 過去20-30シーズンの orgPop グラフ）
└ (将来拡張: 集客推移、★平均推移など)
```

orgPop 推移グラフの仕様:
- 横軸: シーズン (過去 20-30 シーズン分)
- 縦軸: orgPop (0-100)
- 折れ線グラフ
- ホバー or タップで該当シーズンの値を表示
- データソース: `state.seasonHistory[].peakPop` または `orgPop`

### 6.3 設計意図

プレイヤーが因果を理解する手段を「計算式を見せる」ではなく「結果の推移を見せる」に集約する。グラフを見れば「あ、シーズン20のあたりで成長止まったな」「シーズン25から少し落ちてる」など、自分のプレイ履歴と照らし合わせて自然に気付ける。

## §7 年始の小芝居 (シーズン末年次減衰の見せ方)

### 7.1 概要

シーズン更新時の年次減衰(`calcAnnualDecay`)は現在サイレントに削られている。これをプレイヤーに見せる手段として、**「年始の恒例イベント」として選手と団体長(プレイヤー)の対話シーン**を追加する。

### 7.2 デザインの方向性 (確定事項のみ記載)

- 新聞通知ではなく **対話形式の小芝居**
- 各シーズン開始週に1回発生
- 王者 or エース選手 or ランダムなロスター選手と団体長の対話
- 内容は orgPop 帯ごとに変化:
  - 50未満: 「まだまだここから」と前向き
  - 50-80: 「ファンが増えてきましたね」と手応え
  - 80+: 「去年は良い興行が多かった、でも今年はもっと話題が必要かも」と維持の話題
  - 90+: 「頂点を保つのは大変ですね…」と維持コストへの言及
- **対話の中で前シーズンからの orgPop 変動を自然に織り込む** (数字を直接出すかは演出次第)
- 選手の反応文はランダム or 関係性ベースで複数バリエーション
