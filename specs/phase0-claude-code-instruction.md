## ■ 修正1: B系大型イベントの発火レート引き上げ

**対象**: engine.js `generateWeeklyEvent` 内の種別重み配分 + `generateLargeEvent` 内のクールダウン

### 現状の問題
- 種別重み: 通知型50% / 選択型40% / 大型10%
- 基本発生率25%/週 × 大型枠10% = 実効2.5%/週
- クールダウン8週
- → B系イベントは約5シーズンに1回しか起きない。人間関係システムのトリガーとして機能しない

### 修正内容
1. 種別重みを変更:
   - 変更前: 通知50% / 選択40% / 大型10%
   - 変更後: **通知35% / 選択25% / 大型40%**
   - コード箇所: `generateWeeklyEvent` 内の `roll < 0.50` / `roll < 0.90` の閾値
   - 変更後: `roll < 0.35`（通知）/ `roll < 0.60`（選択）/ else（大型=40%）

2. クールダウンを短縮:
   - 変更前: `absWeek - lastLarge < 8`
   - 変更後: **`absWeek - lastLarge < 4`**
   - コード箇所: `generateLargeEvent` 冒頭

### 期待される結果
- 実効レート: 25% × 40% = 10%/週
- CD4週で実質4〜5回の判定機会/シーズン × 10% → 1〜2回/シーズン
- B1〜B4の重み比率（3:2:2:3）は変更しない

## ■ 修正2: B4 trust直接加算の不整合修正

**対象**: engine.js `processMediaSpotlight` 内の大成功時trust処理

### 現状の問題
- L8633付近: `trust: Engine.util.clamp((f.trust != null ? f.trust : 50) + 3, 0, 100)`
- 他のすべてのtrust変動は `Engine.trust.applyCoeff`（mentalCoeff）+ `gainMult`（高trust帯逓減）を経由するが、B4の大成功だけ直接加算

### 修正内容
- trust +3 を `applyCoeff` + `gainMult` 経由に変更
- 同じ関数内にある `applyTrust` ヘルパーの書き方を参考にすること（`applyLargeEventEffect` 内に実装例あり）
- 反骨心の ×1.3 も適用すること

## ■ 修正3: 因縁決着のorgPopボーナス追加

**対象**: engine.js `applyPPVResults` 内の因縁決着処理（L5436付近の `orgPopBonus: 0` 固定箇所）

### 現状の問題
- 因縁決着はPPV限定 → PPVは合同大会のため `orgPopBonus` が常に0
- 因縁を育てて決着させても団体的報酬がゼロ

### 修正内容
- 因縁決着時に直接orgPopを加算するパスを追加（合同大会の通常orgPop処理とは別枠）
- 1回目決着（宿敵決着）: orgPop **+1.5**（`Engine.orgPop.applyOrgPopChange` の逓減適用）
- 2回目決着（宿命の相手 最終決着）: orgPop **+2.5**（同上）
- イベントログにもorgPop変動を表示すること

### 数値の根拠
- ①スケール: orgPopは0〜100、通常の週次変動は±0.5〜2程度
- ②相対比較: 通常興行の好成績orgPop+1〜2に対し、決着は特別だが過大ではない範囲
- ③プレイ体験: 因縁を育てた報酬として実感でき、かつ決着連発で破綻しない（最大2回/ペア）

## ■ 修正4: B3辞退ペナルティ追加

**対象**: app.js のB3イベント辞退処理（`_executeLargeEventMatch` 内、B3の辞退選択肢）

### 現状の問題
- 辞退してもペナルティゼロ → リスクなしで断れるため辞退が最適戦略

### 修正内容
- 辞退時に **orgPop -1**（`Engine.orgPop.applyOrgPopChange` の逓減適用）を追加
- イベントログに「対抗戦を辞退した（団体人気 -X）」を表示

### 数値の根拠
- ①スケール: orgPop -1は軽微だが「タダでは断れない」心理的コスト
- ②相対比較: B3勝利時の+3と比べて辞退のコストは低い → 無理なら断っても致命傷にはならない
- ③プレイ体験: 「受けるリスク vs 断るコスト」のジレンマを生む

## ■ 修正5: 乱入クールダウン追加

**対象**: engine.js `Engine.intrusion.check`

### 現状の問題
- クールダウンなし → 理論上連続発動可能（確率4%だが効果が破壊的）

### 修正内容
- state に `lastIntrusionWeek` フィールドを追加（絶対週数を記録）
- `check` 関数の冒頭に条件追加: **前回乱入から28週未満なら即 `return null`**
- 絶対週数の計算: `(state.season - 1) * 52 + state.week`（既存の `absWeek` 計算と同じ方式）
- 乱入発生時（`applyResult` 呼び出し元）に `lastIntrusionWeek` を現在の絶対週数で更新

### 28週の根拠
- ①スケール: 1シーズン=52週。28週は約6.5ヶ月
- ②相対比較: シーズン制限だと境界でのリセットが不自然。28週なら「前回から半年以上空く」自然な間隔
- ③プレイ体験: シーズン中盤で食らったら次シーズン序盤まで来ない安心感。ただし防衛3回条件もあるため実質的には1年近く空くことが多い

## ■ 修正6: 乱入heat変動の見直し

**対象**: engine.js `Engine.intrusion.applyResult` 内の乱入者勝利時heat処理

### 現状の問題
- L996: `const penalty = -(15 + Engine.rng.int(rng, 0, 5))` → 常に-15〜-20
- heatの通常変動（±1〜3/週）と比べて下限も上限も壊滅的
- 結果が常に「致命傷」で、振れ幅による緊張感がない

### 修正内容
- 変更後: **`const penalty = -(7 + Engine.rng.int(rng, 0, 13))`** → **-7〜-20**
- 下限-7: 「助かった…3〜4週で立て直せる」
- 上限-20: 「シーズン終了レベルの致命傷」
- この振れ幅自体がプレイヤーに恐怖と緊張感を与える

### 数値の根拠
- ①スケール: heatは通常±1〜3/週で変動。-7は約3週分、-20は約10週分
- ②相対比較: 他の大型イベントの最大ペナルティ（B2放置のmorale -10等）と比べ、乱入者勝利は最悪級のペナルティとして位置づける
- ③プレイ体験: 「乱入されたら終わりかもしれない」という恐怖。ただし運が良ければ軽傷で済む可能性もあり、毎回同じ絶望にはならない
