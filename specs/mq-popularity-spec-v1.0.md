## 設計原則

1. **バトルエンジンの出力をそのままスコア化** — 試合の「ドラマ度」を客観的に数値化する。外部パラメータを極力持ち込まない
2. **MQが経済を駆動する** — MQ→個人人気→集客→収入、MQ→Heat→集客倍率の2本のパスで経済システムに流れる
3. **好試合の再現性に不確実性を残す** — 強い選手を組めば確実にMQが高いわけではない。展開の運も絡む設計
4. **人気はMQ以外でも動く** — プロモ・勝敗・カード位置も人気変動に寄与し、育成フェーズとのトレードオフを生む
5. **Heatは団体の「勢い」** — 直近の興行結果の累積で動く。維持には継続的な好カードが必要

## §1 MQスコア（マッチクオリティ）

### §1.1 概要

MQスコアは**1試合ごとに算出される0〜100の品質評価値**。バトルエンジンの試合ログから自動計算する。

| 項目 | 値 |
|------|---|
| 値域 | 0〜100（整数） |
| 算出タイミング | 試合終了直後 |
| 表示 | 星評価に変換して表示（§1.7） |
| 影響先 | 個人人気変動（§2）、Heat変動（§4）、シーズン表彰 |

### §1.2 MQスコア構成

MQスコアは**5つの構成要素**の合計で算出する。

```
MQ = Base + Drama + Pacing + Finish + Bonus
MQ = clamp(MQ, 0, 100)
```

| 構成要素 | 略称 | 内容 | 値域 |
|---------|------|------|:----:|
| 基礎点 | Base | 両選手の実力から決まる下地 | 10〜35 |
| ドラマ点 | Drama | 試合中の見せ場の数と質 | 0〜35 |
| ペース点 | Pacing | 試合長の適切さ | -10〜+10 |
| 決着点 | Finish | 決着タイプの満足度 | -5〜+15 |
| ボーナス点 | Bonus | カード枠・推奨・興行種別等の外部補正 | 0〜30 |

### §1.3 Base（基礎点）: 10〜35

両選手の実力が高いほど「レベルの高い試合」になる土台。ただし基礎点だけでは凡戦と名勝負の差は出ない。

```javascript
avgOverall = (fighter_A.overall + fighter_B.overall) / 2

if (avgOverall <= 50)  Base = 10
else if (avgOverall <= 70)  Base = 10 + (avgOverall - 50) × 0.5   // 10〜20
else if (avgOverall <= 90)  Base = 20 + (avgOverall - 70) × 0.5   // 20〜30
else  Base = 30 + min(5, (avgOverall - 90) × 0.25)                // 30〜35

Base = clamp(round(Base), 10, 35)  🔧
```

**設計意図**:
- 新人同士（Overall 40〜50）でも Base=10 は確保される。ドラマ次第で50台の好試合は可能
- トップ同士（Overall 90+）で Base=30+。ここにドラマが乗ると80超えの名勝負になる
- Overall差が大きいマッチメイクへのペナルティは**ない**（スコアッシュ試合はPacing/Dramaで自然に低くなる）

### §1.4 Drama（ドラマ点）: 0〜35

バトルエンジンのイベントログから「見せ場」を拾い上げてスコア化する。**MQの最大の変動要因**。

| ドラマイベント | 1回あたりの得点 🔧 | 上限回数 🔧 | 備考 |
|--------------|:-----------------:|:---------:|------|
| キックアウト | +7 | 2 | 3回目は確定フォールなので発生しない |
| ロープブレイク（ギブアップ脱出） | +7 | 2 | キックアウトと同等のドラマ |
| フォール狙い失敗（ニアフォール） | +5 | 3 | HP残で返す「もう少しだった」感 |
| カウンター | +3 | 4 | 流れが変わる瞬間。多すぎると価値が薄れるので上限あり |
| 粘りバフ（Grit）発動 | +2 | 2 | キックアウト/ロープブレイクに含まれるが、粘り演出として追加加点 |
| モメンタム大逆転 | +3 | 3 | モメンタムの符号が反転した瞬間（+30以上の変動）|
| 丸め込み失敗 | +2 | 2 | 「危なかった！」の演出 |

```javascript
Drama = kickouts × 7
      + ropeBreaks × 7
      + nearFalls × 5
      + min(counters, 4) × 3
      + gritActivations × 2
      + momentumSwings × 3
      + rollupFails × 2

Drama = clamp(Drama, 0, 35)  🔧
```

**設計意図**:
- キックアウト2回＋ニアフォール2回＋カウンター3回 = 14+10+9 = 33点（ほぼ上限）→ これが「名勝負」の展開
- 一方的なスコアッシュ（イベントなし）→ Drama=0。Baseが高くても「凡戦」になる
- バトルエンジンの統計値（キックアウト0-2回/試合、カウンター1-3回/試合）から、平均的な試合でDrama=10〜18程度になる設計

### §1.5 Pacing（ペース点）: -10〜+10

試合長の「ちょうどよさ」を評価する。短すぎるスコアッシュも、だらだら長い試合も減点。

```javascript
turns = 試合のターン数

if (turns >= 10 && turns <= 16)  Pacing = +10       // 理想帯（ベストペース）
else if (turns >= 8 && turns <= 18)  Pacing = +5    // 許容帯
else if (turns >= 6 && turns <= 20)  Pacing = 0     // 短めor長め
else if (turns < 6)  Pacing = -10                    // スコアッシュ（極端に短い）
else  Pacing = -5                                    // タイムアップ域
```

🔧 上記の閾値は全て調整可能パラメータ

**設計意図**:
- バトルエンジンの平均ターン数は13.9。10〜16ターンが「理想帯」
- 5ターン以下の瞬殺は大幅減点。実力差が大きいマッチメイクへの間接的なペナルティになる
- タイムアップ（20ターン超）は別途Finishでも減点される

### §1.6 Finish（決着点）: -5〜+15

決着タイプによる観客満足度。クリーンフィニッシュは高評価、凡戦決着は低評価。

| 決着タイプ | 得点 🔧 | 追加条件 |
|-----------|:------:|---------|
| フォール（Climaxフェーズ） | +15 | 最終盤でのフォール勝ち。最高の決着 |
| フォール（End以前） | +10 | 十分にクリーン |
| ギブアップ（Climaxフェーズ） | +15 | submissionフィニッシュ。ドラマチック |
| ギブアップ（End以前） | +10 | |
| TKO | +8 | 圧倒的だが見応えはある |
| 丸め込み | +12 | 番狂わせの興奮 |
| フォール狙い成功（ピン） | +12 | HP残からの3カウント。サプライズ性が高い |
| タイムアップ（判定） | -5 | 決着がつかない不満 |

```javascript
// Climax到達ボーナス（フォール・ギブアップ）
if (finishType === 'fall' || finishType === 'giveup') {
  Finish = (finishPhase === 'Climax') ? 15 : 10
}
else if (finishType === 'tko')     Finish = 8
else if (finishType === 'rollup')  Finish = 12
else if (finishType === 'pin')     Finish = 12
else if (finishType === 'timeout') Finish = -5
```

**設計意図**:
- Climaxフェーズまで行って決着 = 観客が最も盛り上がる展開 → 最高点
- 丸め込み/フォール狙い成功は「まさか！」の驚き補正で高得点
- タイムアップは唯一のマイナス。実力差が小さく両者堅い試合でも「決着がつかない」のはファン的に不満

### §1.7 Bonus（ボーナス点）: 0〜30

試合の外部コンテキストによる加点。**既存システムで予約済みのフック**をそのまま適用する。

| ボーナスソース | 得点 🔧 | 参照元 |
|-------------|:------:|-------|
| メインイベント枠 | +10 | weekly-gameloop §4.2 |
| セミファイナル枠 | +5 | weekly-gameloop §4.2 |
| 推奨カード ★★★ | +10 | weekly-gameloop §4.4 |
| 推奨カード ★★ | +5 | weekly-gameloop §4.4 |
| タイトルマッチ（メイン枠） | +5 | weekly-gameloop §4.3 |
| 特別興行補正 | +3 🔧 | 特別興行の舞台効果 |
| PPV補正 | +5 🔧 | PPVの特別感 |

```javascript
Bonus = slotBonus + recommendBonus + titleBonus + eventBonus
Bonus = clamp(Bonus, 0, 30)  🔧
```

**設計意図**:
- メイン＋推奨★★★＋PPV＋タイトルマッチ = +10+10+5+5 = 30（理論上限）
- これらは「どのカードを組むか」というプレイヤーの戦略的判断に報いる加点
- アンダーカードの推奨なしカードはBonus=0。試合内容（Drama/Base）だけで勝負する

### §1.8 MQスコアの期待分布

バトルエンジンの統計値（v4.1b tuneB基準）と組み合わせた場合の目安。

| MQ帯 | 星評価 | 期待される試合内容 | 出現頻度（推定）🔧 |

| 20〜39 | ★ | 平凡な試合。見せ場が少ない | 〜25% |
| 40〜59 | ★★ | そこそこの好試合。ドラマが1〜2回 | 〜35% |
| 60〜74 | ★★★ | 好勝負。キックアウトやカウンターが光る | 〜20% |
| 75〜89 | ★★★★ | 名勝負。複数のニアフォール＋Climaxフィニッシュ | 〜10% |

## §2 個人人気

### §2.1 概要

個人人気は**各選手が持つ0〜100のファン支持度**。集客力・グッズ売上に直結する。

| 項目 | 値 |
|------|---|
| 値域 | 0〜100（整数） |
| 初期値 | 入団時のOverallに応じて設定（§2.2） |
| 変動タイミング | 試合後・プロモ後・週末処理時 |
| 影響先 | 集客計算（economy §3.3）、グッズ収入（economy §4.1）、メインペナルティ判定（weekly §4.3） |

### §2.2 初期人気

| 条件 | 初期個人人気 🔧 |
|------|:-------------:|
| 新人（Overall 〜49） | 5 |
| 若手（Overall 50〜64） | 15 |
| 中堅（Overall 65〜79） | 30 |
| 主力（Overall 80〜89） | 50 |
| トップ（Overall 90〜） | 65 |
| フリー選手→正式契約時 | 契約時Overall準拠 + 5（対戦歴ボーナス）|

### §2.3 試合後の人気変動

試合終了時に、**出場した両選手**の個人人気が変動する。

```javascript
// 基本変動値
mqBonus = MQ_to_popGain(matchMQ)   // MQスコアから変換（§2.4）
winBonus = isWinner ? +2 : 0       // 勝者ボーナス 🔧
loseBonus = isLoser ? -1 : 0       // 敗者ペナルティ 🔧（軽微）

// カード位置補正
slotMult = (slot === 'main') ? 1.5 : (slot === 'semi') ? 1.2 : 1.0  🔧

// 番狂わせ補正（弱者が勝った場合）
upsetBonus = 0
if (isWinner && own.overall < opponent.overall - 15) {
  upsetBonus = +3  🔧  // 格上に勝つと人気急上昇
}

// 最終変動
popChange = round((mqBonus + winBonus + loseBonus + upsetBonus) × slotMult)

// 適用
newPop = clamp(fighter.popularity + popChange, 0, 100)
```

### §2.4 MQ→人気変換テーブル

MQスコアに応じた試合1回あたりの人気獲得量。

| MQ帯 | 星評価 | 人気変動（基本値）🔧 |
|:-----:|:-----:|:------------------:|
| 0〜19 | ☆ | -2（悪印象） |
| 20〜39 | ★ | 0（変動なし） |
| 40〜59 | ★★ | +2 |
| 60〜74 | ★★★ | +4 |
| 75〜89 | ★★★★ | +6 |
| 90〜100 | ★★★★★ | +8 |

**設計意図**:
- ★以下の凡戦は人気が**下がる**。悪い試合をメインに組むリスク
- ★★★以上を安定して出せれば、2週に1回の興行で人気が着実に上がる
- メイン枠（×1.5）なら ★★★★（+6 × 1.5 = +9）で一気に伸びる
- 人気100到達には相当な好試合の積み重ねが必要

### §2.5 プロモによる人気変動

週間スケジュールで「プロモ」を選択した週の効果。

```javascript
promoGain = 2 + round(fighter.charisma × 0.03)  🔧
// charisma = MNT（精神力をカリスマの代用値として使用）

newPop = clamp(fighter.popularity + promoGain, 0, popCap)
```

| MNT値 | プロモ1回の人気増加 🔧 |
|:-----:|:-------------------:|
| 40 | +3 |
| 60 | +4 |
| 80 | +4 |
| 100 | +5 |

**プロモの人気上限（popCap）**:

プロモだけでは人気に天井がある。高い人気は試合で証明しないと得られない。

```javascript
popCap = 40  🔧  // プロモのみで到達できる人気の上限
```

**設計意図**:
- プロモは「安全に人気を稼ぐ手段」だが、上限40で頭打ち
- 40を超えるには試合で好MQを出す必要がある → 練習 vs プロモのトレードオフが成立
- MNT（精神力）が高い選手 = カリスマがある = プロモが上手い、というフレーバー

### §2.6 人気の自然減衰

試合にもプロモにも出ない週が続くと人気が下がる。怪我離脱中も減衰する。

```javascript
// 2週間連続で試合にもプロモにも出ていない場合
if (weeksInactive >= 2) {
  decay = 1  🔧  // 2週ごとに-1
  fighter.popularity = max(0, fighter.popularity - decay)
}
```

**設計意図**:
- 怪我で離脱すると人気がじわじわ下がる → コンディション管理の重要性を裏付ける
- 減衰は緩やか（2週で-1）。短期の怪我ならほぼ影響なし
- 長期離脱（8週以上）だと-4程度。復帰後に取り戻す必要がある

## §3 団体人気

### §3.1 概要

団体人気は**団体全体のブランド力を示す0〜100の値**。会場解放・スポンサー・放映権収入に直結する。

| 項目 | 値 |
|------|---|
| 値域 | 0〜100（整数） |
| 初期値 | 10 🔧 |
| 変動タイミング | 興行終了後（2週に1回） |
| 影響先 | 会場解放（economy §3.1）、スポンサー（economy §4.2）、放映権（economy §4.3）、集客基本値（economy §3.3） |

### §3.2 興行後の団体人気変動

各興行の結果に基づいて変動する。

```javascript
// ① 興行MQ平均
showAvgMQ = 興行内全試合のMQスコア平均

// ② MQ平均からの変動値
mqDelta = orgPop_from_MQ(showAvgMQ)  // §3.3テーブル参照

// ③ 集客率補正
attendanceRate = 実集客 / 会場キャパ
if (attendanceRate >= 0.9)      attBonus = +2  🔧  // 満員御礼
else if (attendanceRate >= 0.7) attBonus = +1
else if (attendanceRate >= 0.5) attBonus = 0
else if (attendanceRate >= 0.3) attBonus = -1
else                            attBonus = -2  // ガラガラ

// ④ 特別興行・PPV補正
eventBonus = 0
if (isPPV)             eventBonus = +3  🔧
else if (isSpecial)    eventBonus = +1  🔧

// ⑤ 最終変動
orgPopChange = mqDelta + attBonus + eventBonus
orgPopChange = clamp(orgPopChange, -5, +8)  🔧

newOrgPop = clamp(orgPop + orgPopChange, 0, 100)
```

### §3.3 興行MQ平均→団体人気変動テーブル

| 興行MQ平均 | 団体人気変動 🔧 |
|:---------:|:-------------:|
| 0〜29 | -3 |
| 30〜44 | -1 |
| 45〜54 | 0 |
| 55〜64 | +1 |
| 65〜74 | +2 |
| 75〜84 | +3 |
| 85〜100 | +5 |

**設計意図**:
- 興行MQ平均55以上を維持すれば団体人気は緩やかに上昇
- MQ平均45未満が続くと下降。「質の低い興行を繰り返すと団体が衰退する」
- PPVで+3ボーナスがあるため、年間最大の興行で好試合を連発すれば一気に伸びる
- 1興行あたり最大+8なので、団体人気0→95には最低12興行（24週）必要。現実的なペースでは1〜2シーズンかかる

### §3.4 団体人気の自然減衰

```javascript
// 非興行週に毎週適用（興行週は§3.2の変動が優先）
if (非興行週) {
  orgPop = max(0, orgPop - 0.5)  🔧  // 2週で-1（興行がないと少し下がる）
}
```

**設計意図**:
- 2週に1回の興行サイクルでは、非興行週の-0.5と興行週の変動が打ち消し合う構造
- 興行MQ平均55以上を維持すれば「非興行週-0.5 + 興行週+1 = 2週で+0.5」で微増
- 怪我で主力が欠場→MQ低下→団体人気も下がる、という連鎖が自然に発生

## §4 Heatシステム

### §4.1 概要

Heatは**団体の「勢い」を示すランクシステム**。集客倍率に直結し、経済の生命線となる。

| 項目 | 値 |
|------|---|
| 内部値 | HeatPoints: 0〜100（整数） |
| ランク | 5段階（COLD / NEUTRAL / WARM / HOT / HEAT） |
| 初期値 | HeatPoints = 30（NEUTRAL） |
| 変動タイミング | 興行終了後 |
| 影響先 | 集客倍率（economy §3.3）、次シーズン開幕Heat |

### §4.2 Heatランクテーブル

| HeatPoints | ランク | 集客倍率（economy §3.3準拠） |
|:----------:|:------:|:------------------------:|
| 0〜19 | COLD | ×0.7 |
| 20〜39 | NEUTRAL | ×1.0 |
| 40〜59 | WARM | ×1.2 |
| 60〜79 | HOT | ×1.5 |
| 80〜100 | HEAT | ×1.8 |

### §4.3 Heat変動

```javascript
// ① 興行MQ平均からの基本変動
heatMQDelta = heat_from_MQ(showAvgMQ)  // §4.4テーブル参照

// ② メインイベントMQボーナス（メインの出来が特に影響）
mainMQ = メインイベントのMQスコア
if (mainMQ >= 80)       mainBonus = +5  🔧
else if (mainMQ >= 65)  mainBonus = +3
else if (mainMQ >= 50)  mainBonus = +1
else                    mainBonus = -2  // メインが凡戦だと冷める

// ③ 連続好興行ボーナス（勢いの加速）
if (直近3興行のMQ平均 >= 65) streakBonus = +3  🔧
else streakBonus = 0

// ④ 変動適用
heatChange = heatMQDelta + mainBonus + streakBonus
heatChange = clamp(heatChange, -8, +12)  🔧

newHeatPoints = clamp(heatPoints + heatChange, 0, 100)
```

### §4.4 興行MQ平均→Heat変動テーブル

| 興行MQ平均 | Heat変動 🔧 |
|:---------:|:----------:|
| 0〜29 | -6 |
| 30〜44 | -3 |
| 45〜54 | -1 |
| 55〜64 | +1 |
| 65〜74 | +3 |
| 75〜84 | +5 |
| 85〜100 | +8 |

**設計意図**:
- Heatは団体人気より**変動が大きい**。勢いは一気に上がるが、一気に冷めもする
- MQ平均55未満が2〜3興行続くとNEUTRAL→COLDに転落しうる
- 逆に好興行が続けばHOT→HEATへの加速ボーナスも乗る
- メインイベントの出来が特に重要 → 「メインに誰を組むか」の判断がHeatを左右する

### §4.5 Heatの自然減衰

```javascript
// 非興行週に毎週適用
heatPoints = max(0, heatPoints - 1)  🔧
```

- Heatは**放っておくと下がる**。維持には継続的な好興行が必要
- 2週で-2（非興行週のみ）。HOT(60)からNEUTRAL(39)に落ちるまで約20週（怠惰な場合）
- これがeconomy §7.2の「NETURALのままでは赤字が続く」設計と整合する

### §4.6 シーズン間のHeat継承

```javascript
// オフシーズン終了時
if (PPV_MQ >= 80)  nextSeasonHeat = min(100, heatPoints + 10)  🔧
else if (PPV_MQ >= 60)  nextSeasonHeat = heatPoints
else  nextSeasonHeat = max(0, heatPoints - 10)  🔧

// さらにオフ期間（4週）の自然減衰
nextSeasonHeat = max(0, nextSeasonHeat - 4)  🔧
```

**設計意図**:
- PPV（年間最大興行）の結果が次シーズンの開幕に影響 → PPVは「一年の集大成」
- PPVで好試合を連発すれば勢いを維持したまま新シーズンに入れる
- PPVが凡戦だとオフシーズン中にHeatが大幅に下がる → 復調に時間がかかる

## §5 集客計算の具体化（economy §3.3/§9の確定）

economy-system-spec-v1.0 で未確定だった項目をここで確定する。

### §5.1 集客計算の完全式

```javascript
// ① 基本集客（団体人気×会場キャパ係数）の具体化
baseAttendance = 会場キャパ × (orgPop / 100)  🔧

// ② カード補正（メイン選手の個人人気）
mainPopSum = メインイベント両選手の個人人気合計
cardBonus = mainPopSum × (会場キャパ / 100) × 0.03  🔧

// ③ Heat補正（economy §3.3準拠）
heatMult = HeatランクのMult値（§4.2）

// ④ メインペナルティ（weekly §4.3準拠）
mainPenalty = (mainPopSum < 40) ? 0.8 : 1.0

// ⑤ 推奨カード集客ボーナス（weekly §4.4準拠）
recommendMult = 1.0 + 推奨カードの集客ボーナス合計

// ⑥ 興行種別チケット単価倍率
ticketMult = (isPPV) ? 1.5 : (isSpecial) ? 1.3 : 1.0

// 実集客
rawAttendance = (baseAttendance + cardBonus) × heatMult × mainPenalty × recommendMult
actualAttendance = min(会場キャパ, round(rawAttendance))

// チケット収入
ticketRevenue = actualAttendance × チケット単価 × ticketMult
```

### §5.2 シミュレーション例

| シナリオ | 団体人気 | 会場 | メイン人気合計 | Heat | 実集客 | チケット収入 |
|---------|:------:|:----:|:-----------:|:----:|:-----:|:---------:|
| 序盤 | 10 | 公民館(200) | 10 | NEUTRAL | 23人 | 7万 |
| 序盤・WARM | 15 | 公民館(200) | 20 | WARM | 48人 | 14万 |
| 序盤・頑張り | 20 | 小ホール(500) | 30 | WARM | 144人 | 58万 |
| 中盤 | 45 | 中ホール(1500) | 80 | HOT | 1,072人 | 536万 |
| 中盤・HEAT | 50 | 中ホール(1500) | 100 | HEAT | 1,404人 | 702万 |
| 終盤 | 80 | アリーナ(5000) | 150 | HOT | 6,225人→5,000(キャパ) | 3,000万 |

> ※ economy §7.1の序盤シミュレーション（公民館満員200人、利益30万）との整合性を考慮すると、序盤の集客計算は初期状態では厳しい。**序盤の集客下限値**を設ける必要あり。

### §5.3 最低保証集客

```javascript
// どんな状況でも最低限の観客は来る
minAttendance = round(会場キャパ × 0.10)  🔧  // キャパの10%
actualAttendance = max(minAttendance, actualAttendance)
```

- 公民館（200人）→ 最低20人。チケット収入6万
- これにより完全にゼロにはならないが、赤字は確定する → 早期の人気構築が重要

## §7 興行MQスコア（ショーレーティング）

個別試合のMQに加えて、**興行全体の評価値**も算出する。

### §7.1 計算式

```javascript
showRating = 興行内全試合のMQ加重平均

// 加重: メイン×1.5、セミ×1.2、その他×1.0
weightedSum = Σ(match_MQ × slotWeight)
totalWeight = Σ(slotWeight)
showRating = round(weightedSum / totalWeight)
```

### §7.2 ショーレーティングの使用先

| 使用先 | 参照方法 |
|-------|---------|
| 団体人気変動 | §3.2の「興行MQ平均」として使用 |
| Heat変動 | §4.3の「興行MQ平均」として使用 |
| シーズン総括 | ベスト興行・ワースト興行の選出 |
| 実績表示 | 「今シーズンの平均ショーレーティング」としてUI表示 |

## §8 ヒール/ベビーフェイス相性補正

キャラクターデータのヒール度（heel alignment）を活用した試合相性ボーナス。

### §8.1 相性テーブル

ヒール度は0（完全ベビーフェイス）〜100（完全ヒール）の値を持つ。

```javascript
heelDiff = abs(fighter_A.heelAlignment - fighter_B.heelAlignment)

if (heelDiff >= 60)       chemistryBonus = +5  🔧  // ヒール vs ベビー（王道対決）
else if (heelDiff >= 40)  chemistryBonus = +3       // やや対照的
else if (heelDiff <= 15)  chemistryBonus = +2       // 同タイプ対決（同族嫌悪）
else                      chemistryBonus = 0        // 中間（ボーナスなし）
```

### §8.2 適用先

```
chemistryBonus は MQスコアの Bonus に加算する（§1.7のBonus上限30の内数）
```

**設計意図**:
- ヒール vs ベビーフェイスは観客が盛り上がる王道の構図 → MQにボーナス
- 同タイプ対決（ヒール同士）も「どちらが悪いか」の争いで盛り上がる → 小ボーナス
- 中間帯のキャラ同士は相性補正なし。試合内容で勝負

### §10.1 序盤シーズン（団体人気10〜20、選手5人）

