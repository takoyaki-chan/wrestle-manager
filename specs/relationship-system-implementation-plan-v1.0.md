## Phase 0：前提修正（B系イベント頻度＋不整合修正）

### 目的

人間関係システムのトリガーとなるイベントが、まともな頻度で発生する状態にする。
現状のB系大型イベントは25シーズンに1回程度しか起きず、トリガーとして機能しない。

### 作業内容

#### 0-1. B系大型イベントの発火レート見直し

- **現状**: 25%/週でイベント判定 → うち10%が大型 → 実効2.5%/週
- **目標**: 1シーズン（12週）にB系イベントが1〜2回発生する頻度
- **調整案**: 実効レートとクールダウンの組み合わせで調整
  - 実効レートを上げる（10%→高めに）
  - AND/OR 8週クールダウンを短縮（8週→4〜5週）
- **制約**: B1〜B4のバランスは維持。特定イベントだけ偏らないこと

#### 0-2. 設計不整合の修正

| 修正対象 | 現状 | 修正内容 |
|---|---|---|
| B4 trust直接加算 | `applyCoeff`/`gainMult`を経由しない | 他のtrust変動と同じくapplyCoeff経由にする |
| 因縁決着 orgPop=0 | PPV限定のためorgPopBonus無効化 | 決着ボーナスとして直接orgPopを加算するパスを追加 |
| B3 辞退ペナルティなし | リスクゼロで断れる | 辞退時にorgPop微減 or heat微減を追加 |
| 乱入クールダウンなし | 理論上連続発動可能 | 同シーズン内1回制限を追加 |

#### 0-3. 乱入のheat変動見直し

- **現状**: 乱入者勝利で heat -15〜-20（壊滅的）
- **検討**: heatの通常変動が±1〜3/週の中で一撃-15は過剰。適正値を精査

### Claude Code指示文テンプレート

```
リポジトリ: https://github.com/takoyaki-chan/wrestle-manager

Phase 0: B系大型イベント頻度修正＋不整合修正を実施する。

■ 修正1: B系大型イベントの発火レート
- engine.js の大型イベント判定ロジックを修正
- 目標: 1シーズン（12興行週）にB系が1〜2回発生する頻度
- 現状の実効2.5%/週を引き上げる
- 8週クールダウンを短縮する（4〜5週を検討）
- B1〜B4のバランス（重み比率）は維持

■ 修正2: B4 trust直接加算
- engine.js のB4大成功時trust変動をapplyCoeff/gainMult経由にする

■ 修正3: 因縁決着のorgPop
- engine.js の因縁決着処理に、PPVでもorgPopボーナスが入るパスを追加
- 1回目決着: orgPop +1.5、2回目決着: orgPop +2.5（orgPop逓減適用）

■ 修正4: B3辞退ペナルティ
- app.js のB3辞退処理にorgPop -1を追加

■ 修正5: 乱入クールダウン
- engine.js の乱入判定に、同シーズン内1回制限を追加
- state に lastIntrusionSeason 等のフラグを追加

■ 修正6: 乱入heat変動の見直し
- 乱入者勝利時の heat -15〜-20 を適正値に調整
- heatの通常変動（±1〜3/週）とのスケール感を考慮して提案してほしい

※各修正後、変更箇所と変更理由をコメントで記載すること
```

### 完了条件

- B系大型イベントが1シーズンに1〜2回発生することを確認
- 4つの不整合がすべて修正されていること
- 乱入が同シーズン内2回以上発生しないこと

## Phase 1：人間関係データ基盤

### 目的

GameStateにrelationshipsデータ構造を追加し、初期値生成・自然減衰・凍結が裏で動く状態にする。
この段階ではUI表示なし、ゲームプレイへの影響なし。

### 作業内容

#### 1-1. データ構造

- `GameState.relationships` に非対称2軸データを追加
- キー形式: `"charId_A→charId_B"` → `{ bond: number, rivalry: number }`
- 全9,506方向のエントリを保持

#### 1-2. 逓減カウンター

- `GameState.relationshipCounters` に同一ペア×同一イベント種別の累積回数を保持
- キー形式: `"charA→charB:eventType:stage"` → `{ count: number, lastWeek: number }`
- stage = 舞台区分（normal / ppv / title / war）
- 12週未発生でcount -1（カウンター減衰）

#### 1-3. 初期値生成

- ゲーム開始時（ドラフト完了後）に全ペアの初期値を生成
- ベース: bond=50, rivalry=0
- アーキタイプ相性マトリクス補正 + ガウス散らし
- 同団体メンバー同士: bond +3〜+8（同僚ボーナス）
- OVR差5以内: rivalry +2〜+6
- 性格・アーキタイプの相性補正（spec §5.2参照、具体値は実装時に決定）
- バックストーリー初期関係: 2〜4組をランダム生成

#### 1-4. 接触状態判定

- 毎週、全ペアの接触状態を判定
- 接触あり: 同団体 OR 直近4週以内に対戦
- 接触なし: 上記以外

#### 1-5. 自然減衰/凍結の週次処理

- tickWeek内に `Engine.relationships.processWeeklyDecay(state)` を追加
- 接触あり: bond→50方向に-0.2〜-0.3/週、rivalry -0.1〜-0.2/週
- 接触なし: bond凍結、rivalry -0.1/週
- 逓減カウンターの12週減衰チェック

#### 1-6. セーブ/ロード対応

- relationships と relationshipCounters を GameState の永続化対象に含める
- 既存セーブデータとの互換性を維持（relationshipsがない場合はロード時に生成）

### Claude Code指示文テンプレート

```
リポジトリ: https://github.com/takoyaki-chan/wrestle-manager
設計スペック: specs/relationship-system-spec-v0.2.md を参照

Phase 1: 人間関係データ基盤を実装する。

■ 実装内容
1. GameState に relationships データ構造を追加
   - 非対称2軸（bond/rivalry）× 9,506方向
   - キー形式: "charId_A→charId_B" → { bond, rivalry }

2. 逓減カウンターのデータ構造
   - "charA→charB:eventType:stage" → { count, lastWeek }

3. 初期値生成関数 Engine.relationships.initialize(state)
   - ドラフト完了後に呼ぶ
   - spec §5.1〜5.3 に従う（ベース50/0 + 相性補正 + 散らし）
   - 相性マトリクスの具体値はスペックの方向性に従い、
     ①スケール文脈 ②相対比較 ③プレイ体験 の3点で提案すること

4. 週次処理 Engine.relationships.processWeeklyDecay(state)
   - tickWeek内に追加
   - 接触判定（同団体 or 直近4週対戦）→ 減衰 or 凍結
   - spec §2.1 に従う

5. セーブ/ロード互換性
   - 既存セーブにrelationshipsがなければロード時に自動生成

■ この段階ではUI表示なし、MQ等への影響なし。データが裏で動くだけ。
■ テスト用にコンソールから値を確認できるヘルパー関数を用意すること
  例: Engine.relationships.inspect(state, charIdA, charIdB)
```

### 完了条件

- ゲーム開始後にrelationshipsデータが生成されていること
- 週を進めると接触あり/なしで減衰挙動が異なること
- 既存セーブデータのロードでエラーが出ないこと
- コンソールから任意のペアの関係値を確認できること

## Phase 2：試合結果の反映

### 目的

最も頻繁に発生するトリガー（毎週の試合結果）をbond/rivalryに接続する。

### 作業内容

#### 対象イベント（spec §3.1）

| ID | イベント | 逓減適用 |
|---|---|---|
| M-01 | 通常興行で対戦 | あり |
| M-02 | 僅差の好勝負 | あり（舞台別） |
| M-03a/b | 一方的な圧勝（勝者/敗者視点） | あり |
| M-04 | 名勝負（MQ80超） | あり（舞台別） |
| M-05 | PPV/GRAND FINALで対戦 | あり |
| M-06 | タイトルマッチで対戦 | あり |
| M-10 | 因縁決着 | なし（特殊イベント、最大2回） |
| M-11 | 怪我（post-match injury） | あり |
| M-12 | 連敗ストリーク | あり |
| M-13 | キャリアベストMQ更新 | なし（特殊イベント） |

#### 実装ポイント

- `finalizeShow` / `finalizePPV` の試合結果処理後に、bond/rivalry更新を呼ぶ
- 試合結果のコンテキスト（MQ値、勝敗差、舞台種別）から該当イベントを判定
- 逓減ルール（spec §2.3）を適用
- 値の上下限クランプ（0〜100）

### 完了条件

- 試合後にbond/rivalryが変動していること（コンソールで確認）
- 同じペアの同じ舞台での試合が逓減していること
- 名勝負 vs 凡戦 vs 圧勝で変動パターンが異なること

## Phase 3：団体運営・契約イベントの反映

### 目的

移籍・解雇・引退・レンタル等の団体運営イベントをbond/rivalryに接続する。

### 作業内容

#### 対象イベント（spec §3.2）

| ID | イベント |
|---|---|
| O-01 | 同団体に長期所属（週次） |
| O-02 | FA/スカウトで入団 |
| O-03 | 他団体に移籍 |
| O-04 | 引退 |
| O-05 | 契約更新成功 |
| O-06 | 契約更新失敗（退団） |
| O-07 | 解雇（release） |
| O-08 | 突然の離脱（sudden departure） |
| O-09 | 引き抜き（poach/transfer） |
| O-10 | レンタル加入 |
| O-11 | レンタル帰団 |
| O-12 | 引退勧告→拒否（prove mode） |
| O-13 | 引退撤回（retain） |

#### 実装ポイント

### 完了条件

- 移籍・解雇・引退時にbond/rivalryが変動すること
- 再接触イベントが発火すること（凍結状態からの合流時）

### 完了条件

- OVR差の変動でrivalryが動くこと

## Phase 5：ライバル称号システム統合

### 目的

既存のライバルシステム（因縁/宿敵/永遠のライバル）の昇格・降格条件を、人間関係データから導出する形に書き換える。

### 作業内容

#### 5-1. 昇格条件の書き換え

- 現行の対戦回数ベースの昇格判定を、rivalry閾値＋対戦回数の複合条件に変更
- spec §4.2 に従う

#### 5-2. 降格ロジックの追加

- 既存システムにない新機能
- spec §4.3 に従う（因縁消滅、宿敵→因縁降格、永遠のライバル→宿敵降格）

#### 5-3. 片側因縁の実装

- 新状態。片方のrivalryだけが高い場合
- MQボーナス+1（減額版）
- 「認知」イベントの実装

#### 5-4. 履歴管理

- 過去の因縁を記録（相関図でグレー表示用）
- `relationshipHistory` のデータ構造追加

### 完了条件

- rivalryの蓄積により因縁→宿敵→永遠のライバルが段階的に昇格すること
- rivalry低下＋対戦空白により降格が発生すること
- 片側因縁が機能すること（MQ+1）

## Phase 6：UI（人物相関図）

### 目的

人間関係データをプレイヤーに可視化する。

### 作業内容

#### 6-1. 選手詳細画面への関係リスト追加

- 選手詳細を開いた時に、その選手の主要な関係（上位10〜15名）をリスト表示
- bond/rivalryの帯域ラベルを表示

#### 6-2. 人物相関図（放射型）

- 中心に選択キャラ、周囲に関係者を配置
- 矢印2本（行き/帰り）で色・太さが異なる
  - 青系 = 好意・信頼、赤系 = 嫌悪・侮蔑
  - 線の太さ = 感情の強さ
  - オレンジ系の炎マーク = 競争意識
- 過去の因縁はグレー表示
- フィルタ：同団体のみ / ライバルのみ / 全体

#### 6-3. ライバル称号の表示統合

- 因縁/宿敵/永遠のライバルのラベルを相関図上に表示
- 片側因縁の表示

### 完了条件

- 選手詳細画面から関係リストが確認できること
- 人物相関図が表示され、フィルタが機能すること
- 称号が相関図上に表示されること

## フェーズ間の進め方

1. 各フェーズ開始前に、Claude Code指示文をチャットで確認
2. Claude Codeで実装
3. けいすけさんがローカルで動作確認
4. チャットで結果レビュー・数値調整の方針を決定
5. 必要なら追加修正をClaude Codeで実施
6. 問題なければ次のフェーズへ

**重要：Phase間を飛ばさない。** 各フェーズの完了条件を満たしてから次に進む。
