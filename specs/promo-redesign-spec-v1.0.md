## 背景と目的

現状の「プロモ」は人気を微量上げるだけで、上限55・逓減も厳しく、バランス（お任せ）の劣化版に近い。ハードモード序盤で補助金なしだと資金が回らない問題もある。

**改修コンセプト: プロモ＝商売**

プロモは選手がリング外で行う営業活動・ファンイベント。握手会、地域イベント出演、SNS配信、グッズ販売会など。ファンと直接お金が動く場であり、団体の現金収入に直結する。

**改修3点セット:**
1. 人気上限を55→70に引き上げ（逓減で自然に頭打ち）
2. プロモイベント収入の新設（人気帯別の直接現金収入）
3. MQ蓄積ボーナスの新設（試合前の煽り効果）
4. お任せロジックの最適化（無駄なプロモを回避）

## §2 プロモイベント収入

### §2-1 コンセプト

選手がプロモ活動をした週、その選手の人気に応じたイベント収入がポンと団体に入る。人気が低くても出れば稼げる（女子プロレスが日常の世界なので、頑張ってる子にはお金を払う人がいる）。

### §2-2 収入テーブル

```js
// data.js に追加
const PROMO_EVENT_INCOME = [
  { min:  0, max: 14, val:  15 },  // 地元の小イベント
  { min: 15, max: 29, val:  25 },  // 地域イベント常連
  { min: 30, max: 44, val:  40 },  // ファンミ・握手会
  { min: 45, max: 59, val:  55 },  // 単独イベント成立
  { min: 60, max: 74, val:  70 },  // メディア出演含む
  { min: 75, max:100, val:  85 },  // 大型イベント
];
```

### §2-3 スケール感の根拠

①scale: 週単位の収入。序盤の給与+固定費が約70万/週、興行収入が隔週125万程度。
②relative: 既存スポンサー収入（orgPop依存）は0〜200万/週。プロモ収入は1選手あたり15〜85万で、練習1週分を犠牲にする対価。
③play experience:
  - 序盤（pop20×2人プロモ）: 50万/週 → ハードモード赤字を救済できるが楽ではない
  - 中盤（pop45エース1人）: 55万/週 → 安定するが練習機会ロストのトレードオフ
  - 終盤（pop75エース）: 85万/週 → 興行収入が数百万の時期なので、練習を犠牲にする意味が薄れ、自然にプロモ卒業

### §2-4 複数選手のプロモ

各選手のイベント収入を単純合算する。3人プロモに出しても問題ない（ただし3人分の練習機会を失う）。

### §2-5 週次精算の表示

```
// Engine.economy.calcWeeklyFinance 内で計算
// プロモを実行した選手を集め、各選手の収入を合算
// 表示例:
💰 プロモ収入（佐藤選手 握手会）: +25万
💰 プロモ収入（田中選手 地域イベント）: +40万
```

既存の「スポンサー収入」（orgPop依存）とは**別枠**で表示する。

### §2-6 イベント名プール（演出用）

```js
// data.js に追加
const PROMO_EVENT_NAMES = {
  low:  ['地域イベント出演', '商店街キャンペーン', 'SNS配信', '地元FM出演'],
  mid:  ['握手会', 'ファンミーティング', 'トークショー', 'グッズ販売会'],
  high: ['大型イベント出演', 'TV番組出演', '雑誌撮影会', 'スペシャルショー'],

// pop < 30 → low、30-59 → mid、60+ → high からランダム選択
```

## §3 MQ蓄積ボーナス（promoStack）

### §3-1 仕組み

プロモを実行するたびに選手個人に `promoStack` が蓄積される。試合出場時にMQ外部ボーナスとして消費される。

```
■ 蓄積ルール
  プロモ実行時:  promoStack = min(3, promoStack + 1)
  試合出場時:    MQボーナス適用後、promoStack = 0（全消費）
  シーズン末:    promoStack = 0（リセット）

■ MQボーナス
  bonus = promoStack × 🔧 1.3
  最大: 3 × 1.3 = +3.9（表示上+4）
```

### §3-2 スケール比較

| ボーナス源 | MQ加算 | 条件 |
|-----------|--------|------|
| 因縁「因縁」 | +2 | 試合3回以上 |
| 因縁「宿敵」 | +4 | 試合6回以上 |
| コーチmqBonus | +2〜3 | コーチ雇用 |
| プロモ1回 | +1.3 | 練習1週犠牲 |
| プロモ3回 | +3.9 | 練習3週犠牲 |

→ 1回だけではほぼ誤差。3週投資して因縁「宿敵」並み。ただし練習3週分を失うコストは大きい。「タイトルマッチ前に集中プロモ」という限定的な戦略として成立する。

### §3-3 適用箇所

`simulateMatch` の外部ボーナス（Pass2）で加算。既存のコーチボーナス・因縁ボーナスと同じレイヤー。

```js
// engine.js — simulateMatch のPass2内
const promoBonus = (left.promoStack || 0) * PROMO_MQ_PER_STACK;  // 🔧 1.3
// right側も同様
externalMQ += Math.max(promoBonus_left, promoBonus_right);
// ※ 両者のうち高い方を採用（片方だけプロモしてても試合の質は上がる）
```

### §3-4 データ構造

```js
// fighter に追加
promoStack: 0,  // 0〜3、プロモ実行ごとに+1、試合出場で0リセット
```

## §4 お任せロジックの最適化

### §4-1 現状

```js
// balance: 興行週→プロモ / 練習週→練習
if (action === 'balance') action = isShowWeek ? 'promo' : 'practice';
```

問題: 人気70の選手でもpromoStack 3でも毎興行週にプロモする。

### §4-2 改修後

```js
if (action === 'balance') {
  if (nc.condition <= 30) {
    action = 'rest';
  } else if (isShowWeek) {
    // 興行週: プロモの価値があるか判断
    const popBenefit = nc.popularity < PROMO_POP_CAP;
    const stackBenefit = (nc.promoStack || 0) < 3;
    action = (popBenefit || stackBenefit) ? 'promo' : 'practice';
  } else {
    action = 'practice';
  }
}
```

→ pop 70到達済み かつ promoStack 3 の場合、お任せは自動で練習に切り替え。
